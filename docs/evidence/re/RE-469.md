# RE-469 — The KO crash on a PSP, and the first real-hardware profile

Status: COMPLETE (PSP-2000 PSPLink runs of the pushed-off, smashed-off and run-off KOs before and after the fix; host tests with the FPU traps enabled; golden matrix 197/197 with stack peaks; PSP frame profile of seven scenes)
Topics: hardware, crash, memory, stack, fpu, cpu-ai, particle, performance, animation, pack, visual-regression
Relevant files: `psp-runtime/src/{thread,profile,gu,scene}.rs`, `psp-game/src/{main,campaign}.rs`, `crates/ssb-engine/src/math.rs`, `crates/ssb-game/src/{particle,particle_tests}.rs`, `crates/ssb-game/src/computer/{mod,tests}.rs`, `crates/ssb-rom/src/{pack,ground_obj}.rs`, `crates/ssb-rom/tests/anim_lookup.rs`, `crates/ssb-capture/src/lib.rs`, `tools/{golden,stack-check,run-ppsspp-headless}.sh`, `refs/ssb-decomp-re/src/ft/ftcomputer.c`

## Question

The user reported that the game crashes when a player is KO'd after being
pushed off the stage. The last physical-PSP check was RE-361 (pack v43).
What crashes, and how fast does the game run on a PSP?

## Hardware and builds

- PSP-2000 (Slim), firmware 6.61 ARK, PSPLink v3.2.1 over USB
  `054c:01c9`, `usbhostfs_pc` serving the checkout as `host0:`.
- Pack v106 (`a319e657…d341`), `ssb64-menus.pak` `48a0fdea…032e`.
- `psp-game` built with `capture_scene_file,profile` from `a2cc86e` plus
  this batch. PRX SHA-256: before the fix `8134f4a2…1c94` (no profiler) and
  `a53332444…be86` (profiler, old stack and code); stack fix only
  `93e5cbf4…347c`; stack and CPU fixes `5ea930c5…c0dc`; final
  `3073015b…5f8`.
- Each run: `reset`, scene written to `capture_scene.txt`, `ldstart`,
  `exlist` and `thinfo main_thread` every 10 s, `exprint`/`exprfpu` and
  `scrshot` at the end, `kill`. Captures and logs are under
  `target/hw/re469/` (not committed).

## Findings

Three faults, each found on the PSP after the one before it was fixed.

| Fault | Hardware evidence | Cause | Fix |
|---|---|---|---|
| Stack overflow | `rebirth` before the fix: Breakpoint in `sceThreadManager` (EPC `0x88045E58`, RA `0x88045E14`), `main_thread` KILLED with `StackFree: 0`. A second load hung the PSP until a power cycle; so did `op-jungle` on the old PRX later | `psp::module!` gives `main_thread` a fixed 256 KiB. Battle entry needs 360,248 bytes (PPSSPP, 2 MiB stack): `enter_training` built the 161 KB `GroundObjects` and moved it. Static frames: `campaign::on_host` 281,848 bytes (the 1P battle's `BossScene` built inline), `enter_training` 270,368. PPSSPP never checks the bound | `module_with_stack!` (`psp::module!` with the size as a parameter) at 512 KiB; `GroundObjects::load` in place; the campaign's `enter_*` and `BossScene::new_boxed` out of line. Measured peak 239,016 bytes (goldens), 294,304 (`onepplatforms`) |
| `0 × inf` in the CPU's input | With the stack fixed: FPU Exception (IUV) at EPC `0x089223E8` (`play::computer_input`), `f11 = inf`, `f14 = 0`, before "Go" | `ftComputerSetControlPKThunder`'s `1.0F / sqrtf(d²)`. Inlined, LLVM folds the zero-distance case into `+inf` and computes `dx * scale` on every frame, whatever the command | `inverse_length_or_zero`, out of line: 0 for a zero distance, the stick Rust's NaN conversion already gave |
| `0 / 0` in the KO's particles | Then: FPU Exception (IUZ) at EPC `0x0898FCFC` (`particle::generator_func_run`), on the frame the pushed-off CPU entered `DeadDown` (tick ~900); `f2 = 0` | The KO explosion's generators have no velocity, so `syUtilsArcTan2` sees `(0, 0)`. LLVM divides `y / x` before the `x == 0` branch; `arc_tan`'s `1 / div` likewise; `math::atan2`'s `min / max` too | `math::div_nonzero`, out of line, in all three |

So the push-off KO crash was the third fault: every KO's blast runs those
generators, so any KO traps where the FPU traps. In `fsr` (`0x0000BE0C`)
divide-by-zero, invalid and overflow are enabled under PSPLink, as RE-201
found. Whether a PSP started from the XMB without PSPLink enables them was
not checked. The stack overflow corrupts memory below the stack in any
battle either way.

## Verification

| Run on the PSP | Result |
|---|---|
| `vspush`, `vsknock`, `rebirth`, final PRX | No exception. The CPU is KO'd through the bottom (tick 900) and side (540, SCORE +1) blast zones, loses its stock and comes back; 110 s each; `StackFree` 285,904 |
| `op-jungle`, `vs4`, `onepgame`, `bonuspractice`, `vsplayers`, `title`, final PRX | No exception, 100 s each |
| `vspush` after the stack fix only | CPU trap before "Go" (above) |
| `vspush` after stack and CPU fixes | Particle trap at the KO (above) |
| `op-jungle`, old PRX | PSPLink stopped answering 25 s in; a power cycle was needed |

The final `vspush` frame matches its new golden `f1-vs-push-ko`.

Host:

- `computer::tests::pk_thunder_on_its_target_raises_no_fpu_exception`
  enables glibc's divide-by-zero, invalid and overflow traps and steers a
  trail already on its target. With the old `1.0 / sqrt(...)` it dies with
  SIGFPE; it passes with the fix.
- `particle::tests::arctangents_of_a_zero_vector_raise_no_fpu_exception`
  checks the guarded arctangents under the same traps. It cannot fail
  without the fix: x86 code does not speculate the division the way the
  PSP build does. The hardware run is the evidence for that fix.
- `golden.sh` logs each `psp-game` scene's stack peak and fails one past
  seven eighths of the stack (`stack-near-limit`). With 256 KiB and the old
  copy, `vs4`, `vspush` and `vsknock` fail at 262,144 while their pixels
  match. `tools/stack-check.sh` does the same for the 1P Game and opening
  scenes the matrix does not hold.
- New goldens: `vspush` and `vsknock` (Dream Land, two stocks; the
  player, spawned on the left platform, walks the standing CPU off the
  floor's end at stick 46, 13.8 a frame against the 13.5 two jostled
  fighters separate at, or smashes it at 250%).

## Performance

`ssb_psp_runtime::profile` (feature `profile`, compiled out by default)
writes, every 120 frames, frames per second and per-span averages to
`profile.log`. Final PRX, live scenes (`@4000` keeps the scene running):

| Scene | FPS | Frame ms | Update | of which fighter anim / joints | Draw | Vblank | Free memory (min) |
|---|---:|---:|---:|---:|---:|---:|---:|
| Title attract demo, 2 fighters (`title@4000`) | 15.4 | 64.9 | 21.1 | 10.6 / 6.5 | 25.4 | 14.6 | 2,994,688 |
| Opening Jungle (`op-jungle@1200`, after its battle) | 29.9 | 33.4 | 0 | — | 18.5 | 11.7 | 1,346,816 |
| VS, 4 fighters, Dream Land (`vs4@4000`) | 8.1 | 122.8 | 70.0 | 43.0 / 13.4 | 43.0 | 6.6 | 3,682,048 |
| 1P Game, Link's stage (`onepgame@4000`) | 11.9 | 83.4 | 39.1 | 21.0 / 7.3 | 31.6 | 9.6 | 3,700,736 |
| Bonus Practice, Break the Targets | 14.9 | 66.7 | 28.5 | 10.5 / 3.2 | 25.8 | 9.8 | 3,790,336 |
| VS character select (`vsplayers@4000`) | 14.9 | 66.9 | 21.0 | — | 37.8 | 3.4 | 3,825,152 |

`ge` (waiting in `sceGuSync`) is 0.02–0.8 ms everywhere: the GE finishes
before the CPU does, so the game is CPU-bound. Vblank waits are the
rounding to the next vblank. Free memory fell to 1,346,816 bytes
(1,613,312 contiguous) in the opening's Jungle scene.

Before and after `Pack::fighter_anim`'s binary search (the only change
here that alters run time): the VS select, whose fighter's clip is
looked up every frame, went from 11.9 to 14.9 FPS, its update from 37.1 to
21.0 ms. The old PRX hung the PSP in the next scene, so no other scene has
a hardware "before". Under PPSSPP `vs4`'s animation span fell about 10%.

Hotspots, for `P5`:

1. Fighter animation (`Skeleton::tick_scaled`, the figatree interpreter):
   about 5 ms per fighter a frame, 43 ms with four; a status change
   parses the new clip a second time that frame.
2. Draw-list building on the CPU: 25–43 ms in battle, 38 ms on the VS
   select's sprites.
3. Joint sampling for gameplay (`sample_gameplay_joints`): 3–14 ms.
4. Map collision, items, weapons, camera and hit search are each under
   3.5 ms.

## Deviations

- `ftComputerSetControlPKThunder` with the trail on its target gives a
  zero stick; on the N64 it is the `(s8)` of a NaN. Rust's conversion
  already gave 0, so nothing changes on the host.
- No other behaviour changes; the golden matrix matches 197 of 197.
