# RE-516 — Samus Charge Shot crash on the PSP: FPU traps, fighter light rows, impact wave state

Status: COMPLETE (PSP-2000 under PSPLink and PPSSPP; XMB launch: Samus charge runs without a crash; FCR31 at an XMB-style LoadExec launch: `0x0e00`)
Topics: psp, fpu, audio, lighting, rendering, effects
Relevant files: `crates/ssb-engine/src/math.rs`, `crates/ssb-engine/src/audio/fgm.rs`, `crates/ssb-engine/src/rsp_light.rs`, `crates/ssb-engine/src/fpu_traps.rs`, `psp-runtime/src/fpu.rs`, `psp-runtime/src/fcr31_probe.rs`, `psp-runtime/src/meshdraw.rs`, `tools/romtool/src/main.rs`

## Question

Why did Samus's Charge Shot crash the PSP (user report from the XMB), and what else was wrong on that path?

## Findings

- Platform: PSP-2000, 6.61 ARK, PSPLink v3.2.1, `capture_scene_file` build. `main_thread` and `ssb_audio` both start with FCR31 = `0x00000e00` (V, Z, O enabled), as RE-502 found.
- Hardware, FCR31 at an XMB-style launch: PSP-2000, 6.61 ARK (SystemControl exports `SystemCtrlForUser`), PSPLink v3.2.1; `fcr31_probe` build of c159a49 plus the probe (PRX sha1 `9005aae5`, EBOOT sha1 `06b276c9`; no pack). The XMB starts a Memory Stick EBOOT with `sceKernelLoadExecVSHMs2` (apitype 0x141, key `game`), which reboots user mode; ARK's `sctrlKernelLoadExecVSHMs2` is the same call from user mode. Method, with no one at the PSP: `ldstart` the probe PRX under PSPLink; it logs its own threads, LoadExecs the probe EBOOT on `ms0:` that way, which logs and LoadExecs PSPLink's EBOOT (`ms0:/PSP/GAME/psplink/EBOOT.PBP`) back; the log is copied out through `host0:`. Two round trips: `main_thread` and a new thread with `ssb_audio`'s priority, stack and attributes start with `0x00000e00` in all four launches (PSPLink `ldstart` and LoadExec). PSPLink only writes FCR31 inside its exception handler (`exception_asm.S`), so the value is the kernel's thread default. D-050 holds.
- Hardware (user test): PSP-2000, XMB launch of the release EBOOT (commit 2e215b9, pack v110 sha1 `2ff129ec`): Samus neutral-B Charge Shot charge runs with no crash.
- Fault 1, FGM LFO (`fgm.rs` `lfo_value`): the Charge Shot sound has period 0. n_env.c divides by it; the N64's FCSR (FS|EV) gives inf, the PSP traps. Fixed with `div_ieee`; target stores go through `f32_to_i32_sat`. PCM is bit-identical (`pcm_hash_golden`).
- Fault 2, RSP light (`rsp_light.rs` `fixed_rows`): `(v * 65536.0) as i32` reaches 2^31 exactly and traps in `trunc.w.s`. Now `f32_to_i32_sat`, the vmadn/vmadh clamp.
- Behind fault 2, a real bug: PSP node matrices carry MODEL_SCALE = 32768, so the light rows were 32768x too large and saturated. Every lit fighter had a garbage light direction on the PSP since RE-514. `meshdraw.rs` `light_rows` divides it out. Against the RE-514 LLE data (772 vertices): new path RGB and shade alpha match 772/772, the old scaled path 340/772 (only 4/772 directions right). RE-514's 768/768 was host-only with unscaled rows; its PSP claim is corrected there.
- Trap audit, fixed with the same helpers: `audio/cseq.rs` and `audio/synth.rs` (1/division, 1/count), `ssb-rom/src/pack.rs` (i16 rounding of a huge `relative`, a normal division), `ssb-rom/src/scene.rs` (1/det), `math.rs` lookat normalise. Host sweep (every FGM for 40 frames, BGM 0-7) runs clean under armed traps (`every_fgm_renders_without_an_fpu_trap`); each new test was shown to fail with SIGFPE when its fix is reverted. Latent sites not proven reachable remain in PLAN.md.
- Impact wave drawn opaque: the Charge Shot loop (and Kirby's, DK's SpinningKong/HandSlap, landings) makes ImpactWave effects whose list (file 83 + 0x7C28) sets a combiner but no render mode; `efManagerImpactWaveProcDisplay` supplies `G_RM_AA_ZB_XLU_SURF`, PRIM and ENV first. `romtool` now seeds that state (`IMPACT_WAVE_GRAPH`); the wave is translucent and depth-tested without a depth write. Samus-red / wave-green pixel fractions against the N64: 0.146/0.307 (N64) vs 0.143/0.314 (PSP after, same moment); before 0.052/0.402.
- Scene scripts: the A at tick 8 left the fighter in Attack11, swallowing the B at 20, so the `samus`, `samusshot` and `donkey` goldens never showed a charge. They press B at tick 40.
- Instrumentation: FCR31 at thread start is logged (`fpu: fcr31 at start ...`); the `fpu_mask` feature (off by default) masks all enables; the `fcr31_probe` feature (off by default, ARK only) replaces the game with the launch probe above.

## Consequences

- Policy: [D-050](../../decisions/D-050.md).
- Pack content changed with the same `VERSION` 110 (see the commit message).
- Goldens rebaselined: every lit fighter row (`light_rows`), the samus, samusshot and donkey rows (scripts and wave), and stage previews with a fighter.
