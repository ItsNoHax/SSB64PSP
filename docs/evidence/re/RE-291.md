# RE-291 — `psp-game` loads and parses the real asset pack; `Psp.toml` was missing RE-255's `memsize` key

Status: COMPLETE
Topics: front-end, toolchain, asset-pipeline, visual-regression
Relevant files: psp-game/src/assets.rs (new), psp-game/src/main.rs (`mod assets`, pack load/open, `BG_TRAINING_NO_PACK`), psp-game/Psp.toml (`memsize = 1`), tools/run-ppsspp-headless.sh (stale comment fix)

**Question.** `plans/gameplay/F1.md`'s "Scene loading — still to build" section
lists `assets.rs` as the first remaining step toward acceptance criteria 4-5:
load `assets/generated/ssb64.pak` into a heap buffer and open it with
`ssb_rom::pack::Pack`, mirroring `psp/src/assets.rs`. Does the same loader,
ported into `psp-game`, actually load and parse the real ~29 MiB pack there,
the same way it does in `psp/`?

**What was built.** `psp-game/src/assets.rs` — a verbatim copy of
`psp/src/assets.rs` (`AlignedBuf`, `LoadError`, `SEARCH_PATHS`,
`load_pack()`), per F1's crate-boundary rule (own copy, not a shared
refactor of `psp/`). `main.rs` now calls `assets::load_pack()` once at boot,
opens the result with `ssb_rom::pack::Pack::open`, and holds `pack_ok: bool`
for the rest of the run. There is no `sceFont` text yet
(`plans/gameplay/F1.md`'s "Scene loading" section — real on-screen text is
later F1 work), so pack status is made pixel-provable the same way RE-290
proved screen state: the Training background is `BG_TRAINING` (`20,48,24`,
unchanged) when the pack loads and parses, or a new, distinct
`BG_TRAINING_NO_PACK` (`80,16,16`) otherwise.

**What broke, and the fix.** First headless capture showed the *new* red
`(80,16,16)`, i.e. `pack_ok == false`, despite the pack being staged
correctly (`ls ~/.ppsspp/PSP/GAME/ssb64_game_regression/` showed both
`EBOOT.PBP` and `ssb64.pak`). A temporary diagnostic build (one distinct
background colour per `LoadError`/`PackError` variant, reverted after)
isolated it to `LoadError::OutOfMemory` — `AlignedBuf::new` failing to
allocate. `psp-game/Psp.toml` had never set RE-255's `memsize = 1` PARAM.SFO
key (`psp/Psp.toml` has had it since RE-255: the ~25.6 MiB pack exceeds the
~20-24 MiB default user partition, and RE-255/256 established that
PPSSPPHeadless only reads `MEMSIZE` for an installed `PSP_GAME` directory,
which is exactly how `tools/run-ppsspp-headless.sh` stages both crates).
Adding `memsize = 1` to `psp-game/Psp.toml` fixed it — same key, same reason,
just never carried over when the crate was scaffolded in RE-289 (a scene
that draws no real assets doesn't need real RAM, so this was
theoretical-but-untested until this session).

**Verification.**

*Build.* `cargo psp --release` (plain, no features) succeeds. `psp/` is
untouched (`git status --short` shows only `psp-game/Psp.toml`,
`psp-game/src/main.rs`, `tools/run-ppsspp-headless.sh` modified, plus the new
`psp-game/src/assets.rs`).

*Headless capture, diagnostic (before the `memsize` fix).* One distinct
colour per `LoadError`/`PackError` variant, sampled at the Training
background pixel: `(255,128,0)` — `LoadError::OutOfMemory` exactly. No other
variant fired.

*Headless capture, diagnostic (after the fix).* Same diagnostic build,
rebuilt with `memsize = 1`: `(0,255,0)` — `Ok(Ok(_))`, i.e. the pack loaded
*and* parsed.

*Headless capture, real binary logic (final).* Diagnostic reverted to the
shipped `if pack_ok { BG_TRAINING } else { BG_TRAINING_NO_PACK }` logic,
rebuilt, recaptured: Training background `(20,48,24)`, an exact match to
`BG_TRAINING`'s literal value — `pack_ok == true` through the real code
path, not just the diagnostic. No error/panic/reject lines in the PPSSPP
log on any of the three captures.

*Cleanup.* Final interactive (no-features) EBOOT rebuilt after all
diagnostics were reverted; SHA-256 recorded in `STATUS.md`.

**Confidence: high.** `psp-game` now loads and parses the real
`assets/generated/ssb64.pak`, the first item of `plans/gameplay/F1.md`'s
"Scene loading" list. Still open: the pack is loaded but nothing is drawn
