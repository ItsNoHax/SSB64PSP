# RE-532 — Opening CPU cost on a PSP-2000: exact clip and lighting rewrites, light pre-pass, chunked vertex blocks and a new link order

Status: COMPLETE (PSP-2000, 6.61 ARK, PSPLink v3.2.1, `capture_scene_file,frame_timer` builds with audio on, `REPORT_FRAMES` temporarily 60, pack v117 by link beside the host0 PRX; base 0f1cdfc)
Topics: performance, hardware, cache, link-order, rendering
Relevant files: `crates/ssb-engine/src/guard_clip.rs`, `crates/ssb-engine/src/rsp_light.rs`, `psp-runtime/src/meshdraw.rs`, `psp-runtime/src/gu.rs`, `psp-game/link-order.txt`

## Question

After RE-530 the opening still missed its targets on a PSP-2000. Where does the remaining CPU go, and what can be cut without changing a pixel?

## Findings

- Room clip census (`profile`): about 50 `clip_submission` calls a frame, about 20 rebuilt prims with about 130 triangles, of which about 65 cross the guard band; the rebuild CPU is the crossing triangles, not the inside ones. The scan itself is about 0.3 ms. An index-pool polygon clip (no per-plane vertex copies), encoding each clip vertex once and writing clip vertices through the cache cut the `rebuild` span from 3.1-3.3 ms to about 2.0 ms. Inside runs of a rebuilt prim are drawn from the original submission.
- Lit census, Run: 216 prims, 208 lit, 122 lit meshes, 168 distinct light keys (1.38 a mesh) over mostly disjoint vertex ranges. A per-mesh lit buffer would light more vertices than the per-prim expand, so it was not built.
- Per-prim costs (Run, `profile`): `apply_material` about 20 us a prim, of it the per-node light direction 1.4 ms a frame; one `sceGuGetMemory` about 0.85 us and every `sceGumDrawArray` about 3.3 us (both update the stall address, a syscall). A light-direction pre-pass over all mesh nodes of a fighter-lit object (one tight loop before the node loop, same matrices and function) cut the light span 1.41 to 0.44 ms. Carving vertex blocks from an 8 KB list chunk cuts about 200 stall-address syscalls a frame to about 25.
- The exact shade simplification (base = a*32767+128, dot 0 answered from a precomputed colour), the costume mesh memo and the texture-header decode skip gave no resolvable gain; kept because exact, tested and inside the searched order.
- Layout dominates single-item A/Bs: code that never runs in a scene moved it by up to 1.6 ms (the pre-pass code made the room, which never runs it, 0.75 ms slower). Item gains under about 1 ms are only resolvable as relinks of one saved build.
- New link order (8 seeds, 50,000 iterations, trained on room, fighter and vs4 traces, 381 names): model misses -22%. On hardware every searched order beat the old one; the chosen one (s2) was best or tied in every scene: 2.0 ms in the room, 1.5 in Run, 2.4 in Yoster, 1.1 in `vs4@2400`; Clash did not move (18.0 ms).
- Output is bit-identical: 218 of 218 goldens unchanged, and the room (which rebuilds about 20 prims a frame) matched HEAD at ten extra temporary ticks.
- `vs4@2400` at HEAD runs 17.7 ms busy / 48.5 FPS on this PSP-2000, against RE-500's 13-14 ms / 59.3 FPS: VS slowed between RE-500 and HEAD (not this batch; now 16.0 ms / 56.0 FPS).

## Consequences

- Targets: room 2-5 under 10.5 ms not met (11.5); room 2-12 at 55 FPS met; Run/Yoster/Clash under 17 ms not met (17.6/17.3/18.0), 45 FPS not met (40.5/38.1/34.9). Jungle and Sector improved; fighters, portraits and Standoff no worse.
- Remaining levers: `bind_texture` (121 binds a frame at about 11 us), the lit expand's memory traffic (about 1.2 us a vertex), `sceGumDrawArray`'s stall-address syscall per draw (about 3.3 us, 216 draws in Run); Clash did not respond to the link order.
- An order fits only the code it was searched on: re-search when hot code changes size (RE-494).
