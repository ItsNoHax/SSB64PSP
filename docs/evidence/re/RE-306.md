# RE-306 — Material-aware alpha compensation (RE-305 follow-up)

Status: COMPLETE (software and PPSSPP; physical-PSP capture unavailable this batch)
Topics: texture, asset-pipeline, pack, psp-ge, visual-regression
Relevant files: crates/ssb-rom/src/filter_compensation.rs, crates/ssb-rom/src/pack.rs, tools/romtool/src/main.rs

**Problem.** RE-305's build-time N64 3-point compensation optimized only RGB;
candidate alpha was copied unchanged from the source texture, and the final
error metrics were RGBA max error even though alpha was never actually
touched. RE-305's own "Remaining deviation" section named the consequence
directly: "Holding alpha texels... exact intentionally leaves some error,"
and the Dream Land canopy's visible `103:0x5F0` variants were noted as
"alpha holds their residual max."

**Material classification (`filter_compensation::AlphaPolicy`).** This batch
adds a three-way classification -- `Opaque`, `Cutout { greater_or_equal,
threshold }`, `Translucent` -- derived from the same real runtime alpha state
the GE draw path itself consumes, not assumed. `pack::material_alpha_state`
extracts a primitive's `alpha_test`/`alpha_compare_threshold`/`blend_color`/
`translucent`/`alpha_blend` fields into the exact bit pattern
`pack::alpha_gate` already resolves for `sceGuAlphaFunc` at runtime
(RE-195), so "what threshold will the GE really test against" is one call
into existing, tested logic rather than a second implementation. `translucent
&& alpha_blend.is_some()` mirrors `add_mesh`'s own `ALPHA_BLEND` gate
(RE-129/RE-130): `translucent` alone never enables real GE blending.

Because a physical texture can be bound by primitives under different
policies, the packer's texture-variant cache (`TexKey`) now carries
`AlphaPolicy` as an identity field alongside the existing algorithm-version/
coverage-hash/animated-relationship fields, so each policy compensates and
packs its own immutable variant rather than guessing one shared answer.
`ALGORITHM_VERSION` is bumped 1 -> 2.

**Per-policy behaviour.**

* **Opaque** -- alpha is forced to 255 and the solver's gradient-descent
  update skips the alpha channel entirely (no wasted iterations). Critically,
  the *admission and acceptance gates* also exclude alpha
  (`measure_samples_impl(..., include_alpha: false)`): an opaque primitive's
  alpha is never sampled by the renderer, so 3-point-vs-bilinear alpha
  reconstruction noise on a channel nothing reads must not veto -- or be
  credited toward -- a real RGB improvement. (An earlier version of this
  change forced alpha to 255 but still gated on full RGBA metrics; a
  regression test with deliberately garbage source alpha caught the bug
  immediately, since a large synthetic alpha byte legitimately diverges from
  "255" and the old gate rejected an otherwise-good RGB candidate for it.)
* **Cutout** -- alpha is optimized through the same objective as RGB, then
  re-measured with a new `count_cutout_mismatches` check: for every measured
  sample, the pass/fail classification against the real runtime threshold
  (from `AlphaPolicy::Cutout`) must agree between the original's 3-point
  reference and the candidate's measured bilinear sample. Any mismatch
  reverts alpha to the source's exact per-texel bytes (RGB stays optimized
  either way). The same check runs again after CI4/CI8 palette quantization
  or RGBA5551 quantization, since snapping to the nearest existing palette
  entry can move alpha a second time -- the float solve being silhouette-safe
  does not guarantee the quantized result is.
* **Translucent** -- alpha is optimized fully, gated on the same SSE/`>=8`/
  max-error rule as RGB, plus a new requirement: the premultiplied "visible"
  SSE (`visible_rgb = rgb * alpha / 255`, requirement 5) must not regress.
  This is what stops a translucent candidate from trading a raw-RGBA win for
  a worse *seen* result, and stops fully- or near-transparent texels' RGB
  (garbage by construction, since nothing ever displays it) from dominating
  that decision -- the multiplication suppresses a huge raw RGB diff exactly
  in proportion to how invisible it is. `Metrics` keeps the existing raw
  RGBA fields unchanged and adds `visible_mean`/`visible_max`/
  `visible_squared_error` alongside them, per requirement 5's "keep the
  existing metrics, do not replace them."

**Tests.** `crates/ssb-rom/src/filter_compensation.rs` adds: a translucent
gradient-alpha case (alpha actually moves, visible SSE does not regress); a
binary hard-edge cutout case (silhouette classification proven unchanged via
`count_cutout_mismatches`); an opaque case (alpha forced to 255, not merely
copied, while RGB still improves); a transparent-RGB-garbage case (raw `max`
sees a 255 diff under alpha 0 on both sides, `visible_max`/`visible_mean` see
0); a classification unit test (`AlphaPolicy::classify`). Together with the
two unchanged pre-existing tests (saddle improvement, flat-texture decline)
and the pre-existing addressing-variant test, the module's suite is now 8
tests, all passing.

**Archive-wide census (US ROM, two independent builds, byte-identical
SHA-256).** Rebuilding from the same ROM this session, with and without this
batch's changes, reproduces RE-305's own figures exactly for the "before"
build (406 variants, 274 CI4/132 RGBA8888, mean 1.947 -> 0.876/255, `>=8`
7.062% -> 2.044%, `>=32` 0.483% -> 0.198%, 494,368 level-0 bytes, pack
30,172,496 bytes) -- confirming an apples-to-apples comparison. The "after"
build:

* **404 compensated variants** (267 CI4, 137 RGBA8888): 364 Opaque, 27
  Cutout, 13 Translucent.
* Level-0 promotion cost 492,352 bytes (-2,016 vs before); full pack
  30,158,688 bytes (-13,808 bytes, -0.046%) -- alpha-aware compensation is
  *cheaper* overall, not more expensive: excluding alpha from the Opaque gate
  lets a few previously-rejected small RGB-only improvements through while
  also declining a few previously-accepted RGBA8888 promotions whose only
  justification was alpha noise nothing reads.
* Unique compensated `(file, offset)` locations rose 121 -> 124 (net): 5
  locations dropped out, 8 newly qualify -- expected, since `AlphaPolicy` now
  partitions the texture-variant cache and a location's total variant count
  can shift even when its own pixel data is untouched.
* Of the 13 **Translucent** variants, all are Dream Land's canopy decorative
  blossoms (`103:0x5F0`, three sizes) and five other stage translucent
  textures (`103:0x2DE0/0x2E90/0x2F40`, `106:0x920/0x548`, `107:0x3310/
  0x1260`, `110:0xEA8/0xA68`×2). Every one of them improves: mean error for
  `103:0x5F0`'s three variants falls 5.154/7.995/4.309 -> 0.974/1.930/1.037
  (previously RE-305 could only reach 2.062-5.195 while holding alpha exact
  -- alpha genuinely was the residual, exactly as RE-305 predicted).
* **30 baseline variants** where the pre-existing 3-point-vs-bilinear gap
  was alpha-dominated (raw `max` exceeded the premultiplied `visible_max`,
  i.e. alpha contributed more to the worst-case error than anything visible
  would show): **all 30 improved** in mean error and none regressed in max.
* Mean per-variant `>=8/255` sample rate: 6.892% -> 1.392%; `>=32/255`:
  0.444% -> 0.048% (both improved beyond RE-305's own already-compensated
  figures, since RE-305's "before" here already includes its own RGB-only
  compensation).

**Format/transparency-semantics preservation.** CI4/CI8 candidates are still
quantized to the *existing* immutable palette (`quantize_to_palette`) before
any promotion decision, and animated indexed textures are still skipped
entirely (`preserve_palette_semantics`) -- neither of RE-305's format/
animation invariants changed. RGBA5551's 1-bit alpha is a natural match for
`Cutout` (binary pass/fail already matches the format's own precision); for
`Translucent` textures stored as 5551 it is an existing, unrelated format
limitation, not something this batch changes. Mirrored variants go through
the same `mirror_extend`-then-compensate pipeline as before; nothing in this
batch touches addressing.

**PPSSPP verification.** All 13 fighter goldens pass at 0 differing pixels
(no fighter geometry binds any of the textures this batch's classification
or gate change touched). `tests/golden/r0-dream-land-default.png` and
`tests/golden/r1-mvopeningroom.png` were refreshed: both changes are real,
localized, and explained -- Dream Land's canopy blossoms render with crisp
optimized alpha edges instead of the old blurry blobs (the exact texture
RE-305 named as alpha-limited), and `mvopeningroom`'s striped wallpaper/
floor/door show fine RGB-level differences from the Opaque gate no longer
being vetoed by alpha noise on textures nothing reads alpha from. Two
independent captures of each refreshed scene (6s and 30s past the freeze
tick) are byte-identical, matching RE-123/RE-305's own determinism
methodology.

**Pre-existing environment finding (not part of this batch, flagged rather
than fixed).** While validating the above, comparing this session's
PPSSPPHeadless build against the *already-committed* `r0-dream-land-default`
and `r1-mvopeningroom` goldens -- using completely unmodified `git stash`
code and the old pack -- still showed ~194-196K differing pixels
concentrated on stage geometry that carries material/palette animation
(tree canopy, grass, dirt), with no code or pack difference at all. The
content was visually identical (same blurry canopy blossoms in both), so
this is capture-timing or PPSSPP-version drift in the previously-committed
goldens, not a rendering regression -- isolated by testing pristine code
against the old pack before touching anything. `tests/golden/
r1-stage-sector.png` shows the identical symptom (134,020 differing pixels
against pristine code and the old pack) and was therefore **left
untouched** by this batch -- its staleness predates and is unrelated to
this work. This is worth a dedicated investigation (why does PPSSPPHeadless
capture-timing determinism hold for fighter/no-stage-animation scenes but
not stage scenes with material animation?) but is out of this batch's scope.
