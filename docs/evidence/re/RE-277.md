# RE-277 — Dense per-texel sweep clears the addressing formula itself; redirects RE-272/274/276 toward GE-side minification, not an index bug

Status: COMPLETE — root cause found and fixed, see RE-280/RE-281
Topics: texture, fighter, hardware, visual-regression
Relevant files: crates/ssb-rom/src/n64_addressing.rs, crates/ssb-rom/src/texture.rs, crates/ssb-rom/src/mesh.rs, psp/src/meshdraw.rs

**Question.** RE-276 narrowed RE-272/274's Mario-face artifact to hypothesis
(b): a real PSP-side addressing/scale bug, not a faithfully-reproduced ROM
quirk. RE-274 named the concrete next step: run this exact axis's parameters
through `n64_addressing`'s hardware reference model and the PSP-lowering
model directly and diff them at concrete UV values, "the way RE-220 did for
the general case." RE-220/RE-221/RE-222's archive-wide census already reports
0/810 divergence for ordinary mirror+clamp axes, but that census samples
per-vertex UV extremes, not the dense interior of one unusually wide-overscan
triangle — RE-274 explicitly left open whether this instance's magnitude
(3.46x/1.19x the tile, sampled points a normal-magnitude axis would never
reach) breaks the model somewhere between vertices.

**Measurement.** Confirmed the exact texture instance still measures the same
as RE-274 (`romtool textures ROM --file 296`): `32x32 Ci/Bits4 <- +0x6F98`,
`uv span 110.6x38.2 texels = 3.46x1.19 repeats`. Added a temporary
`#[cfg(test)]` probe to `crates/ssb-rom/src/n64_addressing.rs` (reverted after
use, matching RE-274/RE-276's own precedent) that sweeps `address_axis` (the
`angrylion-rdp-plus`-transcribed hardware model) against `psp_lowering_axis`
(this project's own PSP-lowering model) at **every real integer texel** the
primitive's measured UV bbox reaches, not just its 19 vertex extremes:

* S axis (`mask=5` → 32-texel period, `mirror=true`, `clamp=true`,
  `drawn_width=64`): swept `-31..=80` texels (the full measured `u -993..2545`
  S10.5 range) — **0 mismatches**, including every texel past the drawn
  rect's own 64-texel far edge, where the axis is deep into clamp territory.
* T axis (`mask=5`, `mirror=false`, `clamp=true`, `drawn_height=32`): swept
  `-7..=32` texels (the measured `v -217..1005` range) — **0 mismatches**.

**Conclusion.** The addressing *formula* — both the hardware reference model
and this project's PSP-lowering abstraction of it — agree bit-for-bit at
every real texel this primitive's geometry reaches, densely, not just at
vertices. This rules out "the addressing math diverges somewhere in this
wide-overscan triangle's interior" as RE-272/274's cause. Combined with
RE-276's live N64 capture (clean, no artifact) and this project's own
archive-wide 0/810 census, three independent addressing-side checks now all
agree the bug is not in the discrete texel-index computation.

What remains unexplained is the gap between "the addressing formula is
correct" and "the rendered pixels are still wrong on both PPSSPP and physical
PSP." The next place to look is no longer index arithmetic but how the GE
*samples* around it: this primitive is a severe minification case (a 64-wide
baked image stretched by a 3.46x UV span onto what RE-274 measured as a
whole-head-sized, not small, screen region) with no mipmap chain (`RE-127`:
`G_TL_TILE`, LOD forced to level 0 throughout this project, matching the ROM's
own real command stream) and no anti-aliasing on the PSP GE path. The real
N64 RDP does per-pixel coverage-based anti-aliasing that this port does not
reproduce; if that AA is what hides aliasing from a comparably wide,
non-mipmapped UV sweep on real hardware, the "repeating, aliased pattern"
RE-272 described is the textbook signature of undersampled minification, not
a wrong texel index. This is not yet measured, only newly the best-supported
remaining hypothesis after this record's negative result — the next step is
to check the PSP GE's `sceGuTexWrap(Clamp)` edge-sample behavior and/or
minification behavior directly (a small synthetic test primitive with a known
mirrored pattern and a controlled, large UV sweep, captured on PPSSPP/physical
PSP and compared pixel-for-pixel against what the addressing model predicts
at each destination pixel, not just each source texel) before reaching for an
`ACCEPTED_DEVIATION`.

**Confidence: high** on the measurement (exhaustive integer sweep, not a
sample); the redirected hypothesis itself is not yet independently confirmed.

**Closed by RE-280/RE-281.** The redirected hypothesis (GE-side minification/
sampling, not the addressing formula) led to RE-278's fixed-coordinate rig
and then RE-280's `Ci4`/`PsmT4` nibble-order root cause. Fixed and confirmed,
see RE-281.
