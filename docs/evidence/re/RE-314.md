# RE-314 — Texture dimensions over 512 overflow the GE `TSIZE` encoding

Status: COMPLETE (host test, PPSSPP software A/B captures, 11 stage goldens refreshed; physical PSP not captured)
Topics: texture, psp-ge, pack, visual-regression

Relevant files: `crates/ssb-rom/src/psp_texture.rs` (`ge_texture_dims`,
`GE_MAX_TEXTURE_DIM`), `psp-runtime/src/meshdraw.rs` (`bind_texture`,
`apply_texture_mapping`), `psp-asset-viewer/src/main.rs` (stage and material
animation ticks), `TODO.md`

**Question.** The RE-312 visual review saw two things it read as a state leak
from large RGBA8888 binds:

1. With review candidate v799 or v800 (`121:0x30` as 448-wide `Psm8888`,
   mesh `138:0x1DB8` prims 9/10), graph `138:0x2998` shows two thin pillars
   magenta (~206,0,206).
2. With v901 or v902 (stage 35, Board the Platforms (Falcon)), the same
   23 pixels of another primitive change.

Neither is a GE state leak. They have two unrelated causes.

## 1. The magenta pillars: `TSIZE` overflow

**Bisection.** All captures use PPSSPPHeadless (software GE) with
`SSB64_CAPTURE_OBJECT=138:0x2998`. Primitives were hidden by setting their
pack `index_count` to 0.

| Pack | Hidden | Magenta px |
|---|---|---|
| c799 | none | 665 |
| c799 | prim 9 (v799's own site; no bind, no draw) | 665 |
| c799 | prims 0, 1 (textures 790, 791) | 665 |
| c799 | prim 10 (texture 800) | 665 |
| c799 | textures 783, 801, 802, 803 | 665 |
| c799 | prim 7 (texture 797) | 0 |
| shipped pack + 1,223,104 zero bytes | none | 0 |

The magenta is drawn by prim 7, not prims 0/1. It persists when texture 799
is never bound, so no bind state carries over.

**Cause.** Texture 797 is `121:0x30`'s 576×64 variant, padded to stride
1024. rust-psp's `sceGuTexImage` encodes each `TSIZE` dimension as
`31 - ctlz(dim & 0x3FF)`. For 1024 that is `-1`, so the whole `TSIZE`
register becomes `0xFFFFFF`. The GE then sees log2 15 (32768) on both axes.
`sceGuTexScale` still normalizes against 1024 and 64, so every texel
coordinate is scaled 32× and 512× too far. PPSSPP clamps each coordinate to
511 (`Sampler.cpp`, `ApplyTexelClampQuad`). Rows up to 511 at a 512-byte
buffer width reach about 256 KB past 797's data. Those bytes belong to 798,
then 799. When 799 is T4, the pillars show plausible greys. When it is
RGBA8888, the same bytes read as 4-bit indices give magenta. The shipped
render of these pillars was already wrong; it only looked right.

The same encoding breaks every texture whose padded width or height is
over 512. Texture 791 (16×576, height 1024) gets `TSIZE` `0xFFFF04`. In the
shipped pack, 48 textures do this. Stages 6, 10, 21, 24, 27, 29, 33, 35, 36,
37 and 39 draw them. Their shipped goldens show the typical symptom:
stretched streaks of one clamped texel row or column.

**Fix.** `ssb_rom::psp_texture::ge_texture_dims(stride, height)` returns the
padded power of two capped at `GE_MAX_TEXTURE_DIM` (512).
`bind_texture` declares that size to `sceGuTexImage` and keeps the real
stride as the buffer width. `apply_texture_mapping` normalizes against the
same capped size. A texel below 512 now maps to its own address. A texel at
512 or above clamps or wraps inside the first 512, which is all the GE can
address. Reads never leave the texture's own rows. The pack is unchanged.

Prim 7's UVs reach u = 576 (`0..575.97` texels), so its last 64 columns
still clamp to column 511. Texture 791's UVs stay below 480, so its whole
used range is now in reach. Splitting or rescaling textures over 512 is
still open (`TODO.md`).

**Verification.**

- Host: `psp_texture::tests::ge_texture_dims_never_exceed_the_encodable_512`
  checks 797 and 791's cases, and that every capped dimension for 1..=4096
  round-trips through rust-psp's encoding. With the cap removed, the test
  fails.
- A/B, fixed runtime, graph `138:0x2998`: shipped pack vs c799 differ in
  6 pixels ≥ 32 and 0 magenta pixels (before: 1,009 and 665).
- Goldens: control stage 1 is byte-identical. The 11 stages above change.
  To prove the change is confined to the over-512 textures, all
  88 primitives that bind one were hidden in the pack. With them hidden,
  old and new runtime captures are byte-identical on all 11 stages.
  The 11 goldens were refreshed; each new capture was repeated once and
  matched byte for byte.

## 2. The stage-35 pixels: animation ticks per render frame

**Bisection.** With the fixed runtime, v901 and v902 still share 66 changed
pixels (23 ≥ 32) at native (228–231, 222–237). Hiding stage-35 primitives
one group at a time isolates mesh `144:0x4018` prim 0 (texture 646, 64×16).
Its descriptor, vertices, indices, texture and palette are byte-identical in
both packs; only its vertex and index addresses move.

| Pack (only that primitive drawn) | Differs from shipped? |
|---|---|
| shipped, its vertices/indices copied to two other addresses | no |
| c901, its vertices/indices copied back to the shipped addresses | yes |
| shipped + 0x4A940 zero bytes appended (c901's size) | yes, identical to c901 |

So the pack's **size** decides the result, not its contents. An
instrumented build logged the render-frame count at the tick-240 freeze:
242 with the shipped pack and 241 with the padded one.
`psp-asset-viewer` calls `stage_anim.tick` and `material_anim.tick` once
per *render* frame, outside the fixed 60 Hz simulation loop. A larger pack
changes emulated load timing. That changes how many render frames run
before the freeze, and so the stage's animation pose at capture. v901/v902
only exposed this through the pack size they add.

This is a capture-determinism gap, not a rendering fault. RE-315 fixed it:
both animators now tick once per simulation tick, and a padded pack no
longer changes any golden capture.

## Related finding

PPSSPP rounds a buffer width under 16 bytes up to 16 bytes
(`GetTextureBufw`, `textureAlignMask16`). The pack stores 300 non-swizzled
T4 textures at stride 16 or 8 (8- or 4-byte rows). PPSSPP therefore reads
them with the wrong row pitch. This was found from PPSSPP source only. It
has not been measured and is not changed here. RE-319 measured and fixed
it.

No physical PSP run was made.
