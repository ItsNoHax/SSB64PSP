# RE-471 — CPU performance: worst frames, the clock and the C memory functions

Status: COMPLETE (PPSSPP cycle-model and host measurements, golden matrix 198/198; physical-PSP measurements pending)
Topics: performance, hardware, memory, collision, psp-ge, framebuffer, toolchain, visual-regression
Relevant files: `psp-runtime/src/{profile,memops,timing,meshdraw,scene,boss}.rs`, `crates/ssb-engine/src/memops.rs`, `crates/ssb-rom/src/{depth_mask,pack,campaign,title,sector}.rs`, `crates/ssb-rom/tests/depth_mask.rs`, `psp-game/src/{main,capture}.rs`, `psp-game/.cargo/config.toml`, `psp-asset-viewer/.cargo/config.toml`, `.github/workflows/ci.yml`

## Question

RE-470 brought every profiled scene to about 60 FPS under PPSSPP, but
measured averages over two-second windows. The game advances one tick per
drawn frame, so a single slow frame plays as slowdown. What are the worst
frames of every kind of scene, and what makes them slow? RE-469 found the
PSP-2000 25% slower than PPSSPP on the title demo, so the target is about
12 ms of CPU a frame on average and no frame over 16.7 ms.

## Method

- **Per-frame profile.** The `profile` feature now records each frame's
  CPU time (update plus draw, less the vblank wait) in a 0.1 ms histogram
  over the whole run and writes, with each two-second report, the run's
  median, 99th percentile, maximum (with its tick) and count of frames
  over 12 ms. A frame over 12 ms is logged with its tick and spans. A
  capture build leaves out the frames frozen at its tick and exits there;
  `stage=GKIND` in `capture_scene.txt` runs a battle on any stage, `hold`
  keeps drawing the frozen tick for the sampling profiler.
- **Scenes.** 66 runs under PPSSPPHeadless (software GE), each to its
  tick: the opening movie (`opening@3000` and each `op-*` scene), the
  title and its attract demo (`title@6000`), `autodemo`, How to Play
  (`explain@4100`); the menus (`modeselect`, `vsmode`, `vsplayers`,
  `stageselect`, `fighterselect`, `characters`, `vsoptions`, `onepmode`,
  `bonusselect`, `datamenu`, `option`, `trainingselect`, `vsrecord`,
  `itemswitch`); four-fighter battles with items (`vs4@3600` on each of
  the nine stages, `vs4@4000`, `vsteam@3600`), `vspause`, `vstimeup`,
  `vsnocontest`, the results and their wipe (`vsresults`,
  `vsresultsemblem`); Training (`training@1200`); the 1P campaign
  (`onepintro`, `onepgame@3600`, Master Hand `onepboss@3600` and
  `onepbossdefeat`, the Polygon Team `onepzako@3600`, Giant Donkey Kong
  `onepgiant@3600`, Metal Mario `onepmetal@3600`, the three bonus stages
  `onepbonus@3000`, `onepplatforms@3000`, `oneprace@3000`, and the
  clear, continue, ending, staff roll, congratulations, challenger,
  message and finale scenes); `bonuspractice@4000`.
- **Sampling profiler.** RE-470's PPSSPP build
  (`~/.cache/ssb64-ppsspp-prof`); a run ending one tick before and one
  after a spike, differenced, names what the spike frame did.
- **Equivalence.** Host tests against the code each change replaces, game
  logs compared before and after, PPSSPP captures, and the golden matrix.

## Findings

| Cost | Evidence | Cause | Fix |
|---|---|---|---|
| The clock | Every scene | The game never set the clock: 222 MHz CPU, 111 MHz bus, a game's default from the XMB. `sf64-psp` and `oot-PSP` both start with `scePowerSetClockFrequency(333, 333, 166)` | The same call first thing in `psp_main` (`timing::full_speed`); PPSSPP scales its clock with it |
| `memcpy`, `memset`, `memmove` | 10–22% of the game's CPU samples in every scene; 23 ms (at 333 MHz) of each battle's first frame | The `psp` crate defines them one byte per loop iteration, five instructions a byte. Every large Rust move or zeroing calls them; a battle's first frame builds about 0.5 MB of effect players | `ssb_engine::memops`: four bytes per load and store when the addresses share alignment, volatile so the compiler cannot call `memcpy` from it. Both binaries link with `--wrap=memcpy,memmove,memset` (`.cargo/config.toml`); the `psp` crate's definitions drop out of the ELF |
| Magnifier depth mask | 46 ms of `vs4`'s entry frames at 222 MHz with three CPUs off screen at scale 3 | Each pixel of the 32 × 32 mask's 109 × 109-pixel image was filtered through the 3-point filter | `ssb_rom::depth_mask`: a quad whose four texels agree in the bits the depth reads has one depth whatever the sample's fraction (each channel of the blend is a convex weighting of its texels, rounded to nearest), so it is looked up once per run of pixels; 965 of the mask's 1,089 quads are. Only pixels on the other 124 are blended. Rows on one texel share a list of runs; spans go to the GE 256 to a draw |
| Map surfaces | 21% of `vs4`'s game CPU, more of Race to the Finish's | Every map query walked `MapSegments`, which decoded each line and vertex from the pack as it went, several queries per fighter per tick | A stage's surfaces decoded once, in table order with each line's group, the last two stages' kept (`Rc`); the groups' existence and motion are applied per walk as before. The query kernel already rejects a segment by its bounding box, so the walk itself is now about 4% of `vs4`'s CPU and no spatial index was added |
| Master Hand's first frame | 55 ms of draw | Each new wallpaper effect scanned all 6,311 animation rows and the whole object table | `BossEffects` keeps file 114's script and objects; the boss cameras, title bakes and Arwing use the indexed `Pack::effect_anim`/`sector_anim` |
| Sprite index | 2 ms of the first frame that looks a sprite up | RE-470's sorted sprite index is built on first use | `Pack::build_indexes` at boot |
| Skinned meshes | Not measurable under PPSSPP | Each bound vertex rebuilt its source joint's relative matrix and its inverse, and the mesh was copied into uncached list memory and read back | `CachedVertexPose` per source joint; each vertex written once from the pack's copy |

`vs4@4000` on Dream Land is `vs4@3600` on its default stage, so its own
row stands for it. Leaving out each scene's loading frame (tick 8 of a
VS battle, 466 of a campaign stage), the worst frame of a four-fighter
battle fell from 56.4 ms (tick 341, three magnifiers) to 9.2, of Race to
the Finish from 19.8 to 5.2 and of the Polygon Team from 18.8 to 11.8
(its stage-clear screen).

By change, under PPSSPP for `vs4@4000` (average / 99th percentile):
the magnifier mask 10.3 / 44.1 → 8.9 / 13.3 ms; 333 MHz → 5.9 / 8.9;
word-wise `memcpy` → 5.5 / 8.3 and the entry frame 44.4 → 17.5; the
decoded map surfaces → 4.5 / 7.8; the indexes at boot, entry frame
17.1 → 15.2.

On RE-470's six scenes, by RE-470's method (two-second reports from the
third on), CPU time a frame went from RE-470's 4.0, 3.2, 9.3, 6.6, 6.8
and 2.2 ms to 1.9 (`title@4000`), 2.0 (`op-jungle@1200`), 4.6
(`vs4@4000`), 3.0 (`onepgame@4000`), 2.4 (`bonuspractice@4000`) and 1.4
(`vsplayers@4000`), all at 59.8 FPS.

Memory: the opening Jungle's lowest free memory under PPSSPP fell by
11.5 KB (2,313,216 to 2,301,696 bytes; the decoded surfaces, the mask's
quads), a four-fighter battle's likewise (4,648,192 to 4,636,672).

**What remains over 16.7 ms** is loading, not CPU work: the frames that
read a scene's files (`opening` 56, `characters` 16, `title` 4934, the
opening's scene changes) spend their time in `sceIoRead`, under PPSSPP's
I/O timing, and a battle's first frame (tick 8 of `vs4`, 466 of the
campaign stages: 14–18 ms) builds its fighters, stage and effect players,
and the 1P intro's first frame (19.4 ms) makes its models and plays each
one's animation up to its start frame. The Polygon Team's intro (ticks
105–466) is the busiest steady drawing, about 11 ms a frame.

**Hardware numbers are pending.** The PSP was unavailable; every number
above is PPSSPP's. RE-469 put the PSP-2000 within 2% of PPSSPP on four
of five battle scenes and 25% slower on the title demo. Byte-wise
`memcpy` and reading back uncached list memory cost more on the PSP's
memory bus than PPSSPP counts, so those two fixes may gain more there.

## Deviations

None. No gameplay value, drawn pixel or tick order changes:

- The clock changes how long a frame takes, not what it computes.
- `memops` copies, moves and fills the same bytes (host tests at every
  length to 69 and every alignment, both overlaps; they fail when a word
  loop's step is wrong).
- `depth_mask::rows` gives the spans sampling every pixel gives, span for
  span: unit tests on a synthetic mask (failing when the quad test reads
  one bit too few) and the real mask at 205 scales and positions. `vs4`
  captured at eight ticks with magnifiers (200–3850) is identical before
  and after; inverting the mask's depth changes the tick-370 capture.
- `MapSegments` yields the surfaces the old walk yielded, in the same
  order: How to Play's per-tick fighter log (8,198 lines) and nine
  battles' capture logs are unchanged.
- The lookups return the rows the scans returned (`anim_lookup.rs`).
- Golden matrix: 198 of 198 match.
