Status: IMPLEMENTED (decomp/ROM evidence, host regressions, paired targeted PSP goldens, both production PSP builds and PPSSPP smoke; no N64 runtime or physical-PSP comparison)

## Questions

Do items made inside an item process run in that pass? Which packed node
owns an item's root after the manager ejects descriptor 0? Do collision
joints and held items follow the light throw's TopN turn?

## Process evidence

`itManagerMakeItem` registers main at priority 3, search at 1 and hit
collisions at 0. `gcLinkGObjProcess` inserts processes in live GObj link
order. `gcRunGObjProcess` reads `priority_next` after executing the
callback, then handles the current object's pending ejection. A maker
appends a new item, so its process runs later in the current priority
pass, including when its parent is destroyed. `gcRunAll` visits priorities
from high to low: contents made by a priority-0 collision callback run
their collision process now, but their first main process is next frame.

The port's snapshot loops missed these processes. Main and collision
passes now walk the live creation list. A surviving item advances the
cursor; destruction removes the current entry without skipping its next
sibling. Allocation still uses the same sixteen structs and free list.
The effect ordinal advances independently of list compaction.

## Root and joint evidence

`itManagerMakeItem` first sets up and plays the attribute scripts, then
calls `lbCommonEjectTreeDObj`. That function removes descriptor 0 and
promotes its child, descriptor 1. The manager replaces the promoted
root's translation with the item position. `itMainSetFighterHold` adds a
kind-82 attachment parent, then resets descriptor transforms; release
ejects that attachment parent and replaces the body/root translation
with the hand position again.

The other item paths already draw from their promoted roots. PK Fire
now explicitly composes from descriptor 1, keeping its descendant scripts
without composing the placeholder or applying its root translation twice.
`StageAnimator::compose_item` leaves the viewer's ordinary composition
unchanged.

RE-383 incorrectly retained descriptor 0 as Link Bomb's root:

- File 353's graph at 0x18D8 has a placeholder, body and fuse. The body is
  descriptor 1, with rest translation (30, 90, 15); the fuse is descriptor
  2, parented to the body, with authored scale about 1.58.
- The script table at 0x1990 is `[NULL, NULL, 0x199C]`: only the fuse
  animates. A ROM-backed test compares its packed and raw poses over
  300 plays and confirms the body has no script.
- `itLinkBombMakeItem` adds kind 46 to the promoted root and `->child`:
  both body and fuse are billboards. The body retains its descriptor
  offset while held; loose, its position is the gameplay position.
- The fuse's translated position inherits the body's billboard matrix;
  its own camera-facing axes then use its spin, scale and `gGCScaleX`.
  It is not a plain-Tra child in the fighter joint's orientation.
- `itLinkBombExplodeWaitUpdateScale` writes the same body node while
  loose and held (`root->child` under the held attachment). The pool now
  records held bloat too; pickup resets the body's descriptor scale.

`ftCommonItemThrowUpdateModelYaw` rotates TopN every turn step and calls
`ftParamsUpdateFighterPartsTransformAll`; facing flips halfway. The port
already tracked the model yaw, but sampled gameplay joints and weapon
anchors from facing alone. They now use the turn yaw, as does the host
TopN collision fallback. Outside the turn statuses the exact facing axes
are retained. The same sampled path covers LiftTurn and HammerTurn.
