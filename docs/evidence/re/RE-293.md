# RE-293 — `psp-game`'s Training Mode spawns a real, physics-ticked stationary dummy target

Status: COMPLETE
Topics: front-end, physics
Relevant files: psp-game/src/play.rs (`Dummy`, `tick_skeleton_animation`), psp-game/src/main.rs (`dummy_state`, `draw_training`)

**Question.** `plans/gameplay/F1.md`'s scope requires "One player-controlled
fighter vs. one stationary/dummy target, no AI" (acceptance criteria 5's
prerequisite) and Known Limitations names it explicitly: "Single stationary
dummy target only — no CPU, no second live fighter." RE-292 landed the real
fighter and stage; no target for it to fight existed yet. Can a second,
independent `Fighter` be spawned at a distinct stage position and kept
standing — real physics/animation, no player/AI control — with the current
`ssb-game`/`ssb-rom` API, or does something block a second fighter (shared
mutable state, only one spawn point in the real pack, etc.)?

**Answer: no blocker.** `ssb_game::fighter::Fighter` is a plain, freely-
instantiable struct with no global/singleton state; `ssb_rom::pack::Pack::
spawn(stage, player)` already supports up to four spawn points per stage by
index (`MPMapObjKind` 0..=3); and `Fighter::tick` takes no input but a
per-call `set_input` — a permanently neutral `ControllerState::default()`
produces a fighter that is real-physics-ticked (gravity, ground snap via the
same collision floor walk) but never moves under its own control, which is
exactly "stationary, no AI."

**What was built.**

* `psp-game/src/play.rs`: a new `Dummy` struct (`fighter`, `skeleton`,
  `object`, `started`) alongside the existing `Play`. `Dummy::at_spawn` mirrors
  `Play::at_spawn` but reads `pack.spawn(stage, 1)` (the stage's *second*
  spawn point, distinct from `Play`'s spawn 0) and returns `None` rather than
  guessing a position when the stage has no second spawn. `Dummy::tick` calls
  `fighter.set_input(ControllerState::default(), false, false)` every frame
  before `fighter.tick`, so the target is real-physics/animation-ticked
  against the real stage collision but never receives a directional or button
  input. `Play::tick_animation`'s status-change animation-restart logic was
  factored into a shared free function, `tick_skeleton_animation`, so `Dummy`
  reuses it exactly rather than duplicating it — the same logic either one
  needs, no divergence risk between two copies.
  `Dummy` has no `psp/` equivalent (the debug asset viewer has no training
  combat), so unlike the rest of `play.rs` — a verbatim port — `Dummy` is
  `psp-game`-only, documented as such in its own doc comment so a future
  reader does not mistake it for a missed port.
* `psp-game/src/main.rs`: `dummy_state: Option<play::Dummy>` spawned alongside
  `play_state` on first entry to Training, ticked every frame `play_state` is
  (same `regression_capture` neutral-input determinism story already applies,
  since `Dummy::tick` never reads pad state at all). `draw_training` draws it
  through `meshdraw::draw_object_posed` exactly like the player fighter — its
  own pose, its own per-fighter light rebuild bracket
  (`configure_fighter_light`/`finish_fighter_light`, RE-164) — with no camera
  interest of its own, since a stationary target must not influence framing.
