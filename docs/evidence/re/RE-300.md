# RE-300 — Mario Fireball's `WEAPON_EXTERNAL` translucency: `alpha_blend` seed fixed, CLUT-alpha runtime rendering still open

Status: PARTIAL — `alpha_blend` classification bug found and fixed (tested); on-device transparency still does not appear, root cause narrowed to the PSP GE/PPSSPP CLUT-alpha path
Topics: fighter, rendering, texture, weapon, visual-regression
Relevant files: crates/ssb-rom/src/mesh.rs, tools/romtool/src/main.rs (file-297 special case), psp-runtime/src/meshdraw.rs, psp-game/src/main.rs

**Question.** STATUS.md's paused batch left one open item: rebuild the pack
after the `InitialMaterial::WEAPON_EXTERNAL` seed (added to make Mario's
Fireball direct display list draw translucent, not as an opaque card) and
confirm the `regression_capture_fireball` PPSSPPHeadless capture actually
shows transparent background pixels. This session ran that verification.

**Bug found and fixed: `alpha_blend` was never seeded.** `MeshMaterial::
alpha_blend` is derived exclusively from an in-list `G_SETCOMBINE` command
(`State::combiner`); nothing seeded it externally. Direct-ROM inspection of
file 297's display list (via `Archive::open`/`archive.load(297)`, not a
stale `romtool dump` copy — an earlier pass through a manually-reconstructed
`File` without `intern_relocs` produced garbage leading bytes and a
misleading phantom `G_SETRENDERMODE`/`G_SETCOMBINE` pair; the real,
correctly-relocated 23-command list has neither) confirms `wpDisplayDrawNormal`
(`refs/ssb-decomp-re/src/wp/wpdisplay.c:131`) sets render mode but never
combine, and the Fireball's own list never issues `G_SETCOMBINE` either — so
`alpha_blend` stayed `None` forever for this primitive, regardless of
`WEAPON_EXTERNAL`'s `translucent: true`. `psp-runtime/src/meshdraw.rs`'s
`apply_material` only enables `GuState::Blend` when *both* `TRANSLUCENT` and
`ALPHA_BLEND` are set (RE-129/RE-130's deliberate gate), so the Fireball
never actually blended — it drew as a fully opaque quad, texel-for-texel,
including its transparent background palette entry.

Fix: `InitialMaterial` gained an `alpha_blend: Option<AlphaBlend>` field,
applied by `State::material_now` only while `combiner` stays `None` (the
same "external seed until a real in-list command overrides it" shape every
other `InitialMaterial` field already has). `WEAPON_EXTERNAL` seeds
`Some(AlphaBlend::TexelOnly)` — not a guess: the packed quad's own baked
vertex alpha bytes are all `0` (`push_vertex`'s general "most vertices are
not a real coverage value" note applies here too, confirmed directly:
`vtx rgba = [255,255,255,0]` before the seed's `TexelOnly` override forces
byte 3 to `255`), so `AlphaBlend::Shade` — which trusts that byte verbatim —
would have multiplied every pixel fully transparent, while `TexelOnly` lets
the CI4 flame texture's own alpha channel drive visibility, matching the
sprite's real appearance. Regression test:
`mesh::tests::convert_sequence_weapon_external_seeds_alpha_blend_with_no_in_list_combine`.
Confirmed in the rebuilt pack directly (`PrimDesc.flags`): `ALPHA_BLEND` and
`TRANSLUCENT` both now set (`0x40250`), where they previously were not.
`cargo test -p ssb-rom -p ssb-game -p ssb-engine -p romtool` (426 tests) and
the existing 23-scene deterministic regression matrix (`r0-dream-land-default.png`
included, 0 differing pixels) both stay green — the change is additive; every
other `InitialMaterial` constant seeds `alpha_blend: None` and is unaffected.

**Still open: the capture still shows an opaque black card, not a
transparent flame.** The real ROM's own palette (decoded straight from file
297 at offset 48, RGBA5551) has entry 0 = `(0,0,0,alpha=0)` (transparent
black) and entries 1-12 = opaque fire colours (`alpha=1`). The real ROM's
own 16×16 CI4 texel grid (offset 88, decoded by hand) is a clear flame
silhouette: 159 of 256 texels (62%) are index 0 (background), the rest form
the flame shape. The *packed* PSP CLUT (`Pack::palette_data`) round-trips
this correctly byte-for-byte: `palette[0] = [00,00,00,00]`, every other
entry `[.., ff]`. So every host-side stage — ROM decode, pack conversion,
pack bytes on disk — is verified correct.

Two on-device experiments narrowed the remaining gap to the GE/PPSSPP
CLUT-alpha path specifically, not the blend-enable logic this session fixed:

1. Forcing `GuState::Blend` unconditionally on for every primitive (bypassing
   the `TRANSLUCENT|ALPHA_BLEND` gate entirely) changed the capture
   elsewhere in the same frame (Mario's own model, whose vertices are zero-
   alpha per the same `push_vertex` note, disappeared entirely) — proving
   `Blend` state genuinely does affect this renderer's output and this
   session's rebuild/capture loop is not stale. The Fireball's background
   stayed exactly as opaque as before.
2. Forcing `AlphaGate::Greater(0)` (cutout alpha-test, the same mechanism
   RE-069 validated for other translucent shapes) unconditionally on every
   primitive also made Mario disappear (same zero-alpha vertices, correctly
   discarded) but again left the Fireball's background fully opaque, not
   discarded.

Both independent alpha-consuming GE paths (`Blend` and `AlphaTest`) confirm
they work in this renderer in general, and both fail to see this specific
texture's index-0 texels as transparent even though the CLUT bytes feeding
`sceGuClutLoad`/`ClutPixelFormat::Psm8888` are byte-identical to what a
correct RGBA8888 entry 0 should be. This is a real, unresolved rendering gap
in `psp-runtime`'s CLUT/`PsmT4`-plus-alpha path (or a PPSSPP software-render
limitation for that exact combination) — no other rendering category in the
project's existing 22-scene matrix exercises a genuinely transparent (not
merely depth-tested or cutout-via-known-working-path) paletted texture, so
this may be the first time this specific combination has been exercised at
all.

**Deferred:** further diagnosis needs either GE-level tracing (PPSSPP debug
build/RenderDoc-equivalent) or a physical-PSP comparison to rule out a
PPSSPP-only limitation, neither available this session. Not blocking further
gameplay batches; parked here rather than guessed around, per this project's
