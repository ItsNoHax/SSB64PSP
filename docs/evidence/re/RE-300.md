# RE-300 — Mario Fireball's `WEAPON_EXTERNAL` translucency: `alpha_blend` seed fixed, CLUT-alpha runtime rendering still open

Status: PARTIAL — `alpha_blend` classification bug found and fixed (tested); on-device transparency still does not appear on PPSSPP *or real PSP hardware*, root cause narrowed to the GE's narrow-CLUT-texture alpha path (not a PPSSPP emulation artifact, not a CLUT-DMA alignment bug)
Topics: fighter, rendering, texture, weapon, visual-regression
Relevant files: crates/ssb-rom/src/mesh.rs, tools/romtool/src/main.rs (file-297 special case), psp-runtime/src/meshdraw.rs, psp-game/src/main.rs

**Question.** STATUS.md's paused batch left one open item: rebuild the pack
after the `InitialMaterial::WEAPON_EXTERNAL` seed (added to make Mario's
Fireball direct display list draw translucent, not as an opaque card) and
confirm the `regression_capture_fireball` PPSSPPHeadless capture actually
shows transparent background pixels. This session ran that verification.

**Bug found and fixed: `alpha_blend` was never seeded.** `MeshMaterial::
alpha_blend` is derived exclusively from an in-list `G_SETCOMBINE` command
(`State::combiner`); nothing seeded it externally. Direct-ROM inspection of
file 297's display list (via `Archive::open`/`archive.load(297)`, not a
stale `romtool dump` copy — an earlier pass through a manually-reconstructed
`File` without `intern_relocs` produced garbage leading bytes and a
misleading phantom `G_SETRENDERMODE`/`G_SETCOMBINE` pair; the real,
correctly-relocated 23-command list has neither) confirms `wpDisplayDrawNormal`
(`refs/ssb-decomp-re/src/wp/wpdisplay.c:131`) sets render mode but never
combine, and the Fireball's own list never issues `G_SETCOMBINE` either — so
`alpha_blend` stayed `None` forever for this primitive, regardless of
`WEAPON_EXTERNAL`'s `translucent: true`. `psp-runtime/src/meshdraw.rs`'s
`apply_material` only enables `GuState::Blend` when *both* `TRANSLUCENT` and
`ALPHA_BLEND` are set (RE-129/RE-130's deliberate gate), so the Fireball
never actually blended — it drew as a fully opaque quad, texel-for-texel,
including its transparent background palette entry.

Fix: `InitialMaterial` gained an `alpha_blend: Option<AlphaBlend>` field,
applied by `State::material_now` only while `combiner` stays `None` (the
same "external seed until a real in-list command overrides it" shape every
other `InitialMaterial` field already has). `WEAPON_EXTERNAL` seeds
`Some(AlphaBlend::TexelOnly)` — not a guess: the packed quad's own baked
vertex alpha bytes are all `0` (`push_vertex`'s general "most vertices are
not a real coverage value" note applies here too, confirmed directly:
`vtx rgba = [255,255,255,0]` before the seed's `TexelOnly` override forces
byte 3 to `255`), so `AlphaBlend::Shade` — which trusts that byte verbatim —
would have multiplied every pixel fully transparent, while `TexelOnly` lets
the CI4 flame texture's own alpha channel drive visibility, matching the
sprite's real appearance. Regression test:
`mesh::tests::convert_sequence_weapon_external_seeds_alpha_blend_with_no_in_list_combine`.
Confirmed in the rebuilt pack directly (`PrimDesc.flags`): `ALPHA_BLEND` and
`TRANSLUCENT` both now set (`0x40250`), where they previously were not.
`cargo test -p ssb-rom -p ssb-game -p ssb-engine -p romtool` (426 tests) and
the existing 23-scene deterministic regression matrix (`r0-dream-land-default.png`
included, 0 differing pixels) both stay green — the change is additive; every
other `InitialMaterial` constant seeds `alpha_blend: None` and is unaffected.

**Still open: the capture still shows an opaque black card, not a
transparent flame.** The real ROM's own palette (decoded straight from file
297 at offset 48, RGBA5551) has entry 0 = `(0,0,0,alpha=0)` (transparent
black) and entries 1-12 = opaque fire colours (`alpha=1`). The real ROM's
own 16×16 CI4 texel grid (offset 88, decoded by hand) is a clear flame
silhouette: 159 of 256 texels (62%) are index 0 (background), the rest form
the flame shape. The *packed* PSP CLUT (`Pack::palette_data`) round-trips
this correctly byte-for-byte: `palette[0] = [00,00,00,00]`, every other
entry `[.., ff]`. So every host-side stage — ROM decode, pack conversion,
pack bytes on disk — is verified correct.

Two on-device experiments narrowed the remaining gap to the GE/PPSSPP
CLUT-alpha path specifically, not the blend-enable logic this session fixed:

1. Forcing `GuState::Blend` unconditionally on for every primitive (bypassing
   the `TRANSLUCENT|ALPHA_BLEND` gate entirely) changed the capture
   elsewhere in the same frame (Mario's own model, whose vertices are zero-
   alpha per the same `push_vertex` note, disappeared entirely) — proving
   `Blend` state genuinely does affect this renderer's output and this
   session's rebuild/capture loop is not stale. The Fireball's background
   stayed exactly as opaque as before.
2. Forcing `AlphaGate::Greater(0)` (cutout alpha-test, the same mechanism
   RE-069 validated for other translucent shapes) unconditionally on every
   primitive also made Mario disappear (same zero-alpha vertices, correctly
   discarded) but again left the Fireball's background fully opaque, not
   discarded.

Both independent alpha-consuming GE paths (`Blend` and `AlphaTest`) confirm
they work in this renderer in general, and both fail to see this specific
texture's index-0 texels as transparent even though the CLUT bytes feeding
`sceGuClutLoad`/`ClutPixelFormat::Psm8888` are byte-identical to what a
correct RGBA8888 entry 0 should be. This is a real, unresolved rendering gap
in `psp-runtime`'s CLUT/`PsmT4`-plus-alpha path (or a PPSSPP software-render
limitation for that exact combination) — no other rendering category in the
project's existing 22-scene matrix exercises a genuinely transparent (not
merely depth-tested or cutout-via-known-working-path) paletted texture, so
this may be the first time this specific combination has been exercised at
all.

**Deferred:** further diagnosis needs either GE-level tracing (PPSSPP debug
build/RenderDoc-equivalent) or a physical-PSP comparison to rule out a
PPSSPP-only limitation, neither available this session. Not blocking further
gameplay batches; parked here rather than guessed around, per this project's
own no-unsupported-heuristics rule.

**Update (2026-09-20): confirmed on real hardware, not a PPSSPP-only
limitation.** PSP hardware (PSP Slim, 6.61, ARK/Infinity, PSPLink v3.2.1) was
connected this session (USB permissions needed a udev rule reload — the
device had enumerated before the rule took effect, leaving it root-owned;
`udevadm control --reload-rules && udevadm trigger` after replug fixed it).
Built `psp-game --features regression_capture_fireball`, loaded via
`host0:`/PSPLink following [psp-hardware](../../../.claude/skills/psp-hardware/SKILL.md),
let it run to the frozen tick, and captured a native `scrshot`. **The
Fireball renders as the same opaque black card on real hardware as in
PPSSPP.** This rules out the leading remaining hypothesis (a PPSSPP
software-renderer-only quirk) — the bug is real GE behavior, or a genuine
bug in this project's own texture/CLUT bind code that both PPSSPP and
hardware faithfully execute.

Exact repro parameters, confirmed via a throwaway `ssb-rom` example
converting file 297 directly: the Fireball's `TextureRef` is `format: Ci,
size: Bits4, width: 16, height: 16, source_width: 16, palette_entries: 13`.
At pack time this is a `PsmT4` texture with `stride_bytes = 8`
(`16 texels * 4 bits / 8`), below `can_swizzle`'s 16-byte-per-row minimum
(`crates/ssb-rom/src/psp_texture.rs:544`), so it packs **unswizzled** — a
linear 4-bit CLUT texture narrower than the GE's swizzle block width. RE-300
originally noted this may be "the first time this specific combination has
been exercised at all" in this project's own regression matrix (translucent
+ paletted + this narrow); that is now the leading remaining hypothesis for
where the bug lives, not yet confirmed.

Ruled out: the classic PSP homebrew CLUT-DMA-alignment pitfall (`sceGuClutLoad`
needing a 16-byte-aligned source pointer). `psp-runtime/src/assets.rs`
already allocates the whole pack buffer via `AlignedBuf`, explicitly aligned
to `ssb_rom::pack::ALIGN` (16 bytes) precisely because "Rust's global
allocator does not guarantee 16-byte alignment on a 32-bit target" (its own
doc comment), and `pack.rs` has an existing test
(`every_ge_blob_is_sixteen_byte_aligned`) enforcing every blob offset,
including palette data, stays 16-byte aligned within that buffer. This was a
credible independent hypothesis before checking; it is not the cause here.

**Update (2026-09-20, same session): CLUT/format ruled out entirely.**
`convert_texture` (`tools/romtool/src/main.rs`) has an existing, proven
bypass pattern from RE-283 (`is_link_boot`/`is_yoshi_head`/etc.): force a
narrow CI4 texture's `psm` to `Psm8888` so it decodes fully to direct RGBA
host-side and never touches the GE's CLUT hardware at all — established
there for a *different* symptom (scrambled/purple-black noise on other
narrow-CI4 textures) but strictly more general, since it removes the CLUT
and narrow-row-addressing path entirely. RE-283 explicitly records that
widening a texture's row to swizzle-eligible width was tried and **rejected**
as a fix for that defect class ("the defect persisted byte-identical"), so
the padding experiment planned above was not attempted — it was already
disproven by prior work.

Applying the same `Psm8888` bypass to the Fireball (`is_fireball = src.home.id
== 297 && t.data_offset == 88`, scoped to this texture only, reverted after
the experiment) and re-testing on real hardware: **the opaque black card was
byte-for-byte unchanged**, confirmed after also forcing a full `kill`+`reset`
PSPLink cycle to rule out a stale asset load. Independently dumped the
resulting packed Psm8888 texel bytes directly from the `.pak` (unswizzling by
hand): confirmed the RGBA data going into `sceGuTexImage` is correct —159 of
256 texels are exactly `[0,0,0,0]` (transparent black background), the rest
are the expected opaque fire colours. So the source data reaching the GE is
provably correct in both the CLUT and non-CLUT paths, and switching pixel
format/removing the CLUT entirely changes nothing about the symptom. **This
rules out CLUT, palette format, and narrow-texture addressing as the cause.**

Cross-checked against this project's two N64→PSP prior-art references
(`refs/sf64-psp`, `refs/oot-PSP`, already checked out for other RE work):
neither ever exercises the GE's real indexed/CLUT texture path for actual
game art. `oot-PSP`'s `psp_texture_manager.c` only uses `GU_PSM_T8` for a
synthetic 256-entry grayscale intensity ramp (`sceGuClutMode(GU_PSM_8888, 0,
0xFF, 0)`), never a real multi-colour palette; `sf64-psp` has no
`sceGuClutLoad` call anywhere in its source. Both always pre-decode to direct
colour formats, matching what RE-283 and this update both independently
concluded is the safer path on this hardware. Worth adopting as a standing
project policy question (separate from RE-300's remaining mystery) —
not actioned here.

**Ruled attribution back in:** rebuilt `psp-game` with the Fireball draw call
`if false`-gated out entirely — the black card disappeared from the capture,
confirming the card really is this primitive (not a shadow decal or
unrelated draw sharing the same screen region).

**One more falsified hypothesis:** inserted an unconditional, brute-force
GE-state override (`sceGuEnable(Blend)`/`sceGuBlendFunc`/disable
`AlphaTest`/disable `DepthTest`/`sceGuTexFunc(Modulate, Rgba)`/
`sceGuMaterial`) immediately after `apply_material` for every
translucent+alpha_blend primitive in the frame, bypassing the
dirty-tracking/state-cache logic entirely, to test whether a caching bug in
`apply_material`'s `last_flags`/`last_texture_blend` diffing was silently
skipping a needed state change for this one primitive. Result: **the captured
frame corrupted into scrambled purple/magenta noise across the whole
scene** (no exception, `main_thread` stayed alive, `exlist` empty) — the
state calls are clearly not being silently ignored in general, but this
particular combination broke rendering too broadly to read anything useful
out of it about the Fireball specifically. Reverted immediately; not a safe
avenue to keep pushing on blindly.

All experimental code (the `Psm8888` bypass, the disabled draw call, the
brute-force state override, plus throwaway `ssb-rom` examples used to
inspect packed texture bytes and flags) was reverted this session. The pack
was rebuilt clean and hardware-verified back to the original (pre-experiment)
opaque-card state. `cargo test -p ssb-rom -p romtool -p ssb-game -p
ssb-engine` all pass.

**Where this leaves RE-300:** the bug is real, reproduces identically on
PPSSPP and physical hardware, is provably not caused by wrong source data,
wrong texture format, wrong CLUT, or an obviously missing/stale GE state
call for *this* primitive's own transition (the brute-force override should
have masked a caching bug if that were the cause, and instead broke
everything, suggesting the state calls were already doing roughly the right
thing). What remains unexplored: genuine interactive GE-level step tracing
(PPSSPP's windowed GE debugger, not headless) to see the *actual* GE command
stream and its per-stage output for this exact draw call, which this session
did not attempt (it requires interactive UI stepping, not batch capture).
That is the most promising remaining next step.
