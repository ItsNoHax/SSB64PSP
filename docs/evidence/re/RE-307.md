# RE-307 — Filter-aware palette-index optimization (RE-305/RE-306 follow-up)

Status: COMPLETE (software and PPSSPP, including a user-caught visual
regression found, root-caused, and fixed within this batch, plus a fixed and
reverified `psp-runtime` double-buffer clear bug this batch's own capture
pass also found; physical-PSP capture unavailable this batch)
Topics: texture, asset-pipeline, pack, psp-ge, visual-regression
Relevant files: crates/ssb-rom/src/filter_compensation.rs, crates/ssb-rom/src/n64_filter.rs, tools/romtool/src/main.rs, psp-runtime/src/gu.rs

**Problem.** RE-305/RE-306's CI4/CI8 path quantizes the continuous compensated
RGBA solve back to the existing palette with `quantize_to_palette`: for each
texel, independently, the palette entry nearest that texel's own solved
color. That minimizes per-texel color distance, not the actual filtered
output error — a coverage sample's GE bilinear reconstruction blends *four*
texels together, so the index that minimizes one texel's own color error in
isolation is not necessarily the index that minimizes what any sample
actually reads.

**Algorithm (`filter_compensation::optimize_palette_indices`).** Seeded from
the same nearest-color assignment `quantize_to_palette` already computes
against the continuous solve (step 1: `solved`'s own per-texel nearest entry,
not `original`'s — `original`'s texels are already exact palette entries by
construction, so seeding from `original` would just reproduce the source
unchanged). Coordinate descent then sweeps every texel, and for each tries
every legal index (`0..16` for CI4, `0..palette.len()` for CI8 — a CI4 nibble
can never address a bank's 17th entry regardless of how many more the loaded
TLUT chunk carries), keeping whichever index gives the lowest *exact* summed
squared error against the real N64 3-point reference, over only the coverage
samples that texel is the **dominant** (highest-weight) corner of — see
"A user-caught regression" below for why dominance, not mere membership,
is the right scope. Sweeping stops once a full pass changes no index, or at
`PALETTE_OPTIMIZE_MAX_SWEEPS` (8) — deterministic either way.

The exact objective reuses the real measured GE sampler bit-for-bit rather
than re-deriving it: `n64_filter::sample_bilinear_addressed` was refactored
into `bilinear_taps_addressed` (which four texels a sample reads, plus its
truncated 4-bit fractional weights) and `compose_bilinear` (the one place the
truncating blend arithmetic is written); the ordinary sampler and the
optimizer's per-texel candidate evaluation both call the same
`compose_bilinear`, so there is no second, driftable copy of the
+0.5-alignment/4-bit-weight/truncating-channel formula RE-304 measured.
`n64_filter`'s own 8-test suite (unchanged assertions) confirms the refactor
is bit-identical to the pre-refactor inline version.

**Acceptance gate (requirement 10).** `convert_texture` computes both
`quantize_to_palette`'s nearest result and `optimize_palette_indices`'s
result, measures each through the same integer samplers over the same
coverage, and selects the optimized candidate only if it is not worse on
*all four* metrics simultaneously — SSE, max error, `>=8/255` count,
`>=32/255` count — else keeps the plain nearest result; for `Translucent`
policy it additionally requires the premultiplied "visible" SSE
(`measure_samples`'s existing `visible_squared_error` field) not regress,
carrying RE-306's own requirement-5 protection into this second, independent
place alpha can move. The archive census confirms the four-metric gate is
load-bearing: of the final 305 CI4/CI8 conversions, 49 had a raw optimizer
output that measured worse on at least one metric, and all 49 were correctly
rejected in favor of nearest (`index_opt=false` on exactly those 49 and no
others).

**A user-caught visual regression, root-caused and fixed within this
batch.** After this batch's first PPSSPP capture pass (see below) and an
initial golden refresh, the user reported that Dream Land's small hanging
canopy ornaments (decorative star/blossom sprites, `Translucent` policy)
looked visibly broken — fragmented into disconnected speckles with holes,
where the committed reference showed a clean solid silhouette. This was a
real defect, not a rendering trick or a false alarm: cropping and zooming the
exact ornament (file 103, offset `0x2E90`, a 16x16 purple star) against the
pre-batch golden made it directly visible on screen. Root-causing it:

* Instrumenting the specific texel that visibly changed (row 0, column 4)
  showed it had exactly **one** real coverage sample in its influence list,
  and in that sample it was a **minor** corner — blend weight 16/256, versus
  240/256 for its neighbor. The seed (nearest) value there was alpha 0
  (transparent, correct — this texel sits just outside the star's real
  silhouette). The raw optimizer flipped it to alpha 255 (fully opaque)
  because doing so nudged that *one* low-weight sample's blended alpha from 0
  to 15, marginally closer to the sample's real target of 8 — a real, if
  tiny, reduction in that sample's own squared error, with no other sample
  carrying enough weight on this texel to register how wrong an isolated
  opaque texel looks once actually rendered.
* This was not a case the new `Translucent` visible-SSE gate (above) caught,
  and checking why is itself informative: aggregate premultiplied SSE
  *improved* for every one of file 103's textures under the pre-fix code,
  including this one (visible SSE 1,435 -> 361) — a global aggregate can
  hide a single texel whose error moved the wrong way while enough other
  texels improved to still shrink the sum. The bug was not "alpha moved when
  it shouldn't have" in aggregate; it was "one nearly unevidenced texel was
  free to swing to an extreme because nothing measured its *individual*
  contribution before accepting the aggregate win."
* **Root cause:** the sample-to-texel `influence` map attributed each
  coverage sample to *all four* of its bilinear taps, regardless of how
  little weight a given corner actually carried in that sample's blend. A
  texel whose only nearby samples all weight it lightly could still have its
  candidate search "justified" by summing those thin, easily-outvoted terms
  — coordinate descent doesn't know a 16/256-weight term is barely evidence
  at all; it just sees a smaller sum.
* **Fix:** each sample is now attributed only to its *dominant* corner — the
  tap with the largest of the four bilinear weights (ties break toward
  `c00`). A texel only gets reconsidered on samples it primarily represents,
  matching "which texel is this sample really about" rather than "which four
  texels does the interpolator happen to touch." Re-running the same
  instrumented trace after the fix: texel (0,4) is no longer the dominant
  corner for any sample, is excluded from every influence list, and
  correctly keeps its seed value (alpha 0) — the star renders as a clean
  solid silhouette again, confirmed both in the isolated texture dump and in
  the full rendered scene.
* This is a real algorithmic correction, not a tightened threshold: existing
  tests (including the hand-derived `optimize_palette_indices_beats_nearest_
  when_neighbor_blend_matters` case, where the changed texel *is* the
  dominant corner of its sample) all still pass unchanged after the fix.
  `ALGORITHM_VERSION` bumps `3 -> 4` to invalidate every previously-cached
  compensated variant, since this changes the deterministic output.

**Formats/semantics preservation (requirement 8).** Palette entries,
ordering, and animation semantics are untouched — the optimizer only chooses
*which* existing entry a texel encodes, never writes a new entry. Animated
indexed textures are still skipped entirely upstream
(`preserve_palette_semantics`), so the optimizer never runs on them. CI4's
palette-bank semantics are preserved by `max_index` (16, matching the
nibble's own addressing range) rather than the bank's full loaded-chunk
length.

**Tests.** `crates/ssb-rom/src/filter_compensation.rs` adds four synthetic
tests, all passing:

* `optimize_palette_indices_beats_nearest_when_neighbor_blend_matters` — a
  hand-derived 2x2 case (worked arithmetic in the test's own doc comment)
  where nearest-to-`solved` provably picks the wrong index (measured squared
  error 25 against the real 3-point target) and coordinate descent finds a
  strictly better one (measured squared error 1) that is *farther* from
  `solved` in raw color space. The changed texel is the sample's dominant
  corner (weight 144/256), so this case is unaffected by the dominant-corner
  fix above.
* `optimize_palette_indices_respects_max_index_and_is_deterministic` — a
  17-entry palette where the exact match sits at index 16: capped to
  `max_index=16` (CI4), the optimizer picks the best reachable index `<16`;
  given `max_index=17` (CI8), it picks the exact match; two runs on
  identical input produce byte-identical output.
* `optimize_palette_indices_output_still_needs_the_cutout_mismatch_gate` —
  the optimizer is a pure RGBA-distance objective with no knowledge of a
  real alpha-test threshold, so its raw output still needs
  `count_cutout_mismatches` checked before `convert_texture` would ever trust
  it (same requirement RE-306 already established for `quantize_to_palette`);
  confirms the gate still fires on this candidate type.
* (existing) addressing-variant, saddle-improvement, flat-texture-decline,
  and the RE-306 alpha-policy suite are unchanged and still pass.

Module suite: 15 tests (was 11), all passing. `n64_filter`: 8 tests, all
passing (refactor-only, assertions unchanged).

**Runtime-memory impact: none for variants that stay CI4/CI8.** Index
optimization changes *which* existing palette entry a texel encodes, never
the texel bit width or the GE pixel format. The archive's worst-case
aggregate runtime VRAM residency can only fall, never rise, relative to
RE-306 (37 fewer RGBA8888 promotions). Build-time pack storage falls by the
237,856 bytes measured above.

**PPSSPP capture pass also found and fixed a second, unrelated, pre-existing
renderer bug.** Independently of the palette-index regression above,
rebuilding `assets/generated/ssb64.pak` and capturing Dream Land and all 13
fighter goldens initially showed large raw diffs against every committed
golden (126,780–136,820 pixels per scene). Isolating the cause (`git stash`
back to pristine code, same ROM, same old pack — reproduces the committed
golden byte-for-byte at 0 differing pixels) and then testing this batch's
new EBOOT (`--no-build`) against the *old* pack versus the *new* pack in turn
showed the diff was tied to pack content, not code, and further isolation
traced it to a second, independently-latent bug: `psp-runtime`'s
`Gpu::begin_frame` issued its per-frame `sceGuClear` *before* that frame's
own `set_viewport_pillarboxed` narrowed the scissor back down, so only the
very first presented frame, on whichever of the two swap-chain buffers
(`fbp0`/`fbp1`) it landed on, ever received a full-width clear; the other
buffer's pillarbox border was never cleared again for the program's
remaining lifetime and kept whatever was in that VRAM region at allocation
time. Which buffer the first frame lands on depends on how many frames are
presented during pack loading before the simulation's own frame counter
starts, which is sensitive to load duration -- and load duration is
pack-size-dependent, so this batch's smaller pack was enough to flip that
parity and expose the bug as a deterministic ~236-column-wide black border on
every scene. Fixed: `begin_frame` now resets the scissor to full-screen
before clearing. Unrelated to texture format, content, or this batch's
algorithm; unrelated to the palette-index regression above (a completely
different subsystem, `psp-runtime` rendering lifecycle versus build-time
texture packing) — the two were found and fixed in the same session only
because both needed a working PPSSPP capture pipeline to surface.

**Lesson.** The first PPSSPP capture pass and its (also real, also fixed)
`psp-runtime` finding were treated as sufficient verification, and an initial
golden refresh was proposed on the strength of passing numeric gates alone.
It took the user actually looking at the rendered image to catch that one
category of texture had a real, visible defect the numeric gates -- including
a premultiplied-alpha gate added specifically to catch exactly this class of
problem -- did not detect. Passing aggregate metrics is not the same as
looking at the picture; the fix here required a targeted per-texel trace,
not another gate on the aggregate.
