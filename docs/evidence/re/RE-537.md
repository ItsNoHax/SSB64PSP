# RE-537 — GE stall-address batching on a PSP-2000

Status: COMPLETE (PSP-2000 hardware frame-hash comparison, PPSSPP goldens rebaselined under D-051)
Topics: performance, ge, hardware, goldens, link-order
Relevant files: `psp-runtime/src/gu.rs`, `psp-runtime/src/meshdraw.rs`, `psp-game/link-order.txt`

## Question

Can the direct list's stall-address updates (about 3.3 us per `sceGeListUpdateStallAddr`) be batched with no rust-psp change and no PSP output change?

## Method

- `psp-runtime` writes PSPSDK's draw words itself through `sceGuSendCommandi` (`gu::draw_array`). Every 16th draw goes through `sceGuDrawArray`, the only way to move the stall address, because the rust-psp list id is private. `sceGuGetMemory` and `sceGuFinish` move it too.
- List blocks are carved from 8 KiB uncached `sceGuGetMemory` chunks (`gu::list_memory`, 16-byte aligned, separate from the cached vertex chunk, RE-360).
- N chosen by a file-toggle sweep on one PRX (PSP-2000, busy ms, summed delta against N=1: N8 -1.68, N16 -1.71, N32 -1.56, N64 -1.52). N >= 32 starves the GE in the opening's Yoster window.
- PSP output: FNV frame hash per tick, HEAD d529843 against the candidate, PSP-2000, 6.61 ARK, PSPLink v3.2.1.
- Link order re-searched (RE-500 method, 12 seeds, held-out vs4 trace); seed 2 installed after a hardware rank on vs4 busy (L2 15.73, L11 15.77, L8 15.80, L3 15.83, L4 15.84, old order 17.6).

## Findings

1. Coverage: 26,040 hardware frames, 0 differ: vs4@2400 2520, opening 4560, onepgame 1800, campaign start 1200, seven 1P stages (boss 1560; zako, metal, giant, platforms-ride, race-hazards 1200 each; bonus 1080), three Training stages (1080, 1080, 1200), vs 720, vsteam 720, vsarwing 720, cpufx-d 720, vsknock 600, stageselectview 480.
2. Batching alone gains 0.05-0.48 ms busy (vs4 -0.37). Code growth made the old link order stale; with L2 the batch is vs4@2400 17.61 to 15.73 ms (59.2 FPS), Room 14.43 to 12.40, Run 17.12 to 14.99, Yoster 18.95 to 15.52, Clash 14.50 to 13.18.
3. PPSSPP goldens move on 44 rows, stable over 6 captures (including `-j 1`). Per-row native pixels:
   - f1: cpufx-down 4, training-fireball 4, training-heavy-carry 6, training-inishie 5, training-stage-select-view 94 (y=248), training-stage-select-yoshi 50 (y=248), training-whispy-wind 5, vs-arwing 120 (y=65), vs-countdown 120 (y=65), vs-four-low-detail 120 (y=65), vs-knock-ko 6, vs-no-contest 5, vs-rays 5 (max delta 1), vs-sector 118 (y=65), vs-team 3.
   - r2: peach-castle 4; stage-bonus1 captain-falcon 1, donkey-kong 2, fox 1, kirby 2, link 9, mario 1, ness 7, pikachu 10, purin 1, yoshi 4; stage-bonus2 captain-falcon 9, fox 11, kirby 13, link 3, luigi 4, mario 4, ness 12, pikachu 5, purin 9, yoshi 6; stage-bonus3-race-to-the-finish 3; stage-final-destination 2, hyrule-castle 2, metal-mario 2, sector-z 1, small-yoshis-island 5, test-stage 2, zebes 1.
4. Crops at native resolution: r2 and small f1 differences are isolated edge pixels in clusters of 1-6. The larger f1 rows are exactly one scanline at the bottom edge of a 2D sprite rectangle (VS start lamp y=65, x 179-299, background replaces the dark row; stage-select nameplate y=248, the gold row replaces background). The row moves both ways, so no draw is dropped: it is RE-534's mechanism, softgpu `DrawRectangle` stepping UV from a range-clamped start while flush chunking moves the bin boundaries. Nothing is missing.
5. GE safety: a draw between stall moves lies beyond the stall address, so the GE cannot read it or its vertex block until a later stall move; `sceGuFinish` closes the list at frame end. Every buffer a draw names must be final when `draw_array` is called (cached blocks are written back first).

## Conclusion

Stall batching ships under [D-051](../../decisions/D-051.md). Peak memory 20,426,240 B and deepest stack 392,544 B are unchanged.
