# RE-294 — Training Mode's first real attack: Mario's jab, hitbox to hitstun

Status: COMPLETE (numeric slice) — see "Still open" below
Topics: front-end, physics, gameplay
Relevant files: crates/ssb-game/src/attack.rs (new), crates/ssb-game/src/status.rs (`Status::Attack11`, `check_attack1`, `set_attack11`), crates/ssb-game/src/fighter.rs (`tick_timers`), psp-game/src/play.rs (`Dummy::apply_hit_from`), psp-game/src/main.rs

**Question.** `plans/gameplay/F1.md` acceptance criterion 5 requires "the
player-controlled fighter executes at least one grounded attack against a
stationary dummy/target, applying decomp-accurate hitbox/hurtbox, damage, and
knockback/hitstun." RE-293 built the target; no attack existed yet. Where do
a Smash 64 attack's real numbers actually live in the decompilation, and can
one grounded attack (input → hitbox → hurtbox → damage → knockback →
hitstun) be ported end to end with numbers sourced from the decomp rather
than invented?

**Answer: yes, hitbox data is a motion-event argument list, not a table.**
There is no per-character "attack table" struct. A hitbox's damage, offset,
size, angle and knockback fields are literal arguments to
`ftMotionCommandMakeAttackColl(...)`, baked into the character's own motion
script and only unpacked into a runtime `FTAttackColl` when the animation
parser reaches that event
(`ftMainParseMotionEvent`/`nFTMotionEventMakeAttackColl`, `ft/ftmain.c:152-267`).
Mario's neutral jab's real numbers are in
`refs/ssb-decomp-re/src/relocData/202_MarioMainMotion.c`,
`dMarioMainMotion_Jab1`:

```c
ftMotionCommand dMarioMainMotion_Jab1[] = {
    ftMotionCommandWaitAsync(2),
    ftMotionCommandMakeAttackColl(0, 0, 10, 2, 1, 0, 160, 0, 0, 0, 361, 50, 0, 3, 0, 0, 0, 8),
    ftMotionCommandMakeAttackColl(1, 0, 9, 2, 1, 0, 160, 0, 0, 0, 361, 50, 0, 3, 0, 0, 0, 8),
    ftMotionCommandPlayFGMStoreInfo(nSYAudioFGMLightSwingS),
    ftMotionCommandWait(2),
    ftMotionCommandClearAttackCollAll(),
    ftMotionCommandWaitAsync(10),
    ftMotionCommandSetFlag1(1),
    ftMotionCommandEnd(),
};
```

Knockback, hitstun and the "Sakurai angle" formulas are elsewhere again:
`ft/ftparam.c`'s `ftParamGetCommonKnockback`/`ftParamGetHitStun`, and
`ft/ftcommon/ftcommondamage.c`'s `ftCommonDamageGetKnockbackAngle`/
`ftCommonDamageInitDamageVars`. None of the three files know about the
others' data; the original wires them together per-hit at runtime.

**What was built** (`crates/ssb-game/src/attack.rs`, new module — full
provenance and every simplification's rationale are in its module docs, not
repeated here):

* `MARIO_JAB1_HITBOX`: a `Hitbox` transcribed field-for-field from
  `Jab1`'s first `MakeAttackColl` call (the joint-10/forearm hitbox; the
  second, joint-9 hitbox is a documented gap, not a guess — no per-bone
  attachment exists to place it).
* `sakurai_angle_radians` — `ftCommonDamageGetKnockbackAngle` verbatim,
  including its real coarseness (a grounded hit's angle jumps from 0° to the
  42.5° cap within about 0.1 units of knockback past the 32.0 threshold; this
  is the original's own behavior, not a bug here).
* `common_knockback` — `ftParamGetCommonKnockback`'s damage-dependent branch
  (`kb_weight == 0`, which is `Jab1`'s case), with handicap/damage-ratio
  terms fixed at their singleplayer-neutral `1.0` and `recent_damage` treated
  as zero (neither system is ported).
* `hitstun_frames`, `damage_lr` (`this_fp->damage_lr = (defender.x <
  attacker.x) ? +1 : -1` — relative position, not the attacker's facing) and
  `resolve_hit`, which composes all of the above into a `HitResult`
  (damage, knockback velocity, hitstun frames).
* `crates/ssb-game/src/status.rs`: `Status::Attack11 = 190` (the real
  `nFTCommonStatusAttack11` ordinal, resolved by simulating the C enum's
  auto-increment/anchor assignments from `nFTCommonStatusControlStart`
  through to it — `10` for `ControlStart` matches the already-pinned
  `Status::Wait = 10`, so the simulation's anchor is independently
  cross-checked). `check_attack1` ports `ftCommonAttack1CheckInterruptCommon`
  restricted to the no-item case (Training has no items); `set_attack11`
  ports `ftCommonAttack11SetStatus` restricted to no combo followup (always
  ends in `ftAnimEndSetWait`, never chains into `Attack12`/`Attack13` on a
  repeated tap). `ground_interrupt` gained `check_attack1` in the original
  macro's exact priority slot (before `KneeBend`).
* `crates/ssb-game/src/fighter.rs`: `tick_timers` now clears
  `physics.vel_knockback` the instant `hitstun` reaches zero, rather than the
  original's gradual friction decay (no such curve exists yet) — held
  constant through hitstun, snapped to zero after.
* `psp-game/src/play.rs`: `Dummy::apply_hit_from(&Fighter)` — the only place
  both fighters exist together, so this is where the hitbox-vs-hurtbox test
  and hit application live rather than in `ssb-game`. Tests
  `jab1_hitbox_active(anim_frame)` (the real 2-frame window from `Jab1`'s own
  `WaitAsync(2)`/`Wait(2)`), then `spheres_overlap` against a single-sphere
  hurtbox sized from Mario's own real collision-diamond width
  (`dMarioMain_attr.map_coll` width `150.0`, halved) rather than the
  original's eleven per-bone `FTDamageColl` capsules (not yet ported). A
  `hit_by_current_attack` flag (cleared when the attacker leaves `Attack11`)
  stands in for the original's per-attack `GMAttackRecord` hit list, so one
  jab cannot hit the same target twice across its 2-frame window.
* `psp-game/src/main.rs`: `dummy.apply_hit_from(&pl.fighter)` called every
  Training tick, right after both fighters have ticked.

**Verification.**

*Unit tests* (`cargo test -p ssb-game --lib --features std`, 135 passed, 0
failed): `attack.rs`'s 11 tests pin the formulas against hand-checked
arithmetic — at 0% damage, Mario's jab (`weight = 1.0`) computes knockback
`((0*1.4)+18)*(50*0.01)+8 == 17.0` exactly, hitstun `17.0/1.875 == 9` frames,
and (17.0 being below the 32.0 Sakurai threshold) a flat 0° launch angle —
plus overlap/window-boundary tests. `status.rs` gained three tests: tapping A
from Wait enters `Attack11`; a full-stick dash input mid-jab does not
interrupt it (because `update()`'s dispatch never calls `ground_interrupt`
for a non-`is_actionable_on_ground` status, not because `ground_interrupt`
itself refuses); the jab returns to Wait exactly at its 14-frame length.
`fighter.rs` gained one test pinning the "hold through hitstun, snap to zero
after" knockback-decay stand-in. `cargo test --workspace`: 425 passed, 0
failed — no regression elsewhere.

*Build.* `cargo psp --release` (plain, no features) succeeds for
`psp-game/`; `psp/`'s own tree is untouched (`git status` shows no changes
under `psp/`). Plain-build EBOOT SHA-256:
`baa9e74fb8dcce7469f66b99062c3eb46197dc1184d76eb13e1097f51098632e`.

*Headless capture* (`tools/run-ppsspp-headless.sh --crate psp-game`,
existing `regression_capture,headless_capture` scripted-input script, tick 8,
Menu → Training confirm): no regression — the screenshot
(`docs/images/re294-jab-no-regression.png`) still shows both Marios on Dream
Land exactly as RE-293 pixel-confirmed. This capture does **not** exercise
the jab: `scripted_buttons` only taps A at ticks 4 and 8 (Intro → Menu →
Training confirm), never again once inside Training, so the attack path is
verified by the unit tests above, not by a pixel capture, this session.

**Confidence: high on the numeric slice, open on the visual one.** Every
formula and literal in `crates/ssb-game/src/attack.rs` is transcribed from a
cited decomp source and unit-tested against hand-computed values; the hit
detection and application wiring compiles and links for the real
`mipsel-sony-psp` target. What is *not* yet pixel-confirmed is the jab
actually landing on the dummy on screen — `scripted_buttons` needs a third
tap timed to land within the 2-frame hitbox window once inside Training, and
the resulting capture compared against a new golden. That is the natural
next step, not a silently-skipped one.
