# RE-289 — F1's `psp-game/` crate scaffolded: a second, independent EBOOT boots to an intro/menu state machine

Status: COMPLETE (this increment) — scene loading, real text and Training Mode's combat sandbox remain, see `plans/gameplay/F1.md`
Topics: front-end, toolchain, hardware, visual-regression
Relevant files: psp-game/Cargo.toml, psp-game/Psp.toml, psp-game/rust-toolchain.toml, psp-game/src/main.rs, psp-game/src/gu.rs, psp-game/src/input.rs, Cargo.toml (workspace exclude), tools/run-ppsspp.sh (`--crate` flag)

**Question.** F1 (`plans/gameplay/F1.md`) is the active task: build the PSP
front end and Training Mode as a *second, independent* EBOOT, separate from
the existing debug asset viewer (`psp/`). Acceptance criterion 1 requires
that second application to exist and boot independently without touching
`psp/`'s own build. What is the smallest real slice that proves that, rather
than assuming a new `cargo psp` crate will just work the same way `psp/`
does?

**What was built.** `psp-game/` — its own `Cargo.toml` (`ssb64-psp-game`,
depending on the same `ssb-engine`/`ssb-rom`/`ssb-game` crates `psp/` uses),
`Psp.toml`, and the pinned `rust-toolchain.toml` copied verbatim from
`psp/`'s (same nightly requirement, same reasoning). Added to the workspace's
`exclude` list in the root `Cargo.toml` alongside `psp/`, for the same
reason: `mipsel-sony-psp`, `no_std`, built with `cargo psp`, which needs
nightly + `-Z build-std` and would otherwise break `cargo test` on stable for
the host-side crates.

`psp-game/src/main.rs` implements a three-state machine — `Intro`, `Menu`,
`Training` — driven by the same `ssb_engine::input` edge-detection helpers
(`newly_pressed`) `psp/` already uses. The intro screen advances to the menu
on `A`/`Start`; the menu is three vertically stacked entries (`Training`
selectable, two stubbed/inert per F1's explicit allowance), navigated with
`D_UP`/`D_DOWN` and confirmed with `A`; only the `Training` entry does
anything, entering the (currently placeholder) `Training` screen, which
returns to the menu on `B`. No stocks, KO, match timer, CPU AI, or items
exist anywhere in this build — there is no code path that could reach them
(criterion 6).

**`gu.rs` is a deliberately smaller copy, not a shared refactor of `psp/`.**
F1's crate-boundary rule requires `psp/`'s own build and EBOOT to stay
unmodified, and the two apps are separate `cargo psp` crates outside the
workspace, so there is no shared-library seam to hang common GE glue off of
without either modifying `psp/` or inventing a third crate F1 doesn't ask
for. `psp-game/src/gu.rs` is its own file: display/framebuffer init, a
`begin_frame`/`end_frame` pair, and one `GU_TRANSFORM_2D` flat-rectangle
draw call — enough for the current colour-block menu, nothing else yet. The
3D pipeline (depth test, projection/view matrices, textured mesh drawing)
this increment leaves off is `psp/gu.rs`'s territory to port from once scene
loading lands (tracked in `plans/gameplay/F1.md`'s new "Scene loading" note).

**Deliberately no on-screen text yet.** RE-202 found `sceGuDebugPrint`/
`sceGuDebugFlush` reliably crashes real PSP hardware with an unaligned
instruction-fetch fault — why `psp/`'s own HUD text lives behind an
off-by-default `debug_overlay` feature, used only for interactive PPSSPP
debugging, never shipped on by default. A front-end menu is not a debug
overlay; it cannot carry that fault unconditionally. So this increment's
menu entries are colour-coded rectangles (selected/enabled/disabled), not
labels, and real text is deferred to a follow-up `sceFont` (PGF glyph
rasterisation into a GE texture) implementation — also noted in
`plans/gameplay/F1.md`.

**Verification.**

*Build.* `cargo psp --release` from `psp-game/` succeeds and produces
`EBOOT.PBP`. `psp/`'s own tree is untouched (`git status`/`git diff`
confirm only `Cargo.toml`'s `exclude` line and the new `tools/run-ppsspp.sh`
`--crate` flag changed outside `psp-game/` itself).

*Harness.* `tools/run-ppsspp.sh` was built to run only `psp/`; it now takes
an optional `--crate psp|psp-game` (default `psp`, so every existing
invocation is unchanged) rather than assuming a second, separately
maintained copy of the same 800-line script.

*PPSSPP, automated capture.* `tools/run-ppsspp.sh --crate psp-game
--no-build --seconds 8` (session unlocked, confirmed via `loginctl
show-session ... LockedHint=no` before trusting the capture, per this
project's own screenshot-harness lesson) produced a non-blank 960x544
screenshot whose full-frame standard deviation is `0.010185` — not the
flat-zero a blank/locked capture would show — and whose sampled pixels are
an **exact** match, `(24,32,64)`, to `BG_INTRO`'s literal RGB value. No
error/panic/exception/reject lines in the PPSSPP log.

*PPSSPP, manual input round-trip.* A second, manually driven instance
(same build, `tools/send-x11-key.py` synthesising key events, same fallback
the project's exhaustive stage/animation audits already rely on) exercised
the full menu state machine and confirmed every transition by exact pixel
sampling, not just "it looks different":

* Intro → Menu on the mapped Cross key (PPSSPP's default keyboard binding,
  confirmed against `controls.ini` and PPSSPP's own `NKCODE_Z = 54`):
  background went from `(24,32,64)` (`BG_INTRO`) to exactly `(16,16,24)`
  (`BG_MENU`).
* `D_DOWN` moved the cursor from entry 0 to entry 1: entry 0's rectangle
  read back exactly `(200,200,200)` (`ENTRY_ENABLED`, no longer selected)
  and the selected entry's colour was `(255,200,40)` (`ENTRY_SELECTED`).
* Confirm (`A`) on a non-`Training` entry was a correctly inert no-op: the
  background stayed `(16,16,24)`, no state change.
* `D_UP` from entry 0 wrapped to entry 2 (`(cursor + N - 1) % N`), and a
  second `D_DOWN` returned to entry 0 — both confirmed by exact per-entry
  colour sampling (`ENTRY_SELECTED`/`ENTRY_ENABLED`/`ENTRY_DISABLED` each
  read back at their expected screen position).

The final `Menu` → `Training` confirm press (same `A`/Cross key, same
`newly_pressed` edge-detection already proven correct for the Intro → Menu
transition above) was attempted repeatedly against a separate, freshly
launched instance but could not be reliably delivered: `Xlib`'s
`get_input_focus()` confirmed the PPSSPP window *did* hold X input focus
immediately after each synthetic key send, yet the application state did
not change across eight repeated attempts. This reproduced on a fresh
instance from a cold launch, ruling out stale window/focus state carried
over from the successful round above. The most consistent explanation is
XTEST key injection racing this desktop's Wayland/XWayland compositor-level
focus arbitration (a `xwaylandvideobridge` bridge window was present
throughout) rather than a code defect — the same edge-detection call
(`newly_pressed(prev, curr).contains(N64Buttons::A)`) is exercised
identically by the already-confirmed Intro → Menu transition, and the
`Training` branch is code-reviewed to use the identical pattern, gated only
by `cursor == TRAINING_ENTRY`, which was independently confirmed true by
the exact `ENTRY_SELECTED` pixel read immediately before the failed
attempts. **Not independently pixel-confirmed this session** — flagged as
the one open item for the next hands-on verification pass, not treated as
passing on inference.

*Physical PSP.* Not run this session — no on-device evidence for `psp-game`
yet. Tracked as required before this increment can be called physically
verified, per `AGENTS.md`'s "PPSSPP is not physical PSP proof."

**Confidence: high** for criterion 1 (independent boot, `psp/` unmodified)
and the Intro/Menu navigation shape of criteria 2-3 — each backed by exact
pixel evidence, not visual impression. **Open:** the Menu → Training
transition (code-reviewed, not pixel-confirmed), and all of criteria 4-7
(real scene loading, hitbox/damage/knockback, decomp verification),
which remain future F1 work.
