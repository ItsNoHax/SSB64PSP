# RE-499 — Cached vertex blocks written back per draw: the skin read-back is the gain, and equal-model link orders spread 2–3 FPS on hardware

Status: COMPLETE (PSP-2000, 6.61 ARK, PSPLink v3.2.1, `profile` / `profile_hw` builds of `vs4@2400` and `opening@3000`, means over profile reports 3..18)
Topics: performance, hardware, cache, link-order, methodology
Relevant files: `psp-runtime/src/gu.rs`, `psp-runtime/src/meshdraw.rs`, `psp-game/link-order.txt`, `tools/icache/`

## Question

Mesh vertex blocks are written through the uncached alias, and the skin
buffer is read back by `expand_corners` (uncached loads). Do cached
blocks, written back before each draw, cut CPU time?

## Findings

- Mechanism: vertex blocks come from the display list one line larger
  (`sceGuGetMemory(round64(bytes)+64)`); the code writes through the cached
  alias of the block's first whole 64-byte line, so no command word shares
  a line (RE-360), then writes the block back (`cache 0x1b`; `0x1a`, keep,
  for the skin buffer) plus `sync` before the draw. The GE runs mid-frame:
  rust-psp's direct list moves the stall address on every draw and every
  `sceGuGetMemory`, so an end-of-frame writeback would show stale vertices
  on hardware only.
- Counters (`profile_hw`, per frame): uncached loads 2,531 -> 1,154
  (dfighters 1,810 -> 440); uncached stores 18,072 -> 16,313; D misses
  16,139 -> 16,532; D writebacks 4,287 -> 4,454. The gain is the skin
  buffer read back cached, not cheaper stores (uncached stores are absorbed
  by the write buffer; RE-485's cached display list lost 1.5 FPS, this
  differs by caching vertices only with no per-command checks).
- Same-binary runtime toggle (a temporary probe file beside the PRX chose
  `sceGuGetMemory` without writeback), 3 interleaved rounds, `vs4@2400`:
  54.17 -> 55.06 FPS (+0.89), frame -300 us, CPU -163 us, dfighters
  -157 us, skin +16 us (writeback). Rounds agree within 0.1 FPS; layout is
  identical, so this is the change's own effect.
- Opening (`opening@3000`, same toggle): 59.14 vs 59.17 FPS. Neutral; the
  scene is vsync-bound (vblank wait ~4.6 ms).
- Layout variance: one binary reproduces within 0.25 FPS across sessions,
  but the same code under link orders searched to equal model scores
  spreads 2.0 FPS (HEAD, 6 orders, 55.01-57.01) and 3.3 FPS (candidate,
  5 orders, 53.12-56.44). The I-cache model (RE-494, RE-496) does not rank
  hardware at this scale: HEAD's shipped order was the model's worst
  (317,486 held-out misses) and measures among the best (56.68); the
  model-best candidate order measured 54.30. RE-494's calibration held only
  for large (21%) model differences.
- Consequence for RE-485/494/496/498: a build-vs-build A/B with one
  searched order per arm cannot resolve effects below ~1.5 FPS. RE-498's
  +1.14 FPS is inside that spread; only its -128 us billboard span is
  attributable. Use a same-binary toggle or several orders per arm.
- No measured shipped-build gain over HEAD: no candidate order beat HEAD's
  shipped order on hardware (best 56.44 vs 56.68, `profile` builds; cross
  layout mean -1.24 +- 0.66 FPS, not significant). Only the same-binary
  +0.89 FPS and the counter changes are claimed. The shipped order is
  seed s3 (model tie with s1, hardware tiebreak); `cargo psp --release` is
  byte-identical to the `relink.py` relink of it. No hardware screenshot of
  the final release build was taken; the same code ran as `profile` builds
  with correct pictures.

Caveat (RE-530): the opening figures here predate RE-514 (per-vertex lit expand) and RE-519 (guard clip) and are not today's baseline; see RE-530.
