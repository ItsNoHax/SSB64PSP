# RE-535 — Bind-block extensions on a PSP-2000: descriptor prelookup and a texture-mapping cache pay, a CallList sub-list does not; stall batching is bit-identical on hardware

Status: COMPLETE (PSP-2000, 6.61 ARK, PSPLink v3.2.1, `capture_scene_file,frame_timer`, audio on, 120-frame reports; base cda8ec5)
Topics: performance, hardware, rendering, link-order, memory
Relevant files: `psp-runtime/src/meshdraw.rs`, `psp-game/src/main.rs`, `psp-game/src/opening_screen.rs`, `psp-game/link-order.txt`

## Question

After RE-534, which bind-block extensions pay on a PSP-2000, can stall batching be compared bit for bit on hardware, and does the VS build fit the XMB memory budget?

## Findings

1. Prelookup. `apply_material` checks the bind cache before `pack.texture()` decodes the `TextureDesc`: -0.27 ms busy on `vs4@2400` (same-PRX toggle).
2. Mapping cache. `emit_texture_mapping`'s authored-UV scale and offset are cached per (texture, tile phase, affine window), 256 direct-mapped slots, valid per pack base (+11 KB `.bss`): -0.15 ms. Both together: -0.44 ms. Keys are integers; the cached floats are only copied into `sceGuTexScale`/`TexOffset`, never compared or computed on (D-050, RE-531). The environment (texgen) path is unchanged.
3. CallList sub-list (BASE/CALL/RET into an uncached arena instead of copying recorded words): -0.01 ms; removed. rust-psp's `sceGuCallList` issues a stall-update syscall.
4. Link order. Code growth broke the order again (candidate on the old order 17.67 ms against HEAD 16.53). Re-search (RE-494 procedure): 24 seeds x 30,000 iterations; held-out model misses 414,325 -> 325,025; seed 3 won on hardware (vs4 16.237 ms, two runs; s10 16.303, s13 16.315, s16 16.395, s14 16.447, s1 16.462, s6 16.555, s8 16.560).
5. `room_time()` read the system clock in `capture_scene_file` builds, so the opening was not reproducible under PSPLink. It is now fixed under `regression_capture` too; release and golden output are unchanged. With the fix `opening@4700` gives 39 reports: Room 2-11, Run 20-21, Yoster 28-29, Clash 34-35 (these windows replace RE-532's numbering; Room is not comparable with RE-534's 12.72).

6. Hardware framebuffer comparison. The `frame_hash` feature hashes (FNV-1a) all 480x272 RGBA pixels of the shown buffer after `end_frame`'s `sceGuSync`, one line per sim tick, and appends them to `fhash.log` beside the PRX (PSPLink stdout is not captured). Hashing costs about 28 ms a frame, which does not matter: the sim advances one tick per loop. Runs repeat bit for bit on `vs4@2400` (2402 frames) and, after the `room_time` fix, on `opening@4700` (4560 frames). Sensitivity: reintroducing RE-534's `draw_rect` stack race changes 72 frames at stall/1 and stall/16.
7. Stall batching (16 draws per stall update, rust-psp experiment branch `stall-interval-experiment`, a1c3d86) is bit-identical to stall/1 on hardware, on vs4 and the opening. It saves -0.39 ms busy (stall/32: -0.42; 17.473 -> 17.081 on the same PRX). It would change 7 of 24 PPSSPP VS goldens (`tools/golden.sh verify --filter '^f1-vs-'` gives 17 of 24: countdown 480 px, sudden-death 76, yoshi 480, ball 480, rays 512, four-low-detail 16, knock-ko 20), because softgpu output depends on bin ranges (RE-534). Not adopted; no rust-psp change was made.
8. Prelookup and mapping cache against HEAD are bit-identical on hardware at stall/1 and stall/16 (vs4 and opening) and on PPSSPP (2402-frame RGBA, 0 differing frames); 218 of 218 goldens match. The final link order was not hashed on hardware (a `frame_hash` build has its own layout); its code is the hashed code.
9. XMB budget. `memory_ballast` under PSPLink (build `capture_scene_file,profile,memory_ballast,boot_log`, stricter than release): free at `psp_main` 51,209,472 (RE-475's build: 52,086,016); an XMB launch gets 4 MiB less (RE-475), so the ballast leaves 47,015,168 and held 4,456,448. `vs4@2400`: 31.08 MB free after load, lowest 30.45 MB. VS results (all fighters, 151 files, 93 prefetched): lowest 29.16 MB. No exception. RE-475's figure was 30.9 MB (PPSSPP). The batch grows `.bss` +11,280 bytes, text +2.4 KB, rodata +1 KB. A real XMB LoadExec launch was not used (a failure would leave the PSP outside PSPLink).

## Conclusion

Prelookup and the mapping cache are worth -0.44 ms before re-ordering and -0.29 ms net on `vs4@2400` (58.6 FPS); the CallList sub-list is not. Stall batching is hardware-bit-identical and worth -0.39 ms, held only for the PPSSPP golden decision and a production route. The VS build fits the XMB memory budget with 29 MB to spare.
