# RE-274 — RE-272's forehead artifact traces to one self-contained, wide-UV draw call; root cause still open

Status: OPEN
Topics: texture, fighter, geometry, hardware, visual-regression
Relevant files: crates/ssb-rom/src/mesh.rs, crates/ssb-rom/src/psp_texture.rs, tools/romtool/src/main.rs

**Question.** RE-272 found Mario's face renders a repeating eye/eyebrow
pattern and red patches, on both PPSSPP and physical PSP hardware, though
the raw ROM texture is clean. Candidates listed there: UV/tile addressing,
texture scale/wrap mode, or a mip/minification interaction. Which is it?

**Measurement.** Traced the exact primitive with temporary instrumentation
(reverted after use, not committed) in `romtool`'s `file_meshes`/`texdump`
paths, against `rom/Super Smash Bros. (USA).z64`, Mario's file 296.

1. The texture (`file 296 +0x6F98`, `Ci4 32x32`) is bound by exactly two
   `TextureRef`s archive-wide, both with `mask_s=mask_t=5` (32-texel
   period), `mirror_s=true`, `mirror_t=false`, `clamp_s=clamp_t=true`,
   `drawn_width=64`, `drawn_height=32` — the documented "mirror once, then
   clamp" shape (`mesh::TextureRef::clamp_s`'s own doc comment, RE-102).
2. The primitive binding it in graph `0x2200` has 24 triangles whose vertex
   position bounding box is `x -78..77 y -18..98 z -48..88` — essentially
   the whole head, not a small decal region — while its vertex UV bounding
   box is `u -993..2545 v -217..1005` (S10.5), i.e. **110.6 x 38.2 texels**
   against a 64x32 packed image (3.46x/1.19x the tile).
3. Raw command trace (node 8, dl `0x1990`) shows this is **one self-contained
   draw**: `Vtx count=19 dest=0` immediately followed by 12 `Tri2` (24
   triangles), all indexing only those same 19 freshly-loaded vertices — not
   vertices borrowed from a sibling node via `convert_sequence`'s
   cross-joint vertex-cache inheritance (`mesh.rs`'s own documented
   mechanism, which raised cross-node leakage as a candidate this measurement
   rules out for this specific primitive). The texture itself is bound by a
   segment-`0x0E` `Call` (`MObjSub 0x208`, chain 3/3, cleanly resolved —
   `romtool mobj --file 296` reports 0 mismatched chains archive-wide for
   this file), not an inherited stale binding.
4. `mirror_extend`'s baked output (`64x32`, verified by direct PPM dump) is
   a **correct, symmetric two-eye image**: the raw pre-mirror source
   (`f296_o6F98_Ci4_32x32.ppm`) already contains one eye/eyebrow *and* a
   reddish sideburn patch at its left edge — RE-272's "no red patches" read
   on the raw dump was incomplete, not wrong about corruption; the sideburn
   is real, authored content, and mirroring correctly reproduces it
   symmetrically on both sides. **Texture decode and mirror-baking are not
   the bug.**

**Not yet root-caused.** Two live hypotheses, not yet distinguished:

* **(a) Faithful reproduction of a real ROM quirk.** All 19 vertices' UVs
  come from this node's own `G_VTX` (scaled by the immediately-preceding
  `G_TEXTURE` command, `scale_s=65535 scale_t=33554`), authored in the ROM
  itself — nothing here is synthesized or mis-attributed by the converter.
  If real N64 hardware also samples this same wide UV range against this
  same small mirror+clamp tile, the RDP's own 3-point filtering plus a CRT's
  blur could make the artifact invisible there while our PSP path (and
  PPSSPP) render it sharp — the same shape of gap RE-263/RE-264 already
  named and fixed for Kirby's and Ness's "false eye spikes"
  (`docs/rendering/textures.md`'s texture-filtering section,
  `TEXTURE_FILTER_CORRECTIONS`). Mario is not currently in that table.
* **(b) A real addressing/scale bug specific to this wide-overscan case.**
  RE-102's mirror+clamp fix and R2.0's census were validated against the
  archive's mirror+clamp population in aggregate; this instance's overscan
  ratio (3.46x/1.19x of the *doubled* tile) is more extreme than typical and
  has not been individually checked against the `n64_addressing` reference
  model's per-sample output.

**Scope.** Confirms RE-272's bug is real and narrows it to one specific,
reproducible draw call (file 296, node 8, dl `0x1990`, texture at `0x6F98`)
rather than a general addressing-model failure — the archive-wide addressing
census (RE-220/RE-221/RE-222) already reports 0/810 divergence for ordinary
mirror+clamp axes, so whatever is wrong here is either filtering-class (RE-263
precedent) or specific to this overscan magnitude, not a reintroduction of a
previously-fixed general gap.

**Conclusion.** Not fixed. Next step: get an accurate reference render (real
N64 hardware or a cycle-accurate N64 emulator, e.g. `angrylion-rdp-plus`, which
this project already uses as its host-side addressing/filtering reference
model) of Mario's face at this camera distance to determine whether hypothesis
(a) or (b) applies. If (a), this becomes a `TEXTURE_FILTER_CORRECTIONS`-style
named, per-texture correction, per D-037/AGENTS.md's "no unsupported rendering
heuristics" rule. If (b), the next step is running this exact axis's
parameters (`mask=5, mirror=true, clamp=true, drawn=64`, sampled across
`-31..+80` texels) through `n64_addressing`'s reference model directly and
diffing against the PSP lowering's actual sampled output at several concrete
UV values, the way RE-220 did for the general case.

**Confidence: high** on the measurements (raw command trace, bbox, UV span,
mirror-bake correctness all directly observed); root cause remains open.
