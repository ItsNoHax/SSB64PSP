# RE-493 — Only outlining the per-mesh path's cold blocks wins; hot-code outlining loses despite fewer I-misses

Status: COMPLETE (PSP-2000, 6.61 ARK, PSPLink v3.2.1, `profile_hw,capture_scene_file,no_audio` builds of `vs4@2400` with pack v109 beside the PRX on `host0:`, reports 1–18, three interleaved rounds; 198 of 198 goldens unchanged)
Topics: performance, hardware, psp-ge, icache
Relevant files: `psp-runtime/src/meshdraw.rs`

## Question

RE-487/488 left the per-mesh path (`draw_object_posed_nodes`,
`draw_mesh_vertices`, `apply_material`, `apply_texture_mapping`) as the
largest remaining source of draw I-cache misses. RE-487/488's own numbers
came from the PPSSPP cache model's *function attribution*; this batch asked
whether restructuring how a primitive's GE state is resolved — moving the
"compute the comparison key" code out of the loop body into small
`#[inline(never)]` leaf functions, without changing when any `sceGu*` call
happens — could shrink a pass's `.text` footprint further.

## Findings

### LTO already undid part of RE-487/488's outlining

`psp-nm --size-sort -S` on a from-source rebuild (debug symbols kept,
same LTO/`codegen-units=1`/`opt-level=3` as shipped) showed
`apply_material` and `compose_model_matrix` no longer exist as separate
symbols: LLVM had re-inlined both into their single call site
(`draw_mesh_vertices` and `draw_object_posed_nodes` respectively), since
single-call-site inlining is LLVM's default and neither was marked
`#[inline(never)]` — only their *rare branches* were. `draw_mesh_vertices`
measured 10,592 bytes and `draw_object_posed_nodes` 7,204 bytes this way,
both already over the 16 KB budget combined, consistent with RE-482's
model (~29 KB per pass after RE-488) but not previously confirmed against
real linked symbols.

### Outlining code that runs every primitive loses, even though the function shrinks

Six variants were built and run on hardware (interleaved A/B rounds,
`vs4@2400`, reports 1–18 averaged; A = HEAD before this batch,
`59f8186b7cbde376`, reproduces RE-492's shipped numbers within run-to-run
noise, 48.00–48.04 FPS):

| Build | What changed | FPS | CPU frame µs | Draw µs | Draw I-miss |
|---|---|---:|---:|---:|---:|
| A (HEAD) | — | 48.00–48.04 | 18,596–18,609 | 10,669–10,680 | 17,966 |
| B1 | `apply_material` + LOD-blend pass forced `#[inline(never)]` | 46.26/46.23 | 19,140/19,142 | 11,231/11,232 | 19,220 |
| B2 | B1 + flags-block/texture-mapping-emit also outlined | 47.06/47.11 | 18,931/18,906 | 11,011/10,990 | 18,381 |
| B2o | B2 + outlined helpers placed next to callers in link order | 47.64–47.94 | 18,617–18,641 | 10,707–10,728 | 17,690 |
| C | only the cold LOD-blend pass + fade blend outlined | 48.13–48.18 | 18,521–18,532 | 10,597–10,608 | 17,784 |
| **D2 (shipped)** | C + cold texture-part lookup + cold animated-UV affine | **48.27/48.28** | **18,504/18,511** | **10,598/10,605** | 17,894 |

Outlining `apply_material` itself (B1, the handoff's step 1) cost 1.8 FPS
and 1,254 more draw I-misses, despite shrinking `draw_mesh_vertices` by
6 KB — the opposite of what the byte count predicted. Reordering the new
cold symbols next to their hot callers in `link-order.txt` (B2o, not
shipped: `link-order.txt` is unchanged) recovered most of the loss and
even posted 280 *fewer* I-misses than A, yet still drew about 35 µs
slower (D-misses +40–100, memory stall +60 µs). **Fewer I-cache misses did
not mean less time** — the same disconnect RE-487 found between the
model's miss count and the hardware's cycles.

Outlining only the blocks that are rarely *taken* (the LOD-blend second
pass and the fading-fighter blend, both already conditionally executed but
previously laid out inline) won cleanly: C is −78 µs draw / −80 µs frame
against A with no link-order change.

Layout is sensitive at the 20–100 µs scale: adding one more cold outline
(D1 = C + a texture-part lookup) made `draw_mesh_vertices` 1.8 KB smaller
but cost +630 I-misses and +85 µs draw; adding a further one (D2 = D1 +
an animated-UV-window helper) recovered to C's draw time. The shipped gain
should be read as roughly −75 µs draw / −95 µs frame against A, with the
C→D2 step (~−18 µs frame) inside the noise this kind of layout change
produces.

### Shipped change

Only cold or rarely-taken code was pulled out of `apply_material` and
`draw_mesh_vertices` as new `#[cold] #[inline(never)]` (or, for the
animated-UV-window arm, plain `#[inline(never)]`) functions:
`animated_uv_affine` (RE-326 window), `draw_lod_blend_pass` (already a
function; LTO had inlined it, so this re-pins it), `texture_part_override`
(RE-426 sprite lookup, was a closure), and `apply_fade_blend` (RE-464).
`apply_material`'s flags-gated block and the texture-mapping GE-write half
were extracted into named functions for readability but kept
`#[inline(always)]`, since taking them out of line measured a loss (B2/C2o).
`apply_material` itself is left unmarked; LTO still inlines it, and that
measured better than forcing it out. `link-order.txt` is unchanged.
Pure code motion: no float path or branch condition changed, so no golden
hash moved.

## Consequences

- Confirms RE-487/488's "preserve pixel hashes; measure outlining on
  hardware, not the model" discipline at a third scale: once per-pass code
  is already near the model's predicted floor, outlining further loses
  unless the block is genuinely cold. Resolution code that runs every
  primitive (texture/palette lookup, blend-target resolution — handoff
  steps 3/4) was not attempted, since finding 1 predicts it would lose the
  same way.
- A precomputed flags-derived render-state table (handoff step 7) remains
  unexplored; it would change *what* is computed, not just where the bytes
  live, so it needs its own measurement rather than following from this
  record.
- `link-order.txt` keeps its RE-482 order; two more candidate reorderings
  (B2o, C2o) were A/B'd and neither was adopted, consistent with
  RE-487/488's finding that regenerating it from new symbols does not
  transfer to hardware without its own A/B.
