# RE-284 — 30-minute physical-hardware sustained run, extending past the prior 10-minute sample

Status: COMPLETE
Topics: hardware, visual-regression
Relevant files: STATUS.md, plans/rendering/R2.md

**Question.** RE-271/RE-273 established a 10-continuous-minute sustained
physical run with zero exceptions on two PSP units (Slim, PSP-3000), but
`STATUS.md`/`plans/rendering/R2.md` both explicitly flagged "runs longer
than 10 minutes" as untested coverage. Does the plain feature-free EBOOT
survive a longer sustained run without a hardware-only failure (leak,
corruption, GE race, USB drop) that a short sample could miss?

**Method.** Same unit and procedure as every other RE-283/RE-27x hardware
check (PSP Slim, firmware 6.61, ARK/Infinity, PSPLink v3.2.1). Built the
plain feature-free EBOOT (`cargo psp --release`, no extra features) —
SHA-256 `9b9bfb8f94730a47ea04e50cb2a75a8d91536bd9b13f74682256a3ebe902ca8c`,
matching every prior fix session since RE-281 exactly (confirming this
check exercises the same binary already fixed, not a stale build). Pack
SHA-256 `256d7661bb1dc7266ea8928bc8f341cbb121f83c330a4d3821466192ea42c17d`,
also unchanged. Loaded via PSPLink's `host0:` (`usbhostfs_pc` serving the
repository root, `ldstart host0:/psp/target/mipsel-sony-psp/release/
ssb64-psp.prx`) — confirmed clean baseline first (`exlist` empty, no
`ssb64_psp` module loaded) before starting. Captured a native `scrshot` at
t=0, then let the game run 30 continuous real-time minutes (three times
the prior 10-minute sample), checking `exlist`/`thlist`/`usbstat` at the 5,
10, 15, 20, 25 and 30-minute marks, then a final native `scrshot`.

**Note for future sessions:** `pspsh` alone returned "connection refused"
even with the PSP showing `054c:01c9` on USB and PSPLink visibly launched
on-device — `usbhostfs_pc -v "$PWD"` has to be running first (it bridges
the USB link `pspsh` connects to over TCP); the skill doc's connectivity
check doesn't call this out explicitly.

**Result.** Zero exceptions at every one of the six checkpoints; `exlist`
empty throughout, `main_thread` alive throughout, `usbstat` reported
`Connection: activated` / `USB Connection: established` unchanged at every
check. The t=0 and t=30 native captures are near-identical: 43 differing
pixels out of 130,560, all inside an 8x13 px bounding box
`(237,166)-(244,178)` directly over Mario's own model — consistent with
ordinary idle-pose motion over a 30-minute window, not VRAM corruption or a
leak artifact (no drift, discoloration, or growing garbage elsewhere in the
frame). Module killed and PSPLink reset cleanly afterward; no stale
module-manager state.

**Conclusion.** The prior 10-minute sustained-run finding (RE-271/RE-273)
extends cleanly to 30 minutes on this unit — no new hardware-only failure
mode appears in the additional 20 minutes. This narrows, but does not
close, `STATUS.md`'s "long-duration" coverage gap: 30 minutes is still far
short of a real play session's duration, and this is one unit (PSP Slim)
rather than the two RE-273 used for the 10-minute sample. Full stage/
effect golden coverage (41 stages, most without a dedicated capture scene)
and PSP-1000 confirmation remain open and are unaffected by this result.

**Confidence: high** for "no failure appears in the tested 30-minute
window on this unit", matching the same zero-exceptions bar as every prior
RE-27x/RE-283 hardware session. Not a claim about durations beyond 30
minutes or about the untested PSP-1000/second-unit combination.
