# RE-279 — RE-274's real primitive is correctly routed through the signed-UV float path

Status: RESOLVED
Topics: texture, fighter, hardware, visual-regression
Relevant files: crates/ssb-rom/src/pack.rs

**Question.** RE-278 ruled out the addressing formula and fixed-coordinate GE
sampling for RE-272/274's Mario-face bug. One more candidate sat upstream of
both: `meshdraw.rs`'s own doc comment warns that `GU_TEXTURE_16BIT` decodes as
*unsigned*, so a primitive with a negative authored UV on a clamped axis
(RE-274 measured `u -993..2545`, i.e. touching negative) must be routed
through `flags::SIGNED_CLAMP_UV`'s transient float-UV path
(`meshdraw::draw_mesh`'s `signed_clamp_uv` branch) instead of the plain
16-bit path, or the GE reads a huge wrapped-around unsigned value and clamps
to the wrong edge. Is RE-274's actual primitive (file 296, node 8) correctly
flagged?

**Measurement.** Added a temporary `eprintln!` to `pack.rs`'s
`add_mesh` flag-computation loop (reverted immediately after use, not
committed), gated on `source_file == 296 && t.mask_s == 5 && t.clamp_s &&
t.clamp_t` -- RE-274's exact texture-ref shape -- printing each matching
primitive's triangle count, UV bounding box, and `needs_float_uv`. Ran
`cargo run -p romtool --release -- pack "rom/Super Smash Bros. (USA).z64"
--file 296 --out /tmp/f296.pak` and grepped the output.

The 24-triangle primitive with `umin=-993 umax=2545` (RE-274's exact
primitive) printed `needs_float_uv=true` on every one of its five repeated
appearances across the file's several skeleton-graph instances (fighters
share `add_mesh` calls across pose variants). Reverted the probe afterward;
`git diff --stat` confirmed a clean tree.

**Conclusion.** `SIGNED_CLAMP_UV` is set correctly for this exact primitive.
The signed/unsigned UV reinterpretation bug that flag exists to prevent is
not RE-272's cause -- production already routes this primitive through
`meshdraw::draw_mesh`'s `FloatUvVertex` path, preserving the signed value
exactly. This closes one more candidate before RE-280's real-triangle rig
(built immediately after this check) found the actual cause.

**Confidence: high.** Direct measurement against the real pack-building code
path, not a re-implementation; reproduced identically across all five of
this primitive's repeated instances in the file.
