# RE-548 — Function-local arrays live in the overlay's `.data`; the build map is shifted

Status: COMPLETE (decomp source and US ROM SHA-1 e2929e10 through `crates/ssb-tablegen`'s `d_arrays`; host tests; full golden matrix; no N64 runtime capture; no hardware run)
Topics: tablegen, d048, ido, locals, menus, 1p
Relevant files: `tools/local_arrays.py`, `crates/ssb-tablegen/src/d_arrays.rs`, `crates/ssb-tablegen/src/d_arrays/local/`, `crates/ssb-rom/src/sprite.rs`, `crates/ssb-rom/src/campaign.rs`, `tools/docs/rom_tables_baseline.tsv`

## Question

[D-048](../../decisions/D-048.md) was amended on 2026-10-19: arrays declared
inside decompiled functions are ROM tables. Where does the original keep
them, how are they located without a symbol, and do the committed copies
equal the ROM?

## Evidence

- **Placement.** IDO puts an initialised function-local array into the
  file's `.data` as an anonymous blob, in source order, word-aligned. It is
  not in `.rodata`, which holds only string literals, the float pool and
  switch jump tables. `symbols_us.txt` has no per-array symbol: the blobs
  hide inside `d<Mod>Unused0x<ADDR>` symbols (`dMNVSResultsUnused0x80138F90`
  spans mnvsresults' locals, about 0x728 bytes). A `char *names[]` local is a
  table of pointers into `.rodata` literals (`Elem::CStr`).
- **Build map offset quirk.** `refs/ssb-decomp-re/build/smashbrothers.us.map`
  does not agree with the yaml and `symbols_us.txt` (ovl31 text at
  0x80131C20 / ROM 0x150DB0 there; 0x80131B00 / 0x150CA0 in the yaml, which
  matches `ssb-tablegen`'s `OVL31`). Addresses come from the yaml, the symbol
  list and `source.rs`, never the map.
- **Locator.** `tools/local_arrays.py` preprocesses a decomp file with the
  decomp's flags, lays out every run of initialised locals and file-scope
  arrays in IDO order, fits each run as one wildcard pattern (`ll*` words are
  wildcards) inside the window between known global symbols, cross-checks the
  computed global addresses against `symbols_us.txt` and checks that
  `char *` elements point at their literal. Every mn, sc and mv file tried fit
  (`ok`, `ok (split run)` or `placed by its neighbours`).
- **Generator.** `DArray::local` and `Elem::CStr` in `d_arrays`; one list per
  decomp file in `d_arrays/local/`. Enum-valued lists (fighter kinds, status
  ids) are generated and mapped through checked const conversions
  (`FighterKind::playable_ordinal`, `DemoStatus::from_id`).
- **Moved.** The results screen, results scene and emblem, character
  select, VS record, opening room spotlights and figures, the VS, 1P and
  Training player selects, 1P records and bonus, staff roll, the sprite
  manifests (VS results, game modes, digits, player tags, difficulty,
  common menu, portraits, emblems, announcer letters), the 1P intro
  (stage numbers, figures, positions, opponents, names) and the stage-clear
  digits, colours and difficulty text. `psp-game`'s `campaign_screen.rs` lost
  its own copies. Baseline rows fell from 62 to 36.
- **Result.** Every committed literal, f32 compared by bits, equalled the
  ROM: zero mismatches. A temporary gate compared each before deletion.
- **Stub mode.** With zeroed tables the opening room's `pick_figures` looped
  forever; the stub tables now give the 8 kinds in order.
- **Baseline, 36 rows.** Test fixtures 11; decomp code sites and
  function-body constants 7; non-overlay data 1 (explain ARROWS, archive file
  0xC6); generated copy 1; layout 3 (audio SBK, backup default, GAME_STATUS);
  `ll*` code immediates 13.
- **Not covered.** Manifests with no cited `d*` doc (`PLAYERS_COMMON`,
  `MN_MAPS`, `PLAYERS_1P_MODE`, `ITEM_ARROW`, `BATTLE_PAUSE`, campaign
  label consts); no golden scene exists for the 1P intro or stage clear.
