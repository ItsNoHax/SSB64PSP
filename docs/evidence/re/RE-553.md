# RE-553 — Loop wrap ends, undrawn exit updates, demo pose clock, two-lead clips

Status: IMPLEMENTED (decomp source, N64 RDRAM trace of the attract opening, N64 warp-boot Link entry capture, goldens with the fixes reverted; no hardware run)
Topics: animation, fighter, opening, scene, taskman, pack, n64-trace
Relevant files: `crates/ssb-game/src/status.rs`, `crates/ssb-game/src/opening/room.rs`, `crates/ssb-rom/src/skeleton.rs`, `tools/romtool/src/main.rs`, `psp-game/src/opening_screen.rs`, `psp-runtime/src/gu.rs`

## Question

Which decomp behaviours behind the playtest fixes (Fox ledge freeze, Link
entry, opening cliff exit, opening room hand) are easy to miss?

## Evidence

- **Looping clip ends at the wrap.** `ftAnimEndCheckSetStatus`: a looping clip
  with no known length ends when `anim_frame <= 0` after the clock has passed
  `anim_frame_begin`. The port's `animation_ended` lacked it, so Fox
  CliffCatch/Ottotto never ended. Newly faithful ends: Fox
  Ottotto to OttottoWait after 12 frames, Kirby DamageE1/E2, Ness
  SpecialAirHiBound. No unfaithful early end among all looping clips.
- **Exit update is not drawn, every scene.** `syTaskmanRunTask`
  (`taskman.c:1031-1038`, `:994`) calls `syTaskmanCheckBreakLoop` after
  `task_update` and breaks before `task_draw`; `syTaskmanSetLoadScene`
  (`taskman.c:892`) is called from the update of every scene kind. The update
  that requests a load is never drawn; the previous picture stays through the
  load. Opening: tic 160 (`mvopeningcliff.c:453`) never drawn; the port drew it
  (wrapped frame 0, profile). Port: `hold_picture` in the psp-game loop
  (`SceneKey` change or a waiting scene) plus `Gpu::repeat_frame`, for every
  scene request. Golden `f1-opening-cliff-exit` (361808 px at 2x without the
  fix); no other golden moved.
- **Battle-entry rule.** `syTaskmanStartTask` resets the update count
  (`taskman.c:1208`), so the new scene's update 1 IS drawn. A battle entered by
  a request runs exit, start and update 1 in one port tick (`training_frame`
  after the match arm): that tick is drawn, not held (`Session.updated_scene`).
  Holding it dropped update 1's draw-side state (`ftDisplayMainProcDisplay`
  writes `is_magnify_show`/`magnify_pos`, read by `ifCommonPlayerArrowsFuncRun`)
  and moved `f1-training-piranha-plant` by 308 px. Documented deviation: the
  port merges the N64's undrawn exit frame and update 1, so a battle entry
  repeats one picture fewer than the N64; splitting would shift every battle
  golden by one tick.
- **Hold log.** Headless captures print `scene hold tick=N`; `tools/golden.sh`
  keeps it as `stack/<golden>-<pass>.holds`.
- **Demo pose at tic k is anim frame k.** RDRAM trace of the attract opening
  (clean ROM): `sMVOpeningCliffTotalTimeTics` (0x801327CC) = k matches Link
  joint `anim_frame` (DObj+0x7C) = k for k = 1..159. The pre-play in
  `FighterState::set_status` is not ahead; dropping it would be one frame late.
- **Two-lead clips.** `anim_desc` bits 30+31 (`0xC0000000`): TransN and XRotN
  lead the stream, so model joints bind from entry 2. Affects Link Appear
  (607/608) and Kirby/Purin CliffEscapeQuick1/2 (483/484, now bind all 22
  nodes). N64 Link entry poses match the port (count 45 and 60). Pack v124.
- **Room logo camera.** `mvOpeningRoomMakeLogoCamera` passes `argD` FALSE;
  `gcMakeCameraGObj` sets `COBJ_FLAG_ZBUFFER` only for `argD`. The port's
  z-buffered camera drew Master Hand's hand over the box. Golden
  `f1-opening-room-hand` (1376 px at 2x without the fix).
