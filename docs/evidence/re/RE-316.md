# RE-316 — One-build golden captures with exit-on-capture

Status: COMPLETE (PPSSPP software: all 67 scenes byte-identical to the per-feature pipeline at -j 1 and -j 24; physical PSP not run)
Topics: visual-regression, tooling

Relevant files: `crates/ssb-capture/`, `psp-asset-viewer/src/capture.rs`,
`psp-game/src/capture.rs`, `psp-asset-viewer/src/main.rs`,
`psp-game/src/main.rs`, `psp-runtime/src/assets.rs`,
`tools/run-ppsspp-headless.sh`, `tools/golden.sh`,
`tools/golden-reference.sh`, `tests/golden/scenes.tsv`

**Question.** A full golden run needed one `cargo psp` build per scene (every
golden was a Cargo feature, and 38 stage goldens were one feature built with
38 values of `SSB64_STAGE_INDEX`) and a fixed 8 s PPSSPPHeadless run each,
because the program never exits. Can one build per crate capture every scene,
exit as soon as the screenshot is taken, and run in parallel, without
changing a single captured pixel?

## Change

- `crates/ssb-capture` defines the scene specs (`default`, `scene2`–`scene10`,
  `stage N`, `fighter NAME`, `link_costume_1`, `mario_entry`,
  `bonus_platform`, `depth_mask`; `psp-game`: `training`, `fireball`,
  `superjump`, `fox`, `shadows`). It is `no_std` and host-tested.
- Both binaries pick their scene once at startup. `golden_capture` (and
  `capture_scene_file`, its hardware variant without the screenshot request)
  reads `capture_scene.txt` from the pack's search paths. Otherwise the old
  per-scene features name a compile-time default; with neither there is no
  capture scene. Every scene-related `cfg!` in the viewer became a runtime
  accessor. Audit and diagnostic features without a golden stay build-time.
- The Mario entry pipe scene keeps its old behaviour of running inside the
  effect browser (`regression_capture_mario_entry` enabled
  `effect_audit_capture`), HUD line included, through
  `SceneExt::effect_audit`. The bonus platform and entry pipe keep drifting
  until the freeze, as before; only the scenes the old list named hold the
  spin angle.
- A `golden_capture` build whose scene came from the file renders two frames
  after `emit_headless_screenshot()` (`CAPTURE_EXIT_FRAMES`), then calls
  `sceKernelExitGame()`. Two frames was the first value tried; no capture
  came out empty or stale.
- The runner gained `--scene` and `--job`; `tools/golden.sh` drives it.

## PPSSPPHeadless behaviour

Read from `headless/Headless.cpp` in the local build:

- A timeout prints `TIMEOUT` and the process still exits 0 outside
  `--compare` mode. The runner therefore treats that log line, not the exit
  status, as the failure signal for `--scene` runs.
- The memstick is `$HOME/.ppsspp`. Headless never saves `ppsspp.ini`
  (`~/.ppsspp/PSP/SYSTEM` still does not exist after every run for this
  record), so per-job game directories and per-job `no-status-overlay.ini`
  copies are the only isolation needed. No per-job `HOME`.

Per-capture wall time: 0.4–1.2 s (median 0.7 s) at -j 1; 0.8–2.4 s (median
1.5 s) at -j 24.

## Conclusion

Runtime scene selection, exit-on-capture and parallel per-job runs reproduce
the per-feature pipeline's output byte for byte. A full verify is about 50
times faster. No golden was rebaselined.
