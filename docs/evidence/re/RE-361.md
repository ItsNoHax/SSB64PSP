# RE-361 — Framebuffer capture buffers are written back and cache-line aligned

Status: COMPLETE (code fix; PPSSPPHeadless goldens; PSP-2000 transition capture run. Stale texels were not reproduced on hardware)
Topics: hardware, memory, psp-ge, rendering
Relevant files: `psp-runtime/src/gu.rs`, `docs/memory.md`

## Question

`Gpu::capture_transition_photo` and `Gpu::capture_wallpaper_photo` copy
framebuffer rows into the statics `TRANSITION_PHOTO` and
`WALLPAPER_PHOTO` through cached pointers. The GE later samples both
buffers as textures (`transition_photo_data` through
`meshdraw::bind_texture` for `ROLE_FRAMEBUFFER`, and
`Gpu::draw_wallpaper_sprite`). No D-cache writeback followed either copy,
and both statics were only `Align16`. Is this safe on a physical PSP?

## Finding

No. The Allegrex D-cache is write-back and the GE reads by DMA, so the GE
can sample memory the CPU has not yet written back. PPSSPP does not
model the D-cache, so goldens cannot show this. With 16-byte alignment,
each buffer can also share its first or last 64-byte line with a cached
`.bss` neighbour. RE-360 showed that a neighbour's writeback on a shared
line overwrites GE-visible data.

The GE texture cache is not a separate hazard here. `sceGuTexImage` in
the pinned `rust-psp` revision (`a89142b`) ends with `sceGuTexFlush`,
and both bind paths call it on every draw.

## Change

- Both statics now use `CacheLineAligned` (`repr(align(64))`), the type
  `DISPLAY_LIST` already uses. Both sizes (16 KiB and 512 KiB) are whole
  numbers of lines, so neither buffer shares a line at either end.
- Each capture ends with `sceKernelDcacheWritebackRange` over the whole
  buffer. The capture runs after `sceGuSync(Finish, Wait)` and before
  `sceGuSwapBuffers`, so the writeback completes before any display list
  that samples the buffer is submitted.

## Verification

- Both PSP release builds pass (`psp-game`, `psp-asset-viewer`).
- PPSSPPHeadless: `tools/golden.sh verify --twice` reports 73 of 73 goldens
  match.

Hardware: PSP-2000 Slim, firmware 6.61 ARK, PSPLink v3.2.1, pack v43
(`b83c6d37…`) loaded from `host0:`. The viewer ran with
`transition_audit_capture` and `wallpaper_sprite_audit_capture`, each
built from `a081c68` (base) and from `a081c68` plus this change (fix).
Screenshots were taken 15 s after `ldstart`. `exlist` was empty after every
run.

| Scene | Base PRX | Fix PRX | Result |
|---|---|---|---|
| Transition | `9913ff21…` | `df0a93ec…` | Captures byte-identical (`2242eb46…`) |
| Wallpaper sprite | `ec248cf2…` | `76bcd25e…` | Differ only in the animated water rectangle (199,166)–(280,183) |

In the transition scene the shards show (11, 14, 19). That is the captured
backdrop colour (32, 40, 56) after modulation, not zero texels, so the GE
sampled real captured data in both builds.

## Limits

The hardware runs do not reproduce stale texels on the base build. The
transition wipe is sampled for many frames after its single capture.
Later frame work probably evicts the 16 KiB buffer from the D-cache long
before the screenshot. Only the frames just after a capture can show the
hazard, and a screenshot 15 s after launch cannot see them.

The wallpaper-sprite scene cannot show whether the GE read the capture.
Two screenshots 3 s apart in one fix run differ in the same water
rectangle, so the live stage, not the static sprite, is what reaches the
screen there.

The fix rests on the documented D-cache behaviour and on RE-360's
shared-line failure, not on an observed hardware failure.
