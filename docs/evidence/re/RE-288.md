# RE-288 — Physical PSP-1000 test: pack-load compatibility and an aborted second-unit 30-minute sustained run

Status: COMPLETE
Topics: hardware, visual-regression, asset-pipeline
Relevant files: psp/src/assets.rs (unchanged, read this session), psp/src/main.rs (`pack_status_overlay`), psp/Cargo.toml (`pack_status_overlay`)

**Question.** `STATUS.md`/`plans/rendering/R2.md` both named PSP-1000 pack
compatibility as unresolved rather than assumed: its 32 MiB RAM can't use
`MEMSIZE=1` (ignored on that hardware class, per `psp/Psp.toml`'s own
comment), unlike the 64 MiB PSP-3000 (RE-273) and Slim (RE-201-onward)
already tested, and no unit had been available to test it. The user attached
a PSP-1000 this session, also asking for the still-open "second physical
unit at the 30-minute sustained-run duration" item (RE-284 tested one unit,
PSP Slim; RE-273's second unit, PSP-3000, only ran 10 minutes).

**Setup.** PSP-1000, firmware 6.61, ARK/Infinity, PSPLink v3.2.1, connected
over USB (`054c:01c9`), bridged via `usbhostfs_pc -v "$PWD"` from the
repository root. Plain feature-free EBOOT built with `cargo psp --release`
from `psp/` (matching the pinned `nightly-2026-08-01` toolchain — running
from the repo root instead picks up the wrong `rust-toolchain.toml` and
fails to build; confirmed with `rustup show` before building). Pack
unchanged from the prior session's own recorded hash
(`256d7661bb1dc7266ea8928bc8f341cbb121f83c330a4d3821466192ea42c17d`).

**Result 1 — pack fails to load, cleanly.** Loading the plain build over
`host0:` produced zero exceptions (`exlist` empty, `main_thread` alive) but
rendered the built-in placeholder tetrahedron
(`psp/src/main.rs:2044-2049`'s `None` branch), not real content — the exact
symptom of `assets::load_pack` failing. Diagnosing the specific
`LoadError` needed reading it off the device, since PSPLink's own state
doesn't expose it. The existing `debug_overlay` Cargo feature's HUD prints
`pack_status` but does so via a large multi-line `format_args!` rendered
through `gpu.debug_text`, which uses `sceGuDebugFlush`
(`psp-0.3.13/src/sys/gu.rs`); loading that build produced an instruction-
fetch exception at that exact call site (`EPC` inside `sceGuDebugFlush`,
`BadVAddr` an odd/misaligned address, consistent with a `jr` to a garbage
register value). This looked like a real, PSP-1000-specific hardware crash
in the GU debug-print path and was initially treated as one — until
reloading cleanly (after this project's own documented `kill`-then-`reset`
step, which had been skipped before that load) reproduced **zero**
exceptions with the identical build. The "crash" was stale PSPLink
module-manager exception state carried over from an earlier unreset `kill`,
misattributed to the new load — RE-212's exact class of trap, now confirmed
to also apply to *exception* state, not just pack-load state.

Rather than re-risk the same GU debug-print path, added a narrower,
GU-free diagnostic: a new Cargo feature `pack_status_overlay` (off by
default, `psp/Cargo.toml`) that prints `pack_status` once via
`psp::dprintln!` — a raw-framebuffer text path in the `psp` crate that
bypasses `sceGu`/`sceGuDebugFlush` entirely (`psp/src/main.rs`, right after
`pack_status` is computed, `#[cfg(feature = "pack_status_overlay")]`).
Built and loaded (after the same clean `kill`+`reset` discipline this time)
with zero exceptions. Native `scrshot` shows (top-left, `psp-hw-diag3-
re288.bmp`):

```
pack: out
loaded ok:
```

Both lines clip at the framebuffer edge, but `LoadError::as_str`
(`psp/src/assets.rs:80-87`) has exactly one message starting with "out":
`OutOfMemory => "out of memory"` (the others are "pack not found", "pack is
empty", "short read") — unambiguous. `AlignedBuf::new`'s ~25.6 MiB
allocation (`psp/src/assets.rs:122-125`) fails on this unit's 32 MiB RAM
without `MEMSIZE=1`, exactly the constraint `psp/Psp.toml`'s comment
predicted. No leak or partial state: the allocation fails before anything
is held, so the fallback path runs in ordinary base-engine memory, not
"over the RAM limit" during actual execution — the only overrun is the one
failed allocation attempt itself, handled by design.

**Result 2 — second-unit 30-minute sustained run, stopped early by explicit
user instruction.** Since the pack won't load, only the fallback tetrahedron
runs on this unit; a 30-minute run on that path exercises USB/GE/thread
stability but not real game content, unlike RE-284's full-content run on
PSP Slim. Started anyway (t=0 native capture, zero exceptions) to at least
get partial second-unit duration data; reached the 5-minute checkpoint
clean (`exlist` empty, `main_thread` alive, `usbstat` unchanged) before the
user stopped it: testing a placeholder for 30 minutes doesn't validate
anything a real play session would. Per that instruction, both PSP-1000
real-content confirmation (needs a build that actually fits its RAM class,
which doesn't exist yet) and the second-unit 30-minute parity run are moved
out of R2 and deferred to a future hardware-acceptance pass once real game
UI/scene loading (`G3`) replaces the current debug asset viewer — tracked in
`TODO.md`, not as a standing R2 blocker.

**Operational note.** The PSP-1000 dropped off USB mid-session (`lsusb`
stopped listing `054c:01c9`) while sending a `kill`/`reset` to shut the game
down after the user's stop instruction; `usbhostfs_pc` was left retrying
"waiting for device" and was killed host-side. Last known device state is
either still running the harmless fallback tetrahedron or powered off — not
confirmed clean-shutdown this session. Same class of USB flakiness RE-287
already noted (worth a replug before assuming the udev rule is broken).

**Conclusion.** PSP-1000 pack compatibility is now a closed, documented
question: it does not fit without `MEMSIZE=1`, fails cleanly with
`LoadError::OutOfMemory`, and produces zero hardware-only exceptions either
loading it or falling back — this is a real product constraint (needs a
reduced-content or streaming pack design later), not a rendering bug and
not an open item R2 needs to keep tracking. The GU-debug-print "crash" that
looked PSP-1000-specific was a false alarm from this project's own
documented stale-exception trap, not a new hardware bug — worth restating
plainly since it cost a full diagnostic detour (`debug_overlay` build,
`psp-addr2line` mapping to `sceGuDebugFlush`, register dump) before the
missing `reset` was the actual explanation. R2 is closed; PSP-1000
real-content confirmation and the second-unit 30-minute run move to
`TODO.md`, gated on `G3`.

**Confidence: high** for "the pack does not fit on PSP-1000 without
`MEMSIZE=1`, and this failure mode is clean (zero exceptions, correct
fallback)" — the `OutOfMemory` identification rests on `LoadError::as_str`
being exhaustively checked, not inference. **Low** confidence (not claimed)
on the fallback path's behavior over durations beyond 5 minutes, or on
real-content PSP-1000 behavior at all — neither was tested, per the
session's explicit scope cut.
