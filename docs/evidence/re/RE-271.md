# RE-271 — Exhaustive fighter physical matrix; `draw_triangles` had the same static-buffer GE race `draw_line_strip` already fixed, found via the depth-mask diagnostic's own physical debut; 10-minute sustained-run evidence

Status: COMPLETE
Topics: fighter, hardware, psp-ge, depth, visual-regression
Relevant files: a79b0aa9...5935f, psp/src/depth_diag.rs, psp/src/gu.rs, depth_diag.rs, main.rs, gu.rs, 66ce9869...a5336

**Question.** With RE-270 closing Fox/Ness/Link/Donkey Kong/Dream Land, what
of R2's formal matrix remained reachable without new stage scenes or
PSP-1000 hardware: the other 6 playable fighters (Mario, Luigi, Samus, Yoshi,
Pikachu, Purin), Kirby's post-RE-263 re-capture, the depth-mask diagnostic's
first-ever physical run, and a long-duration physical session?

**Setup.** Same PSP Slim, firmware 6.6.1, ARK/Infinity, PSPLink v3.2.1,
`usbhostfs_pc`/`host0:` session as RE-270, same rebuilt pack
(`a79b0aa9...5935f`, 28,531.3 KiB).

**Fighter matrix.** For each of `regression_capture_mario`, `_luigi`,
`_samus`, `_yoshi`, `_pikachu`, `_purin`, and `_kirby`: built, `ldstart`ed,
waited past tick 240, checked `exlist`/`thlist` (empty/alive every time),
`scrshot`, killed by UID, `reset` before the next `ldstart`. All seven loads:
zero exceptions. Upscaled 2x nearest-neighbour diffs against their PPSSPP
goldens ran 25,136–40,328 differing pixels (out of 522,240) — the same
edge-antialiasing/PSPLink-overlay shape already established, not a solid
corrupted region. Visual inspection confirms every model, colour and texture
matches: Mario, Luigi, Samus, Yoshi, Pikachu and Purin's own golden poses
(none previously captured on physical hardware at all), and Kirby's smooth
oval eyes with no inward spike under RE-263's fix (superseding RE-209's
pre-fix capture). All 12 playable fighters are now physically confirmed.

**Depth-mask diagnostic: a real hardware-only bug, not noise.** Physically
running `depth_mask_diagnostic` (RE-251's synthetic three-quad
`sceGuDepthMask` ON→OFF→ON proof) for the first time produced 319,876
differing pixels against the golden — an order of magnitude above every
other capture this session. Visual inspection showed only the smallest quad
(C, opaque blue) on a correct clear-colour background; the two larger quads
(A, opaque red, farthest; B, translucent green, nearest) were entirely
absent, not merely misaligned or discoloured. A second capture, unrelated in
timing, reproduced the identical result byte-for-byte (aside from PSPLink's
own overlay), ruling out a one-off capture race.

Reading `psp/src/depth_diag.rs`'s `quad()` helper found it writes each of
the three quads' vertex data into one `static mut QUAD` buffer, reused in
place for all three sequential `gpu.draw_triangles()` calls in the same
frame. `Gpu::draw_triangles` (`psp/src/gu.rs`) submitted that pointer to
`sceGumDrawArray` directly, with no copy. This is exactly the hazard
`Gpu::draw_line_strip`'s own doc comment already names, from a prior
session's fix for the same class of bug: the GE reads submitted vertex data
asynchronously, and a caller that reuses one scratch buffer across several
draws in the same frame can have real hardware's GE still reading an
earlier draw's vertices out of that buffer after the CPU has already
overwritten it with the next one — so by the time the GE actually executes
A's and B's draw commands, the shared buffer holds C's geometry, and all
three draw calls end up rendering C's small quad (each under its own
already-correctly-sequenced blend/depth-mask state), producing exactly one
visible opaque blue square. `draw_line_strip` was fixed this way already;
`draw_triangles` — used only by `depth_diag.rs`'s three sequential quads and
one single-shot collision-overlay call in `main.rs` — was not.

**Fix.** Changed `Gpu::draw_triangles` to copy `verts` into
`sceGuGetMemory`-allocated display-list arena memory before submitting,
mirroring `draw_line_strip`'s existing fix exactly (`psp/src/gu.rs`). No
caller changed.

**Verification.** PPSSPP headless capture of `depth_mask_diagnostic` after
the fix is byte-identical to the existing committed golden (0 differing
pixels) — confirming PPSSPP's GE emulation was never affected by this race,
consistent with `draw_line_strip`'s own doc comment ("PPSSPP's GE emulation
keeps pace with the CPU closely enough that this never shows up there").
Physical re-capture after the fix: 628 differing pixels (ordinary
antialiasing/overlay noise), and visual inspection shows the correct nested
red/olive/blue squares exactly matching the golden. `cargo fmt --check`
inside `psp/` shows no diff for the changed `gu.rs` hunk (an unrelated,
pre-existing `main.rs` formatting drift remains, already noted by RE-251 as
a separate toolchain issue, not touched here).

**Long-duration run.** Launched the plain feature-free EBOOT
(`66ce9869...a5336`) and let it run 10 continuous real-time minutes under
PSPLink, checking `exlist`/`thlist` at the 5- and 10-minute marks: zero
exceptions, `main_thread` alive throughout, USB connection stable. A final
screenshot after 10 minutes shows Dream Land rendering intact with no VRAM
corruption or leak artifacts.

**Conclusion.** All 12 playable fighters are now physically confirmed (Mario,
Fox, Captain Falcon, Kirby, Ness, Donkey Kong, Link, Luigi, Samus, Yoshi,
Pikachu, Purin), the depth-mask diagnostic is physically confirmed post-fix,
and a 10-minute sustained run shows no hardware-only stability failure. This
session also found and fixed a second real instance of the exact GE-race bug
class `draw_line_strip` already named — proof that R2's physical matrix
finds real bugs PPSSPP cannot, exactly as the milestone's own objective
states. PSP-1000 coverage and exhaustive/long-duration coverage beyond this
10-minute sample remain open, deliberately deferred until the game structure
grows beyond the current asset viewer.

**Confidence: high** — zero exceptions across 8 fighter/diagnostic loads and
one 10-minute session, matching golden content on every load, a
reproducible pre-fix failure, a byte-identical PPSSPP golden after the fix
(ruling out a software-side regression), and a physical re-capture
confirming the fix, all mutually consistent.
