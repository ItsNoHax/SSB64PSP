# RE-324 — Material animation phase

Status: COMPLETE (decomp reference exact at phase 0; PPSSPP goldens; pre-roll control)
Topics: material, animation, stage, visual-regression
Relevant files: `crates/ssb-rom/src/matanim.rs`, `tools/romtool/src/matcolors.rs`

**Question.** RE-322 measured `MaterialJoint`'s tick `n` as the decomp's
frame `n + 2` for every material track. Where do the two frames come from,
and does removing them change anything beyond the phase?

## Source behaviour

`gcParseMObjMatAnimJoint` (`sys/objanim.c:840-853`):

- On the first call `anim_wait == AOBJ_ANIM_CHANGED`. It becomes
  `-anim_frame` and the parse runs without subtracting `anim_speed` and
  without the early `anim_wait > 0` return.
- Every key command sets `length = -anim_wait - anim_speed`
  (`objanim.c:931`, `968`, `1012`, `1074`, `1159`, `1196`).
  `gcPlayMObjMatAnim` then adds `anim_speed` before reading, so a key's
  first visible length is 0.

`gcAddAObjForMObj` (`sys/objman.c:1230-1237`) starts each track at value 0
and `length_invert` 1.

## Cause

`MaterialJoint` had two one-frame leads:

1. `start` stored `anim_wait = -frame`, and the first `parse` also
   subtracted `speed`. The decomp's first parse does not.
2. `apply` set `length = -anim_wait`, without `- speed`.

## Change

- `MaterialJoint` has a `changed` flag, set by `start` and cleared by the
  first `parse`. That parse does not advance the clock.
- `apply` sets `length = -anim_wait - speed`.
- `romtool matcolors` drops its `PHASE` offset: runtime tick `n` is compared
  with reference frame `n`.
- Stage (`MaterialAnimator`) and effect (`EffectMaterialAnimator`) joints
  share the engine, so both shift. `colors_at` (costume lists) already used
  the decomp's convention and is unchanged.

**Consequences now pinned by tests.** Frame 1 shows a ramp's authored start
(Link Spin Attack's alpha is 0 on frame 1, 204 on frame 13). A payload-0 key
from an unset track shows the zero base on frame 1 and its value on frame 2.
A loop that ends on a `_AFTER` step with a new value, followed by
`SET_ANIM` into a payload-0 step, never shows that value: the restart
replaces it on the frame it becomes due. The old engine showed it for one
tick. ROM loops close on their start value (for example file 105's palette
cycles), so two synthetic test scripts gained that closing step.

## Limits

- Frame 1 is the first `gcParseMObjMatAnimJoint` call. When that call
  happens relative to scene start or effect spawn is not measured here.
- `romtool matcolors` checks raw track values, not the resolvers that
  turn them into a texture, palette, UV window or LOD fraction.
- `MaterialJoint`'s `SetTargetRate` rewrites the value pair, length and
  kind, and its steps keep `rate_target`; the decomp does neither. The
  replay runs four ROM `SetTargetRate` commands and sees no difference,
  so no ROM script exposes either divergence. Left unchanged.
- No physical-PSP capture; the change adds no GE state.
