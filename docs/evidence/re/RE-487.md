# RE-487 — Compacting the per-mesh draw path: fetches down, link order still wins on hardware

Status: COMPLETE (PSP-2000, 6.61 ARK, PSPLink v3.2.1, `profile_hw,capture_scene_file,no_audio` builds of `vs4@2400` from `ms0:/PSP/GAME/ssb64/` with pack v108, `profile_hw.txt` = `frame`, reports 1–18, one run per build)
Topics: performance, hardware, toolchain
Relevant files: `psp-runtime/src/meshdraw.rs`, `psp-game/link-order.txt`

## Question

RE-482 found three quarters of the draw's I-cache misses in twelve
functions, one pass touching 14.7 KB scattered through ~60 KB; linking
the hot functions first already cut misses 8%. Would compacting the hot
paths themselves inside those functions — moving rare branches
(billboard nodes, the loading-transition photo, vertex colour/texgen
overrides, the always-`top=0` mip loop) out of line, and composing the
per-node model matrix on the CPU instead of through `sceGum*` — shrink
the touched footprint further, and would regenerating the link order
from the new, smaller functions help on real hardware?

## Change measured

`psp-runtime/src/meshdraw.rs`, three source changes, no rendering-path
change for levers 2–4 (pure code motion) and one float-path change for
lever 1:

1. `bind_texture`'s `ROLE_FRAMEBUFFER` branch (the loading-transition
   photo) outlined to `bind_transition_photo`; the mip-level loop
   (`for level in 0..=top`, confirmed `top` is always a literal `0`,
   RE-127) flattened to straight-line code for the one iteration that
   ever runs.
2. `draw_mesh_vertices`'s `signed_clamp_uv` and
   `effect_colors.is_some() || linear_texgen` branches outlined to
   separate `#[inline(never)]` functions.
3. `draw_object_posed_nodes`'s billboard arm outlined.
4. The non-billboard model matrix is now composed on the CPU
   (`ssb_engine::math::Mat4`, `base * local`) and submitted with one
   `sys::sceGuSetMatrix`, replacing the
   `sceGumMatrixMode`+`sceGumLoadMatrix`+`sceGumMultMatrix` sequence
   (and its `vfpu_context::prepare` save/restore) for the common case;
   the billboard arm keeps `sceGum*` (RE-482's attributed misses apply
   only there now). `DrawState::set_model_matrix` records the composed
   matrix for the texgen path the same way `note_model_matrix` already
   did.

`psp-game/link-order.txt` was also regenerated from the new, smaller
symbols (`tools/icache/order.py`) and tried as a candidate; see results.

## Results

Model (PPSSPP I-cache model, `tools/icache/`, same method as RE-482):
one draw pass's fetches are down 21% and its modelled misses down 1.2%
against the pre-batch build. The per-pass footprint is still about
29 KB: `draw_stage_links`, `draw_magnifiers` and `draw_training` share
the same pass as the per-mesh path and were not touched by this batch,
so they now dominate the remaining footprint.

Hardware, PSP-2000, 6.61 ARK, PSPLink v3.2.1, `vs4@2400` without audio,
`profile_hw.txt` reports 1–18 averaged, frame span in µs
(CPU/draw/draw-I-miss):

| Build | Frame | Draw | Draw I-miss |
|---|---:|---:|---:|
| HEAD (`f6fb8ab`, pre-batch) | 21,533 | 13,585 | 20,360 |
| This batch, HEAD's link order | 20,877 | 12,934 | 18,857 |
| This batch, regenerated link order | 21,035 | 13,164 | 19,766 |

Runs are deterministic within about 20 µs (RE-481's convention).

- **The compaction itself works**: HEAD's link order with the compacted
  functions draws 651 µs (4.8%) faster and takes 1,503 fewer I-misses
  than pre-batch HEAD.
- **Regenerating the link order from the model made it worse**, not
  better: 158 µs slower and 909 more I-misses than keeping HEAD's order
  on the same compacted source. The model's ranking of function orders
  does not transfer to hardware at this scale — RE-482's own link-order
  change was validated on hardware directly, not re-derived from the
  model a second time; a second re-derivation does not reproduce or
  improve on the first. `psp-game/link-order.txt` stays at HEAD's
  ordering.
- Lever 1 (the CPU-composed matrix) changed the actual float path for
  the common per-node case; a full golden run (198/198) against this
  `meshdraw.rs` passed with pixel-hash equality, so the VFPU multiply
  and the scalar one agree to the rounding the hashes check.

## Consequences

- Further gains from this function set are smaller now: the remaining
  ~29 KB per pass is shared with `draw_stage_links`, `draw_magnifiers`
  and `draw_training`, not concentrated in the per-mesh functions this
  batch touched.
- Next candidate: `draw_stage_links` (13.6 KB, ~850 misses/frame per
  RE-482's attribution) is the next largest single function in the
  shared pass.
- Do not re-derive `link-order.txt` from the model again without a
  hardware A/B; this batch's second attempt cost 158 µs for no model
  disagreement before the run.
