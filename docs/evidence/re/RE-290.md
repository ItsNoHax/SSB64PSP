# RE-290 — `psp-game`'s Menu -> Training confirm transition, pixel-confirmed via PPSSPPHeadless (closes RE-289's open item)

Status: COMPLETE
Topics: front-end, toolchain, visual-regression
Relevant files: psp-game/Cargo.toml (`regression_capture`/`headless_capture` features), psp-game/src/main.rs (`scripted_buttons`, `deterministic_capture_frozen`, `emit_headless_screenshot`), tools/run-ppsspp-headless.sh (`--crate` flag)

**Question.** RE-289 confirmed `psp-game`'s Intro -> Menu transition and full
menu-cursor navigation by exact pixel sampling, but could not confirm the
final Menu -> Training confirm press: synthetic X11 key injection into a
windowed PPSSPP instance (the project's Xlib fallback) raced this desktop's
Wayland/XWayland compositor focus arbitration and the key never landed,
across eight repeated attempts on a fresh instance. This session re-attempted
the same windowed approach with `xdotool` instead (installed, confirmed
`xdotool getactivewindow` correctly reported the PPSSPP window as focused)
and reproduced the identical failure — the key still did not register at
the target screen, ruling out the specific injection tool as the cause and
confirming RE-289's Wayland/XWayland diagnosis. The user also flagged that
windowed/X11-input automation takes over real desktop input focus while it
runs, interfering with normal use of the machine. So: can the transition be
confirmed without a windowed PPSSPP instance or any X11 input injection at
all?

**What was built.** `psp-game` gained the same deterministic-capture
machinery `psp/` already has for its own unrelated purpose (freezing
render/physics state for golden screenshots), reused for a new purpose:
scripting *input*, not just freezing output. `psp/` has no existing
precedent for input scripting — its viewer has no input-driven state
machine to script, so its `regression_capture` family only ever freezes
physics/animation/camera. `psp-game`'s Intro -> Menu -> Training navigation
is entirely input-driven, so proving it deterministically needs a scripted
input source, not just a frozen one.

Two new Cargo features on `psp-game`, named to match `psp/`'s existing
`regression_capture`/`headless_capture` for tooling symmetry even though the
underlying mechanism differs:

* `regression_capture`: `scripted_buttons(tick: u64) -> N64Buttons` replaces
  real `sceCtrl` polling with a fixed table — tick 4 presses `A` (Intro ->
  Menu), tick 8 presses `A` again (Menu -> Training; the cursor already
  starts on `TRAINING_ENTRY`, so no D-pad navigation is needed first).
  `deterministic_capture_frozen(tick)` (mirroring `psp/main.rs`'s function of
  the same name/pattern) stops all further state transitions once
  `sim_frame_index >= DETERMINISTIC_CAPTURE_TICKS`.
* `headless_capture`: `emit_headless_screenshot()`, a verbatim copy of
  `psp/`'s function of the same name (`sceIoDevctl(b"emulator:\0",
  0x20, ...)`), fired once via a latch when the sim first reaches the frozen
  tick.

`tools/run-ppsspp-headless.sh` gained a `--crate psp|psp-game` flag (default
`psp`, existing invocations unchanged), staging each crate's EBOOT into its
own memstick subfolder (`ssb64_regression` / `ssb64_game_regression`) so a
`psp` and a `psp-game` capture can't clobber each other. `psp-game` doesn't
load the asset pack yet, so pack staging is best-effort for that crate
(warns, doesn't fail) rather than the hard requirement it is for `psp`.

**Verification.**

*Build.* Both `cargo psp --release --features regression_capture,headless_capture`
and the plain `cargo psp --release` (normal interactive build, features off)
succeed from `psp-game/`. `psp/`'s own tree is untouched (`git status` shows
only `psp-game/Cargo.toml`, `psp-game/src/main.rs`, and
`tools/run-ppsspp-headless.sh` changed).

*Headless capture, final state (`DETERMINISTIC_CAPTURE_TICKS = 16`, past both
scripted presses).* `tools/run-ppsspp-headless.sh --crate psp-game --seconds 6`
produced a screenshot whose background pixel is an **exact** match,
`(20,48,24)`, to `BG_TRAINING`'s literal RGB value — a value distinct from
both `BG_INTRO` (`24,32,64`) and `BG_MENU` (`16,16,24`), so this alone proves
the full Intro -> Menu -> Training sequence ran (that screen is only
reachable via `Screen::Training`, itself only reachable from `Screen::Menu`
with `cursor == TRAINING_ENTRY` and a fresh `A` press, itself only reachable
from `Screen::Intro`). No error/panic/reject lines in the PPSSPP log.
Reproduced on a second run: identical `(20,48,24)`, no log errors.

*Headless capture, intermediate state (chain-of-evidence check).* Temporarily
lowering `DETERMINISTIC_CAPTURE_TICKS` to `6` (after the first scripted press
at tick 4, before the second at tick 8) and recapturing showed the
in-between `Menu` state exactly as RE-289's manual session found it:
background `(16,16,24)` (`BG_MENU`) and the entry-0 rectangle
`(255,200,40)` (`ENTRY_SELECTED`, sampled at the scaled screen position of
that entry). Reverted to `16` afterward and rebuilt; the final-state capture
above reproduced unchanged.

*No windowed instance, no X11 input injection.* This entire verification used
`PPSSPPHeadless` exclusively — no `flatpak run` windowed PPSSPP, no
`xdotool`/`Xlib` key injection, and no interference with the desktop's real
keyboard/mouse focus, per the user's explicit instruction to use the headless
harness for this kind of check from now on.

*Cleanup.* The regression-built EBOOT was rebuilt plain (`cargo psp
--release`, no features) immediately after, so the crate's normal build
artifact does not carry the scripted-input/freeze behaviour into ordinary
use — same discipline `psp/`'s own `regression_capture` docs require.

**Confidence: high.** This closes RE-289's one open item: the Menu ->
Training confirm transition is now pixel-confirmed, not just code-reviewed.
Criteria 2-3 of `plans/gameplay/F1.md` are now fully pixel-confirmed
end-to-end (Intro -> Menu -> Training) under PPSSPP software rendering. Still
open, unchanged from RE-289: no physical-PSP evidence for `psp-game` yet, and
criteria 4-7 (real scene loading, hitbox/damage/knockback, decomp
verification) remain future F1 work.
