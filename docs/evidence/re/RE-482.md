# RE-482 — Where the draw's I-cache misses come from; link-order placement

Status: COMPLETE (PSP-2000, 6.61 ARK, PSPLink v3.2.1, `profile_hw` builds of `vs4@2400` without audio; the per-function attribution comes from a cache model in PPSSPP, checked against the PSP's counters)
Topics: performance, hardware, toolchain
Relevant files: `tools/psp-link.py`, `psp-game/link-order.txt`, `psp-game/.cargo/config.toml`, `tools/icache/`, `psp-runtime/src/meshdraw.rs`

## Question

RE-481: four-player VS draws with 22,900 I-cache misses a frame, its
largest memory cost. PSPLink cannot sample the PC (RE-480). Which code
misses, and why?

## Method: an I-cache model in PPSSPP

`tools/icache/ppsspp-icache.patch` (on a local PPSSPP build) makes the IR
interpreter (`--ir`) log every block it runs, and models the PSP's
I-cache on that stream: 16 KB, two ways, 64-byte lines, 128 sets, LRU.
Misses and fetches are kept per line, also within a phase (from a
function's entry to its return; `draw_frame` here). With
`PPSSPP_ICACHE_TRACE` it writes the block stream for offline replay
(`reuse.py`, `loop.py`). `symbolize.py` maps lines to functions.

The model counts 19,600 draw misses a frame against the PSP's 22,900
(86%). The rest is code the model does not run: the kernel and system
calls, which PPSSPP emulates at a high level. Each function's share comes
from the model.

## Results (`vs4@2400`, frames 10–20 model, reports 1–18 PSP)

- Misses a frame by function in the draw: `draw_mesh_vertices` 3,917,
  `draw_object_posed_nodes` 3,250, `bind_texture` 1,744,
  `apply_texture_mapping` 1,003, `draw_stage_links` 810,
  `Mat4::inverse_affine` 789, `sceGumUpdateMatrix` 525,
  `sceGumMatrixMode` 515, `Pack::vertices` 407, `CachedVertexPose::pose`
  372, `vfpu_context::Context::prepare` 311. Twelve functions make up
  three quarters of the misses.
- The draw makes 135–140 mesh draws a frame. One pass of
  `draw_object_posed_nodes`'s loop (4,215 passes) touches 236 distinct
  lines, 14.7 KB: `draw_object_posed_nodes` 3.6 KB,
  `draw_mesh_vertices` 3.5, `bind_texture` 0.9,
  `apply_texture_mapping` 0.8, `sceGum*` 1.0, the rest under 0.5 each.
  Those lines are scattered through ~60 KB of function bodies (the two
  largest functions are 8 KB and 13 KB, most of which never runs), so
  they fight over sets: a pass nearly fills the cache, and a two-way
  cache cannot hold it.
- Reuse distance (30 frames, 614k two-way misses in the draw): 39% of
  the misses return to a line within 16 KB of distinct code (conflict
  misses). A fully associative 16 KB cache would miss 477k times, a
  20 KB one 284k, and a 24 KB one 223k. Placing the code better can
  remove the conflicts. To go further, a pass has to touch less code.

## Levers tried

| Build | Draw I-misses/frame | Draw µs | Frame µs |
|---|---:|---:|---:|
| Baseline (PSP) | 22,913 | 14,601 | 22,937 |
| `opt-level = "s"` for `psp-runtime` and `ssb-rom` (PSP) | 29,695 frame (unchanged) | — | 24,901 (37.8 FPS) |
| Function order (PSP) | 21,081 (−8%) | 14,087 | 22,473 |
| Function order (model) | 17,715 (−10%) | | |

- `opt-level = "s"` is slower, with the same misses. This run did not
  take PSPLink down (compare RE-480).
- LLVM's hot/cold splitting (`-hot-cold-split=true`) without a profile
  outlines 423 cold fragments, but none from the hot functions:
  `draw_object_posed_nodes` stays 8.2 KB.
- Function order: lld's `--symbol-ordering-file` places the functions
  one pass runs, in loop order, at the start of `.text`. The other
  functions follow by model line fetches. That gives −8% on the PSP, about
  0.5 ms of draw. A miss is worth about 0.28 µs here, so the draw's
  misses cost at most ~6 ms.
- After ordering, most of the misses are inside the two large functions:
  their hot paths are interleaved with cold code (`draw_object_posed_nodes`
  3,206 a frame, `draw_mesh_vertices` 3,152).

## Shipped

`tools/psp-link.py` is `psp-game`'s linker (`.cargo/config.toml`). It
runs `rust-lld` with `--symbol-ordering-file` from
`psp-game/link-order.txt`, which `tools/icache/order.py` generates from a
model dump and `loop.py` output. Names are v0-mangled with the crate hash
(`Cs<base62>_`) removed, because the hash changes with the feature set.
The production build and the `profile_hw` build both start `.text` with
`draw_object_posed_nodes`. Function order changes where the code goes,
but not the code itself.

## Open

- Shrink the per-mesh path: split the hot path within a function, via
  sample PGO from the model's block counts (an AutoFDO-style profile) with
  machine function splitting. Alternatively, restructure the per-mesh GE
  state (texture binding, texture mapping, matrices) so a pass touches
  well under 16 KB.
- The 14% of misses the model cannot see (kernel and system calls).
- When the draw code changes much, regenerate `link-order.txt`. Stale
  names are skipped (`--no-warn-symbol-ordering`), which never breaks the
  build but loses the effect.
