**Question.** `STATUS.md`/`plans/rendering/R2.md` both name "coverage across
all 41 stages/effects (no dedicated capture scenes exist for most of them)"
as open, deliberately-deferred work. Only 3 of the archive's 41 stage
entries (`255`..`295`) had a dedicated golden: stage 0 (Dream Land, the
default scene), stage 7 (`StageSectorFile2`/Sector Z, scene 3), and stage 9
(Saffron City's animated gate, scene 5) — the rest were either bonus/
tutorial/test maps or simply untested. Rather than attempt all 41 at once
(explicitly out of scope for one session), add one bounded new stage as
the next increment, per this chain's own established pattern of adding one
fighter/scene golden at a time (RE-207/208/209/etc.).

**Which stage.** Cross-referencing `romtool stages`' file-id-to-layer dump
against `refs/ssb-decomp-re/src/relocData/`'s named source files
(`255_GRPupupuMap.c` = Dream Land, `262_GRSectorMap.c` = Sector Z,
`264_GRYamabukiMap.c` = Saffron/"Yamabuki" — confirming the existing
stage-9 identification) narrows the 41-entry block to: 6 real VS-mode
battle stages (Dream Land, Zebes, Peach's Castle, Kongo Jungle, Sector Z,
Yoshi's Island, Saffron, Hyrule Castle, Final Destination — stage indices
0/2/4/6/7/8/9/10/11), a tutorial map, a Metal Mario stage, several small/
test map variants, and 26 single-fighter bonus maps (`GRBonus1*`/
`GRBonus2*`/`GRBonus3`, stages 16..40). Picked stage 4 (file 259,
`259_GRCastleMap.c`, Peach's Castle) as the next real battle stage to
cover — not a bonus/test/tutorial map — with two animated joint layers,
giving a second independent stage-animation data point besides Saffron's
gate.

**Implementation.** `regression_capture_scene10` (`psp/Cargo.toml`), added
to `deterministic_capture_frozen`'s feature list (`psp/src/main.rs`) and
setting `stage_index = 4` in the same place scene 5 sets `stage_index = 9`
— stays in the default whole-stage `stage_view` (not the object viewer),
same deterministic tick-240 freeze and diagnostic suppression as every
other scene.

**Verification.** PPSSPPHeadless software capture is deterministic:
two captures at different `--seconds` (6 and 20) are byte-identical
(`cmp`). Rebuilding plain `regression_capture` and `regression_capture_
scene5` afterward still match their existing goldens exactly (0 differing
pixels each), confirming the new feature has no effect on unrelated
builds. `tools/verify-fighter-goldens.sh` — all 12 fighter goldens still
pass. `cargo fmt --all --check` and `cargo test --workspace` (425 passed)
clean. Golden committed at `tests/golden/r2-peach-castle.png`, SHA-256
`58dfba129845c48a4231b6a1996354e9481eda883bde6263f1b9528fde43bce9`.
Physical hardware: same PSP Slim/6.61/ARK-Infinity/PSPLink v3.2.1 unit as
every prior RE-283/RE-284 check. Clean baseline (`exlist` empty, no stale
module) before load; loaded via `host0:`, zero exceptions, `main_thread`
alive; native `scrshot` visually matches the PPSSPP golden exactly (same
tower silhouette, roof, side "kite" decorations, and collision-overlay
lines the stage viewer always draws) — no scrambling, no missing geometry,
no exceptions.

**Conclusion.** Stage golden coverage is now 4/41 (Dream Land, Sector Z,
Saffron City, Peach's Castle), one more real VS-mode battle stage
physically confirmed. This narrows, but does not close, the "41 stages/
effects" coverage gap `STATUS.md`/`R2.md` name — 37 stages (5 more real
battle stages, the tutorial map, the Metal Mario stage, several test-map
variants, and 26 bonus maps) remain without a dedicated golden. Not a
blocker for R2.2 (already closed); tracked the same way the rest of this
gap already is.

**Confidence: high** — same bar as every other stage/fighter golden this
