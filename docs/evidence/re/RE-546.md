# RE-546 — Overlay `d*` tables from the ROM: the boss wallpapers' effects fade in by `dobj_color_id`

Status: COMPLETE (decomp source and US ROM SHA-1 e2929e10 through `crates/ssb-tablegen`; host tests; golden matrix; no hardware run)
Topics: tablegen, overlay, boss, d048
Relevant files: `crates/ssb-tablegen/src/source.rs`, `crates/ssb-tablegen/src/battle_data.rs`, `crates/ssb-tablegen/src/sc1p_data.rs`, `crates/ssb-tablegen/src/rom_layout.rs`, `crates/ssb-game/src/spgame/boss.rs`, `crates/ssb-rom/src/effect.rs`

## Question

The user decided on 2026-10-18 that the decompilation's `d*` data arrays
compiled into the code and overlay segments are ROM tables under
[D-048](../../decisions/D-048.md). The port had committed more than forty of
them: battle tables in `ovl2` and `ovl3`, HUD data, the title,
Characters, 1P Game, stage-clear, staff-roll, congratulations and opening
scene data, and the archive file ids, offsets and effect descriptors
`ssb-rom` reads. Many overlays share one VRAM range, so each table's ROM
offset has to come from the overlay that defines its symbol. Before the
ROM replaced each committed transcription, every entry had to be
compared with the ROM.

## Evidence

- **Where the tables lie.** Each symbol's VRAM comes from
  `symbols/symbols_us.txt` and its overlay from the `.data`/`.rodata`
  subsegment of its defining `.c` file in `smashbrothers.us.yaml`. Its ROM
  offset is the overlay's ROM start plus the offset into the overlay.
  `OverlayData` checks both ends of every read against the overlay's size.
  The ELF under `refs/ssb-decomp-re/build/` is not a matching build: its
  VRAMs are shifted and cannot be used.
- **Equal to the committed tables.** A temporary test compared the
  generated text of each table with the committed one (`Debug`, so f32s
  compare by bits): every row and every field the port keeps was equal,
  except the boss wallpapers below. The item throws' IDO bitfields read
  MSB first (`is_smash:1`, `vel_scale:10` signed, `angle:11` signed,
  `damage_scale:10`).
- **Boss wallpapers.** `SC1PGameBossWallpaper` holds `dobj_color_id` at
  +16 and `color_id` at +20. In the US ROM (`dSC1PGameBossWallpaperDescs`,
  `ovl65`) the four wallpapers have `dobj_color_id` 1, 1, 1, 5 and
  `color_id` 1, 1, 3, 1. The committed table had one field, labelled
  `dobj_color_id` but holding the `color_id` values, and used it for both.
  The decomp makes each effect with `user_data.s = dobj_color_id`
  (sc1pgameboss.c:861, 914), which is the alpha step its update adds each
  frame (:621), and `sc1PGameBossUpdateWallpaperColorID` (:600) sets the
  step to `-color_id` when the wallpaper changes. So the third wallpaper's
  effects faded in at 3 a frame instead of 1, and the fourth's at 1
  instead of 5. Their fade-out steps were already right.
- **DeadExplode effect.** The tenth effect descriptor in the ROM points
  its material-animation joints at 0x5870, player 4's entry of
  `dEFManagerDeadExplodeMatAnimJoints`. `efManagerDeadExplodeMakeEffect`
  overwrites that field with the dying player's entry before every make,
  so the port keeps element 0 (0x58E0) as its base and selects per player,
  as before.

## Outcome

- `ssb-tablegen`'s `battle_data`, `ifcommon`, `menu_data`, `sc1p_data`,
  `ending_data`, `opening_data` and `rom_layout` generate the tables, with
  zeros for the stub build. Only symbols, overlays, VRAMs, record sizes,
  counts and the names the port gives entries are committed.
- The boss wallpapers carry both fields. An effect starts with the
  wallpaper's `dobj_color_id` as its step and turns to `-color_id` on a
  wallpaper change, as in the decomp.
- `tools/docs/rom_tables_baseline.tsv` keeps the large arrays that are not
  `d*` data: tables local to a decompiled function, `ll*` link-time
  offsets the code passes as immediates, the `ftMainSetStatus` call-site
  columns, archive vertex data and test fixtures. Whether function-local
  arrays count as ROM tables is an open question in `PLAN.md`.
