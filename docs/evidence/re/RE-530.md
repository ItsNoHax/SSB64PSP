# RE-530 — Opening frame rate on a PSP-2000: the guard clip and per-vertex lighting are the cost; outcode clip and cached lighting recover part of it

Status: PARTIAL (PSP-2000, 6.61 ARK, PSPLink v3.2.1, `frame_timer` and `profile` builds, `REPORT_FRAMES` temporarily 60, pack v117; acceptance targets not met)
Topics: performance, hardware, opening movie, guard clip, lighting, fpu
Relevant files: `crates/ssb-engine/src/guard_clip.rs`, `crates/ssb-engine/src/rsp_light.rs`, `psp-runtime/src/meshdraw.rs`, `psp-game/link-order.txt`, `crates/ssb-game/src/map.rs`

## Question

RE-529 measured 30-38 FPS in the opening while RE-476 and RE-499 recorded 45-57 and 59 FPS. Which is right, and what changed?

## Method

Interleaved A/B runs on the same PSP-2000, scene `opening@2900` (whole opening from tic 0, frozen at sim tick 2900), audio on; also `opening@4400` and `opening@1100` (`profile`). Per-commit builds (bisect) of `frame_timer` with the same pack. Final = outcode-table guard clip, per-vertex lighting with the indexed draw kept, new link order (PRX sha1 0379524d); base = 3b07585 (PRX sha1 256ded5e). Raw logs and scripts were kept outside the repository (orchestrator `opening-fps-logs/`).

## Findings

1. RE-529's 30-38 FPS is real. The build at 19029f7 measures the same; HEAD is 3-5% slower than it in the room (0.5-0.9 ms CPU). RE-476's and RE-499's 45-57 FPS and 59.1 FPS predate two commits that raised the movie mesh cost; the same method at c19df38 (before RE-514) reproduces them (Run/Cliff 46-57 FPS, room 60 FPS).
2. Bisect, cause attribution:
   - 726789b (RE-519 CPU guard-band clip): the room, ticks ~60-1260, +7 ms CPU a frame, 59.7 to 36 FPS at ticks 240-300. RE-520 and RE-521 in the same commit cost nothing (clip disabled alone).
   - eddb65a (RE-514 CPU fighter vertex lighting): Run and Cliff (ticks ~2280-2580) +12.6 ms CPU, 46 to 30 FPS; fighter scenes +4 ms; room +2 ms.
3. Fix, bit-identical (218 of 218 goldens unchanged): the clip uses a per-mesh outcode table and rebuilds only crossing primitives; lighting transforms each vertex once into a cached block and keeps the indexed draw; the light-direction transform is exact in 32 bits (tested against the 48-bit accumulator).

Run stays at 30 FPS because its busy time still exceeds 16.7 ms.

`profile` run at `opening@1100` (distorts the I-cache), base to final, reports 1-17: cpu 14.9-23.6 to 12.4-19.5 ms; mmesh 12.7-20.2 to 10.1-16.1; material 2.3-4.6 to 2.1-3.2; skin 1.0-1.9 to 1.0-1.7.

Ablations (final build, room 2-5 / Run 40-42 busy): no lighting at all 11.6-12.3 / 16.5-16.7 ms; light computed but no expand 12.4-13.1 / 19.0-20.1 ms; guard clip disabled 10.0-10.1 ms in the room (room 6-12 10.8-12.7 vs 14.3-16.8 ms), Run unchanged. Run at 45 FPS needs about 16.5 ms, the no-lighting cost, so about 4 ms of lit expand remains. The clip still costs 2-4.5 ms in the room: gate about 1 ms, rebuild about 2.5 ms (18 rebuilt primitives a frame); GE wait is only 0.02-0.2 ms, so it is CPU, mostly I-cache (`rebuild_clipped` is 0x2740 bytes of cold code).

## FPU trap at `opening@4400` (pre-existing)

Base and final both take `FPU Exception (IUV)` on `main_thread` after report 53 (about tick 3180-3240, before Yoster). Final: EPC 0x08AC5268, TextAddr 0x08804000, offset 0x2C1268 in `ssb_game::map::move_ground_pushed` (via `Fighter::tick_physics_map_procs`), instruction `c.olt.s $f6,$f28` with `$f6 = lwc1 4(a3)` compared with 0.0: a NaN reaches an ordered `< 0.0` compare. Base EPC 0x08AC47C0 is the same instruction. Source `crates/ssb-game/src/map.rs:1026`. This blocks measuring Yoster, Sector and Clash.

## Remaining

Per-object batched lighting (122 `object_light_dir` calls a frame in Run) or a persistent lit-vertex arena; shrink the guard clip's executed code; re-search the link order on the shipped configuration; fix the NaN. Tracked in `PLAN.md`.
