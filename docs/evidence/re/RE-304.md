# RE-304 — PSP GE sampling alignment measured and runtime lowering corrected

Status: COMPLETE
Topics: texture, psp-ge, hardware, texgen, material
Relevant files: crates/ssb-rom/src/n64_filter.rs, crates/ssb-rom/src/psp_texture.rs, psp-runtime/src/meshdraw.rs, psp-asset-viewer/src/texture_sampling_diag.rs

**Question.** Before attempting any N64 3-point compensation, does the host
`sample_bilinear()` predict the PSP GE's actual sample positions, and do all
SSB64 UV paths lower the N64's S10.5/tile-relative coordinate to that same
position?

**Source semantics and prior art.** N64 vertex texture coordinates are S10.5
(32 units per texel). Render-tile `uls/ult/lrs/lrt` are S10.2; the runtime's
existing pack-time authored-UV path rebases a clamped coordinate by
`origin * 8`, converting S10.2 to S10.5. Repeat axes retain their phase;
mirror is pre-expanded into pixels. `sceGuTexScale` receives
`1024/uploaded_dim` because `GU_TEXTURE_16BIT` first divides the packed field
by 32768. `sceGuTexOffset` is normalized texture space. The SM64-derived PSP
renderer visible in `refs/oot-PSP` adds `filter_bias = 16.0f` before its tile
origin for linear filtering. That is exactly half an S10.5 texel, but was
treated only as a hypothesis until measured here.

**Measurement rig.** `texture_sampling_diag` is a deterministic full-frame GE
scene with independently-authored unique-colour 2x2 and 4x4 RGBA8888
textures. R/G identify source x/y. It samples centres, halves, +/-1/32 around
boundaries, diagonal positions, clamp, repeat, and a pre-baked mirrored 2x2
period. Rows compare point/no bias, linear/no bias, linear/+0.5, and the
addressing variants. Transient vertices use `sceGuGetMemory` and float screen
positions; the texture buffer uses a hardware-valid 16-pixel stride. Those
details were required for the real device rather than being PPSSPP-only
conveniences.

Real PSP capture SHA-256: `bfcdafc5e9d34c62b2b38f0d661d33628b760ae19e62c90f0bf50d90afe0ac1f`

**Measured convention.** Point filtering selects integer texel `n` at
coordinate `n`: no correction. Linear filtering's centre is half a texel
later, so an N64 coordinate must be submitted as `n + 0.5`. The correction is
16 S10.5 units, or `0.5/uploaded_dim` in the normalized coordinate consumed
by `sceGuTexOffset`/the texture matrix. The GE bilinear accumulator has four
fraction bits: odd N64 1/32 positions truncate to the prior 1/16 (`31/32 ->
15/16`). Channel output truncates rather than rounds. Examples shared by both
captures on the 4x4 pattern: corrected `(31/32,0)` -> `(60,0,45)`, corrected
`(1/2,1/2)` -> `(32,32,24)`, and corrected `(31/32,31/32)` -> `(60,60,5)`.

**Fix.** `sample_bilinear()` now models those four-bit/truncating GE weights;
point and addressed variants cover clamp/repeat and pre-baked mirror tests.
`ge_sample_offset()` centralizes the measured filter-dependent correction.
`apply_texture_mapping()` adds it after the live MObj affine offset on the
authored path, and after the N64 texgen affine term in the regular texture
matrix. CPU linear texgen already enters the authored path. Thus authored,
animated, ordinary texgen, and linear texgen coordinates all receive exactly
one correction after tile-origin lowering. The current ROM uses filtered
sampling for every measured draw (151/151), while point alignment remains
pinned by the diagnostic and host tests.

**Result.** Required correction: **+0.5 texel for filtered sampling; no offset
for point sampling**. The former runtime had no correction, and the former
host reference used ideal five-bit rounded bilinear, so neither predicted the
GE. Both are corrected. No N64 3-point compensation is implemented in this
batch; RE-219's reconstruction deviation remains a separate decision.

--no-default-features`, and the full workspace test suite pass (433
`ssb-rom`, 243 `ssb-game`, 52 `ssb-engine`, 25 `romtool`). Both plain release
PSP EBOOTs build. The diagnostic was captured through PPSSPP software and the
