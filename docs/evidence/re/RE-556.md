## Question

Does `matchtick::step` run the decomp's per-frame process order, and where does it depart?

## Evidence

- Oracle: patched decomp N64 build stamps a ring in RDRAM per process (link, priority), read per frame under mupen. The ring distinguishes both orders, so a null cannot hide a swap.
- Order pinned by `matchtick/tests.rs` (`PROCESSES`: priority, link, file:line). `port_order` = `decomp_order` + `Settle` (D-052). Mutating the Go unlock or interface hook order fails both tests.

## Deviations

- `Settle` after the hit phase: the one port-only phase (D-052).
- Clash search: a slot refilled mid-pass takes no record or clash damage (RE-416).
- Host harness fighters start with private counts; `matchtick::step` adopts them onto the battle's (max of both) so draws stay unique. The stale dedup is keyed on `(attack_id, motion_count)` only (`ftparam.c:1639-1665`); no origin tag.
- `stale::MotionId` is per fighter; `gFTManagerMotionCount` is global in the decomp.
- Stack (RE-469): `ManagerCounts` (an `Rc`) made `FighterScene` and `ItemPool` non-trivially droppable, so the `Session` literal in `run` kept a 36944 B `Option<FighterScene>` alive through unwind cleanup (`run` frame 102240 to 145632 B, deepest game stack 366976 to 410384 B). `#[inline(never)] new_session` builds it out of line: `run` 102176 B, `new_session` 136040 B (boot only, off the deepest path), deepest stack 366928 B (`f1-onep-platforms-ride`).
