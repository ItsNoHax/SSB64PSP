# RE-319 — Texture buffer rows under 16 bytes are read at the wrong pitch

Status: COMPLETE (PPSSPP and PSP-2000 stripe diagnostics, host tests, 44 goldens refreshed)
Topics: texture, psp-ge, pack, visual-regression

Relevant files: `crates/ssb-rom/src/psp_texture.rs` (`ge_buffer_stride`,
`GE_MIN_BUFFER_ROW_BYTES`, `ge_texture_dims`), `crates/ssb-rom/src/pack.rs`
(`VERSION` 32), `psp-runtime/src/meshdraw.rs` (`bind_texture`,
`apply_texture_mapping`), `tools/romtool/src/residuals.rs` (`decode_packed`),
`tools/run-ppsspp-headless.sh` (`PPSSPP_MEMSTICK_NAME`)

**Question.** RE-314 found from PPSSPP source that `GetTextureBufw`
(`GPU/Common/TextureDecoder.cpp`) masks the texture buffer width with
`textureAlignMask16` and turns anything under 16 bytes into 16 bytes. The
software rasterizer uses the same function (`GPU/Software/Rasterizer.cpp`).
Pack v31 stored 304 textures with rows under 16 bytes. Does the GE really read
them at the wrong pitch, and how much of the shipped output does it corrupt?

## Census

A host reader over the RE-318 pack v31: 1,869 textures, of which 304 have rows under
16 bytes. All 304 are `PsmT4`, unswizzled, one level: 241 at stride 16
(8-byte rows) and 63 at stride 8 (4-byte rows). No other format has short
rows. Every texture's stride was `pad_to_power_of_two(width)`.

For `PsmT4`, the mask rounds a 16-texel width down to 0 and PPSSPP substitutes
32 texels. So texel row `r` is read at byte `16 r`: source rows `2r` (texels
0–15) and `2r + 1` (texels 16–31). Only the first half is ever in range of a
16-wide texture, so the GE shows even source rows only. It also reads past
the end of the texture into its pack neighbours. A stride-8 texture is read
at four times its pitch.

## Measurement

PPSSPPHeadless (software GE), graph `138:0x2998`
(`SSB64_CAPTURE_OBJECT`, feature `regression_capture_object`). The data of
textures 790 (16×400) and 791 (16×576) was replaced with row-parity stripes:
index 1 (red) on even rows, index 2 (green) on odd rows.

| Pack | Pillar pixels changed vs unpatched | Colours |
|---|---|---|
| v31 + stripes | 191 | all `(89, 0, 0)`: red only |
| v32 + stripes (stripes laid out at the 16-byte pitch, then swizzled) | 191 (160 ≥ 32) | red/green blends, e.g. `(50, 39, 0)`, `(22, 67, 0)` |

Under linear minification each pixel blends neighbouring rows. With the
correct pitch that mixes both parities. Pure red means every sample came from
an even source row. The doubled pitch is confirmed. The v32 row is the
control: the same test reads both parities once rows are 16 bytes.

## Fix

`psp_texture::ge_buffer_stride(width, bits)` is the power of two of `width`
widened to at least `GE_MIN_BUFFER_ROW_BYTES` (16): 32 texels for `PsmT4`,
16 for `PsmT8`, 8 for 16-bit, 4 for 32-bit. `pack_rgba`, `pack_indexed` and
the mip encoder store every level at that stride. The added columns repeat
the edge texel, like other power-of-two padding (RE-222).

The declared GE size must not grow. A 16-wide texture declared as 32 would
repeat every 32 texels, not 16. `ge_texture_dims` now takes the logical width
(`TextureDesc::width`), not the stride. The runtime passes it to
`sceGuTexImage` and to the UV scale, and keeps `stride` as the buffer width.
For every v31 texture `pad_to_power_of_two(width) == stride`, so the declared
size, UV scale and wrap period of every texture are unchanged.

Mip chains still stop where the unwidened row could not swizzle. That keeps
every chain the same length; the runtime never samples lower levels (RE-127).

Pack `VERSION` 32. A v31 runtime would declare a widened texture from its
stride and double its wrap period, so it must reject v32 packs.

## Result

- Pack v32: 22,109,232 bytes (+98,848), SHA-256
  `4a972a600fe5bec0edc3fcea14d1ce580f72426cce1af6df2f9692055098763e`.
- Pack v31 vs v32, per texture: 1,565 identical; exactly the 304 short-row
  textures changed. Each keeps its level-0 texels row for row and its
  palette, size, levels and wrap. 289 of them now swizzle, because a 16-byte
  row with a height that is a multiple of 8 fills whole swizzle blocks. No
  short rows remain.

## Goldens

Against the RE-318 baseline, `tools/golden.sh verify` found 44 changed scenes
and 23 unchanged. The 44 changes range from 56 to 17,092 differing pixels at
2× resolution. Examples: Bonus 1 Pikachu 17,092 px, Bonus 2 Pikachu 15,808,
Bonus 2 Yoshi 15,556, Training Fireball 14,888, Training Shadows 10,944,
Peach's Castle 7,172, Captain Falcon 6,748, Dream Land 3,312. Both PSP
applications are affected because they share the pack and renderer.

The changed regions match the repaired short-row textures: stripes and
streaks become coherent stage surfaces, Dream Land's stars are intact, and
Captain Falcon's sash and boot textures read correctly. All 44 goldens were
refreshed after two pixel-identical captures. `verify --twice` then passed all
67 scenes. The Mario entry-pipe golden is unchanged; RGB differences in fully
transparent pixels are ignored by the pixel comparator and are not a visible
change. Viewer animation is already per simulation tick (RE-315), so no pack
size control is needed.

The regenerated three-point residual report covers 1,620 variants and 4,235
primitive use sites. It finds 0 suspected implementation bugs, 0 unattempted
formats, 0 packed level-0 mismatches, and 0 padded-addressing mismatches.

## Physical PSP

RE-320 repeated the stripe diagnostic on a PSP-2000 Slim running firmware
6.61. The old 8-byte row produced 191 pure-red pillar pixels; with v32's
16-byte row, 185 of those same pixels contained green from adjacent rows.
The unmodified v32 pack also loaded and rendered without exceptions. Thus
the 16-byte pitch and its correction hold on this physical device for the
`PsmT4` format that accounts for all 304 affected textures. Other formats,
models, and the full on-device golden matrix remain separate questions.
