# RE-292 — `psp-game`'s 3D pipeline, mesh drawing and real gameplay slice ported from `psp/`; Training now renders a real stage and fighter

Status: COMPLETE
Topics: front-end, toolchain, visual-regression, physics, animation
Relevant files: psp-game/src/gu.rs (3D pipeline additions), psp-game/src/meshdraw.rs (new, verbatim copy of psp/src/meshdraw.rs), psp-game/src/play.rs (new, verbatim copy of psp/src/play.rs), psp-game/src/main.rs (`mod meshdraw`/`mod play`, `Play` wiring, `draw_training`)

**Question.** `plans/gameplay/F1.md`'s "Scene loading — still to build" list,
after RE-291 landed pack loading, names three remaining pieces: a full
`gu.rs` 3D pipeline (depth test, culling, projection/view matrices, textured
mesh drawing), fighter/stage instantiation through `ssb-game`'s
`Fighter`/`ground`/`camera` modules, and `sceFont` text. Can the first two be
ported into `psp-game` and made to draw a real stage with a real,
physics-simulated fighter standing on it — the same slice `psp/src/play.rs`
already proves on the debug-viewer side — rather than the flat placeholder
rectangle `BG_TRAINING` has been since RE-289?

**What was built.**

* `psp-game/src/gu.rs`: additive 3D pipeline on top of the existing flat 2D
  rectangle path (unchanged for Intro/Menu, RE-289/290's pixel evidence
  stays valid). Added a depth buffer (`Psm4444`, matching `psp/gu.rs`'s own
  convention), `GuVertex` (textured 3D vertex layout), and
  `set_perspective`/`reset_modelview`/`set_view`/`model_transform`/
  `model_matrix` — all verbatim copies of `psp/gu.rs`'s own methods.
  `Gpu::init` now defaults `DepthTest`/`CullFace`/`ClipPlanes` on (`psp/`'s
  own default); `draw_rect`'s flat 2D sprites bracket both off around their
  own draw call and restore them after, the same pattern `psp/gu.rs`'s own
  `draw_wallpaper_sprite` uses for its 2D content, so the flat screens are
  unaffected by the pipeline now defaulting to 3D-ready. Two viewports:
  `set_viewport_fullscreen` (Intro/Menu, RE-289/290's own already-proven
  shape) and `set_viewport_pillarboxed` (Training, the N64-aspect pillarbox
  `psp/gu.rs`'s own doc comment found necessary by measurement — an
  unpillarboxed 480px-wide viewport stretches every character about a third
  too wide). A `transition_photo_data` stub (zero-filled, documented) lets
  `meshdraw::bind_texture`'s `ROLE_FRAMEBUFFER` branch compile without
  porting `psp/`'s LB-transition capture system, which `psp-game` has no
  caller for yet.
* `psp-game/src/meshdraw.rs` (new): verbatim copy of `psp/src/meshdraw.rs`
  — `DrawState`, `bind_texture`, `apply_texture_mapping`, `apply_material`,
  `draw_mesh`, `draw_object`/`draw_object_posed`/`draw_object_node`,
  `draw_stage`/`draw_stage_animated`, `draw_collision`, `draw_fighter`
  (collision-diamond marker), and the bounds/particle/texture-quad
  diagnostics, unchanged. Per the crate-boundary rule (own copy, not a
  shared refactor — the same reasoning RE-291's `assets.rs` and `psp-game`'s
  `gu.rs` already document): this is the decomp-derived rendering-state
  machine (texture/CLUT binding, N64-to-GE material-flag translation,
  texgen, alpha/depth/blend gating) that `docs/rendering/*.md` and dozens of
  earlier `RE-0xx`–`RE-28x` records established; copying it exactly is what
  keeps this a mechanical port rather than a second, independently-drifting
  implementation of the same rules. Not trimmed to only what Training
  currently calls (`draw_object`/`draw_object_posed`/`draw_stage` pull in
  the rest transitively regardless), so `cargo psp --release` reports
  `dead_code` warnings for the diagnostics/overlay helpers Training does not
  call yet (`draw_collision`, `draw_fighter`, `draw_particle`,
  `draw_texture_quad`, the `*_bounds` functions) — expected, not a defect.
* `psp-game/src/play.rs` (new): verbatim copy of `psp/src/play.rs` —
  `FloorSegments` (walks the pack's collision polylines the way
  `ssb_game::collision` wants), `Play` (spawns a fighter on a stage's first
  spawn point, ticks real physics/animation/camera against the real
  collision every frame, `psp/`'s own gameplay-slice adapter between the
  pack format and `ssb-game`, which knows neither).
* `psp-game/src/main.rs`: `Screen::Menu`'s A-press into Training now spawns
  `play::Play::at_spawn(pack, &stage)` on `TRAINING_STAGE_INDEX` (0, Dream
  Land — this project's own established default/unset convention, e.g.
  `psp/Cargo.toml`'s `regression_capture_stage_index` doc). Every Training
  frame (gated by the existing `deterministic_capture_frozen` check, so
  headless captures stay reproducible) ticks `Play` with real `sceCtrl`
  stick input — `ControllerState::default()` under `regression_capture` so
  a capture cannot vary with incidental pad state, matching
  `scripted_buttons`'s existing determinism story for screen navigation.
  Jump is deliberately **not** wired: `psp/`'s own C_LEFT jump substitute is
  an explicit debug-viewer stand-in (its real controls occupy the actual
  binding) and the real SSB64 jump button has not been sourced from the
  decomp for this front end yet — declined rather than guessed, this
  project's standing rule (`AGENTS.md`). A new `draw_training` function
  replaces the flat-rectangle Training draw: sets the pillarboxed viewport,
  a 38-degree-FOV perspective (`refs/ssb-decomp-re/src/gm/gmcamera.c:1191`'s
  real battle-camera default, matching `psp/main.rs`'s own sourced value)
  with a fixed far plane, the real `Play::camera`'s `eye`/`at` as the view
  matrix, then `meshdraw::draw_stage` for the stage and
  `meshdraw::draw_object_posed` for the fighter (posed via
  `Skeleton::compose`, lit via `configure_fighter_light`/
  `stage.light_angle_xy` matching `ftDisplayMainProcDisplay`'s own
  per-fighter light rebuild, RE-164). Falls back to the unchanged flat
  `BG_TRAINING_NO_PACK` when the pack or stage isn't available — the same
  pixel-provable no-pack signal RE-291 established, still correct with real
  content behind it.

**Known, documented simplifications** (not incorrect, just not yet built):
material animation (palette cycling) is not ticked, so an animated texture
shows its static baked palette (`bind_texture`'s own documented fallback for
"a device build with no animator at all"); stage scenery animation uses
`draw_stage` (the static path) rather than `draw_stage_animated`; costume is
always 0; no second camera interest. None of these are guesses — each is the
documented behaviour of passing `None`/`0` to an already-verbatim decomp-
derived function, not a new heuristic.
