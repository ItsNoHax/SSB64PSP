# RE-303 — Motion-script async waits target animation frames

Status: source verified; Fox normal-attack transcription uses this rule.

## Source

`refs/ssb-decomp-re/src/ft/ftmain.c`, `ftMainParseMotionEvent`, cases
`nFTMotionEventSyncWait` and `nFTMotionEventAsyncWait` (around lines 181–190):

- `SyncWait(n)` adds `n` to `script_wait`.
- `AsyncWait(n)` assigns `n - fighter_gobj->anim_frame` to `script_wait`.

Thus `AsyncWait` targets animation frame `n`; it does not add `n` frames to
the prior event's time. A target already passed advances immediately. This
matters in Fox's forward smash: `AsyncWait(8)`, `AsyncWait(12)`, `Wait(5)`,
`Wait(8)`, `AsyncWait(28)`, `AsyncWait(45)` ends its script at frame 45,
not frame 106. `tools/extract_fox_moves.py` applies this rule and emits the
static Fox `MoveData` in `crates/ssb-game/src/fox_attack.rs`.

## Scope and follow-up

This is a motion-script interpretation, not an animation-clip duration.
The existing Mario `MoveData` comments and some windows sum successive
`WaitAsync` operands; review those values against the interpreter and ROM
clips in a separate correction before treating them as final timing proof.
Fox's clip lengths, status transitions, and packed animation slots are now
