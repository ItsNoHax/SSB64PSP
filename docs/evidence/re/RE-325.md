# RE-325 — Material resolvers against the decomp draw path

Status: COMPLETE (decomp reference exact on all 103 entries; host tests; PPSSPP goldens)
Topics: material, animation, texture, palette, pack, visual-regression
Relevant files: `tools/romtool/src/matcolors.rs`, `crates/ssb-rom/src/skeleton.rs`, `crates/ssb-rom/src/matanim.rs`

**Question.** RE-324 checked `MaterialJoint`'s raw track values. Do the
resolvers that turn them into a texture, palette, tile-0 window and
two-tile blend match `gcDrawMObjForDObj`? And does `MaterialJoint` handle
the commands the ROM replay could not expose the way the decomp does?

## Source behaviour

`gcDrawMObjForDObj` (`sys/objdisplay.c:1125-1420`):

- `sprites[texture_id_curr]` under `FRAC | ALPHA`, and
  `sprites[texture_id_next]` for tile 6 under `FRAC | SPLIT`. Both fields
  are `u16`, so the float track value truncates. Under `MOBJ_FLAG_FRAC`
  the draw overwrites both from `(s32)lfrac`.
- `palettes[(s32)mobj->palette_id]` under `PALETTE`. `palette_id` is an
  `f32`, and `gcPlayMObjMatAnim` writes it for every kind, not only steps.
- Tile 0 from `trau`, `trav`, `scau`, `scav`, `unk0A`, `unk0C`, `unk0E`
  and `unk10`; tile 1 from `scrollu`, `scrollv`, `unk38`, `unk3A`.
- `PRIM_LOD_FRAC` is `lfrac * 255` (or `(lfrac - trunc) * 256` under
  `FRAC`).

`gcAddMObjForDObj` (`objman.c:1321-1328`) starts `lfrac` at
`prim_l / 255` and both texture ids and `palette_id` at 0.

`gcParseMObjMatAnimJoint` (`objanim.c:840-1110`):

- `SetTargetRate` writes `rate_target` only.
- `SetValAfter(Block)` zeroes `rate_target`; `SetExtValAfter(Block)` does not.
- `SetVal(Block)` sets `rate_base` only for a nonzero payload and leaves
  `length_invert` alone.

## Method

`romtool matcolors` now checks every entry's resolvers each frame. It feeds
the decomp draw path from the reference's tracks and from `MObjSub` fields
it reads from the ROM itself, and compares:

- `resolved_texture` with `textures[texture_id_curr]`;
- `resolved_palette` with `first_palette + (s32)palette_id`;
- `resolved_uv` field for field: live and rest `Tra*`/`Sca*`, form and
  tile parameters;
- `resolved_lod_blend`: next texture, `PRIM_LOD_FRAC` byte and tile-1
  window.

Static checks: equal `sprites[]` pointers must share a packed texture, and
distinct ones must not. Each packed palette must hold the ROM palette's
RGBA5551 entries. `EffectMaterialAnimator`, started at frame 0, must
resolve like the stage player on every tick.

## Findings

1. **`PaletteID` linear hold.** Entries 64 and 65 (file 114, scripts
   `0x56F4` and `0x55A8`) open with `SetValBlock(PaletteID, 0)` for 90
   frames, then step through 18 palettes. The decomp draws `palettes[0]`
   for those 90 frames. `resolved_palette` accepted only stepped tracks,
   so it returned `None` and the primitive kept its packed palette: 180
   mismatching frames.
2. **Stale pack.** Entry 91 (file 347, script `0x1A90`) steps
   `TextureIDCurrent` to 1 on frames 1-2, then to 0. The packer sizes the
   sprite table from its own `MaterialJoint` replay. Under the old `+2`
   phase that replay never saw index 1, so the committed v34 pack
   (`a4072881…`) held one texture and the runtime clamped to it: 2
   mismatching frames. RE-324 recorded the pack as unchanged, but the pack
   was not rebuilt after the phase fix. A pack built by RE-324's own code
   gains the second texture. That is the only table difference:
   `textures[]` grows from `[1583]` to `[1583, 1584]`, and later texture
   indices shift by one.
3. **Rounding.** `EffectMaterialAnimator` rounded `TextureIDCurrent` and
   both players rounded `PaletteID`; the decomp truncates both. Every ROM
   value is a whole number, so the ROM replay cannot see this difference.

## Change

- One `resolve_palette` and one `resolve_texture` serve both players:
  any live kind, truncating, clamped to the entry's table.
- `MaterialJoint::apply` follows the decomp for `SetTargetRate`, for
  `rate_target` on material steps, and for `rate_base`/`length_invert` on
  linear keys.
- Pack rebuilt: v34, 22,231,104 bytes (+5,424), SHA-256
  `59cc6d36d58819b195a4df4aa0cac11aef93ccdb82788ca6eb4d20167bed3cbe`. The
  `MaterialJoint` fixes do not change it: a build from RE-324's code
  produces the same bytes.

## Limits

- The check compares resolver inputs (index, window fields, fraction). It
  does not check `UvAffine`'s conversion to GE scale and offset, or
  texture pixels.
- With the texture track unset, the runtime draws the packed texture. The
  check does not confirm that texture is `sprites[0]`.
- `MObjSub.unk10 == 1` tile-0 halving is not modelled. The check reports
  it on any moving tile-0 window and reported none.
- Whether file 114's packed palette already equals `palettes[0]`, which
  would make finding 1 invisible, is not measured.
- No physical-PSP capture.
