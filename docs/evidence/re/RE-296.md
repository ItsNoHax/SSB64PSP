# RE-296 — First physical-PSP confirmation of `psp-game`; found and fixed a `psp/` build break and an `OutOfMemory` pack-load failure under PSPLink

Status: COMPLETE
Topics: front-end, hardware, memory, toolchain, visual-regression
Relevant files: psp-game/src/main.rs, psp/src/play.rs, docs/evidence/re/RE-255.md, docs/evidence/re/RE-256.md, docs/evidence/re/RE-259.md, docs/evidence/re/RE-260.md

**Question.** `STATUS.md` named physical-PSP confirmation of `psp-game` as
entirely outstanding, now more worth doing with RE-295's pixel-confirmed
jab/jump combat loop to validate. This session ran that confirmation.

**Bug found #1 — `psp/` no longer builds.** Before touching hardware, a
sanity build of `psp/` (needed as a same-session control, below) failed:
`cargo psp --release --features regression_capture` in `psp/` hit
`error[E0004]: non-exhaustive patterns: Status::Attack11 not covered` at
`psp/src/play.rs:379`, `status_name()`'s exhaustive match over
`ssb_game::status::Status`. RE-294 (prior session, committed this session as
part of `a357cdf`) added `Status::Attack11` to the shared `crates/ssb-game`
enum for Mario's jab; `psp/`'s own debug-overlay label match was never
updated, breaking its build even though no file under `psp/` was edited —
exactly the shared-crate-break `AGENTS.md`'s F1 carve-out (criterion 1:
"the existing `psp/` crate's build ... are unmodified by this work") exists
to catch. **Fixed**: added `Attack11 => "jab1    "` to the match, mirroring
the fixed-width label style of the surrounding arms. `psp/` builds again.

**Bug found #2 — `psp-game` fails `LoadError::OutOfMemory` under PSPLink's
`ldstart`.** First hardware attempt: PSP Slim, firmware 6.61, ARK/Infinity
CFW, PSPLink v3.2.1, `054c:01c9` USB, `usbhostfs_pc -v "$PWD"` from the repo
root, `pspsh -e ldstart host0:/psp-game/target/mipsel-sony-psp/release/
ssb64-psp-game.prx` (built `--release --features regression_capture`, pack
symlinked beside the PRX per the `psp-hardware` Skill's documented
convention). No exception (`exlist` empty, `main_thread` alive), but the
native `scrshot` capture was a single flat colour across all 130,560
pixels — Training's pack-load-failure fallback, not the real scene.

Root-caused, not just diagnosed: extended `psp-game/src/main.rs`'s existing
`BG_TRAINING_NO_PACK` pixel-provable-failure convention
(`plans/gameplay/F1.md`'s "Scene loading" section) to distinguish *why*
instead of one flat colour for every failure — `BG_TRAINING_PACK_EMPTY`,
`BG_TRAINING_OUT_OF_MEMORY`, `BG_TRAINING_SHORT_READ` (`assets::LoadError`'s
other three variants) and `BG_TRAINING_PARSE_FAILED` (`ssb_rom::pack::
PackError`), computed once in `run()` and threaded into `draw_training`.
Rebuilding and recapturing under the same `ldstart` session showed a
uniform `(120, 0, 160)` — `BG_TRAINING_OUT_OF_MEMORY` exactly: the pack
*opened and read its size* but `AlignedBuf::new` could not allocate the
buffer.

**Not `psp-game`-specific.** `pspsh -e meminfo` on the live session showed
partition 2 (the user heap) at `23,332,352`-`23,594,496` bytes free — under
the pack's `29,255,664`-byte size — regardless of `psp-game/Psp.toml`'s
`memsize = 1` (RE-255/RE-291), because it is not in effect. Controlled
comparison on the same hardware/session: freshly built `psp/`
(`--features regression_capture`, same fixed pack) via the identical
`ldstart` path fell back to the **same** placeholder RE-255 already named
(the M1 fallback tetrahedron) instead of Dream Land — proving both crates
hit the identical ceiling under `ldstart`, not a `psp-game` regression.

This matches this project's own prior findings, re-read carefully: RE-256
showed `MEMSIZE` only takes effect from `PARAM.SFO` on a proper installed-
directory boot (`PSP_PBP_DIRECTORY`), never a loose/PRX load, and RE-259/
RE-260's own physical `MEMSIZE` proof required the user to launch an
*installed* `ms0:/PSP/GAME/ssb64/EBOOT.PBP` from the XMB — PSPLink's
`ldstart` was only ever used there to stage files, never to exercise the
memory-dependent boot itself. This session's `ldstart`-based attempt used
the wrong mechanism for a pack this size, not a new defect.

**Resolution.** Staged `psp-game`'s EBOOT (with its already-fixed pack
symlink resolved to a real copy) at `ms0:/PSP/GAME/ssb64game/EBOOT.PBP` and
`ssb64.pak` via PSPLink's own `ms0:` file commands (no re-mount needed).
The user enabled extended memory on the device and re-checked: `meminfo`
now shows partition 2 at `53,460,992` bytes free. Re-ran the identical
`ldstart` sequence:

* `exlist` empty, `main_thread` alive — zero exceptions.
* Native `scrshot` (`f16bee1c...` PRX SHA-256, pack unchanged
  `256d7661bb1dc7266ea8928bc8f341cbb121f83c330a4d3821466192ea42c17d`, EBOOT
  SHA-256 `53047d31...`) shows the real Training scene: both Marios
  standing together on Dream Land's side platform under the tree, in melee
  range, the same close battle-camera framing RE-295's PPSSPP-headless
  capture recorded — the first real, on-device evidence of `psp-game`'s
  pack-loaded content, not a placeholder.
* Quantitative check against RE-295's PPSSPP golden
  (`docs/images/re295-jab-connects-dummy-platform.png`, box-downsampled
  960x544 to the hardware's native 480x272): 44,189/130,560 pixels (33.8%)
  show any difference (expected — real-GE-vs-software-rasterizer
  antialiasing, this project's established noise floor, RE-203/RE-282), but
  only 1,045 (0.8%) exceed a 30-level channel-sum threshold, maximum
  channel-sum difference 626/765 — the same order this project's prior
  hardware/PPSSPP comparisons already accept (RE-282: 0.27%), not a new
  defect. No PSPLink diagnostic-overlay text is visible in this capture (no
  region excluded from the comparison above).

**Conclusion.** `psp-game`'s pack-loaded Training scene, including RE-295's
jump-then-jab schedule, is now confirmed on real PSP hardware, not only
PPSSPP — closing the "no physical-PSP evidence for `psp-game`" gap
`STATUS.md` had carried since RE-289. Two real bugs were found and fixed in
the process (`psp/`'s stale exhaustive match; the pixel-indistinguishable
generic pack-failure colour), both now committed. The `OutOfMemory` failure
itself was an environment/mechanism issue (device not in extended-memory
mode, plus `ldstart` never honoring `MEMSIZE` regardless), not a code
defect — resolved by using the installed-EBOOT + extended-memory path this
project's own `MEMSIZE` evidence (RE-259/RE-260) already established as the
only mechanism that applies, rather than inventing a new one.

**Confidence: high.** Zero exceptions, a real (not fallback) scene
matching the PPSSPP golden within this project's established hardware
noise floor, and a same-session controlled comparison (`psp/` failing
identically under the pre-fix condition) ruling out a `psp-game`-specific
cause for the original failure.
