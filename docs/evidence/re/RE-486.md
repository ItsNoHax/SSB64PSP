# RE-486 — The running GE costs the CPU 3 ms of memory stalls; stall updates cost nothing

Status: COMPLETE (PSP-2000, 6.61 ARK, PSPLink v3.2.1, one `profile_hw,capture_scene_file,no_audio` build of `vs4@2400` at `2960b58` against rust-psp `a1c3d86`, from `ms0:/PSP/GAME/ssb64/` with pack v108, `profile_hw.txt` = `frame`, reports 1–18, one run per setting)
Topics: performance, hardware, psp-ge
Relevant files: `psp-runtime/src/gu.rs`

## Question

rust-psp's GU makes a `sceGeListUpdateStallAddr` system call after every
draw and every `sceGuGetMemory` in the direct context (RE-485's open
item). Would updating the stall address every few draws, or only at
`sceGuFinish`, save CPU time, and how much CPU–GE overlap would it give
up?

## Change measured

A rust-psp experiment (local fork branch `stall-interval-experiment`,
commit `a1c3d86`; not pushed, not used by the game) reads `gu_stall.txt`
beside the executable at the first `sceGuStart`: the number of draws
between stall updates. 1 is PSPSDK's behaviour. For any other value
`sceGuGetMemory` makes no stall update, and 0 updates only at
`sceGuFinish` and list calls, so the GE starts the frame's list once the
CPU has written all of it. One PRX (SHA-256 prefix `581cdfc579b737ca`)
ran every setting; nothing ran in an exception.

## Results

`vs4@2400`, Mario and three CPUs on Dream Land, without audio. Spans in
ms, counters per frame; `ge` is the wait in `sceGuSync` after
`sceGuFinish`:

- **The stall updates are cheap.** Every 2 to 16 draws saves 0.1–0.25 ms
  of CPU, inside the two baseline runs' spread (40.5–40.9 FPS). Not worth
  a fork change.
- **The running GE slows the CPU.** With the GE held back until
  `sceGuFinish`, the CPU's frame drops by 3.0 ms, and the drop is memory
  stall: 917,000 fewer stall cycles a frame (2.75 ms at 333 MHz), with
  unchanged I- and D-cache misses. The same misses cost more while the GE
  reads main memory: GE and CPU share the bus, and RE-481's high stall per
  miss in the draw is this contention.
- **Overlap still wins.** Finish-only then waits 4.8 ms for the GE, so the
  frame is 1.6 FPS slower; four-player VS has at least ~4.8 ms of GE work
  that now overlaps the CPU.

The stall update stays per draw (PSPSDK).

## Consequences

- Main-memory traffic from the GE (textures, which the runtime samples
  from main RAM; the display list and its `sceGuGetMemory` vertex blocks)
  costs CPU time, not only GE time. Cutting it, through
  texture residency in VRAM or smaller texture formats, is measurable on
  the CPU through the memory-stall counter.
- Double-buffered lists (CPU on frame N+1 while the GE draws frame N)
  would not remove this contention.
