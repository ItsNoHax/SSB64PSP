# RE-475 — The black screen from the XMB, and loading each scene's archive files

Status: IMPLEMENTED (boot logs of an XMB and a PSPLink launch on a PSP-2000; decomp file lists; golden matrix, A/B captures of every other capture scene and the How to Play trace under PPSSPPHeadless, with and without memory ballast; PSPLink attract-loop runs on the PSP-2000 at the XMB budget and at 46 MB; the XMB launch of this build is the user's check)
Topics: hardware, memory, pack, platform, performance, loading
Relevant files: `crates/ssb-rom/src/{pack,residency,scene_roots,menu_pack}.rs`, `psp-runtime/src/{assets,scene_files,memory,gu,movie}.rs`, `psp-game/src/{main,scene_load,boot_log,campaign,campaign_screen,menus_screen,opening_screen,demo_screen}.rs`, `psp-game/Cargo.toml`, `tools/romtool/src/main.rs`, `tools/golden.sh`, `tools/run-ppsspp-headless.sh`, `refs/ssb-decomp-re/src/lb/lbreloc.c`, `refs/ssb-decomp-re/src/sc/scmanager.c`, `refs/ssb-decomp-re/src/ft/ftmanager.c`, `refs/ssb-decomp-re/src/mp/mpcollision.c`

## Question

The production game boots through PSPLink but shows a black screen when
started from the XMB; HOME works, and exiting then hangs. Why, and how
should the game hold its data?

## Hardware and builds

- PSP-2000 (Slim), 6.61 ARK, PSPLink v3.2.1. ARK `SETTINGS.TXT`:
  `highmem:forcemax`, `mscache:4k`, `infernocache:lru`; `PLUGINS.TXT`:
  `homebrew, leda.prx, on`.
- Before: pack v106 (46,908,848 bytes, loaded whole) and
  `ssb64-menus.pak` (13,163,676 bytes, one pack per menu scene); EBOOT
  with debug info.
- After: pack v107 (59,656,048 bytes, SHA-256 `487bfd8a…8036`; 5,478,176
  resident), EBOOT 4,188,974 bytes without debug info (`boot_log`, SHA-256
  `4248b82d…4b45`), installed in `ms0:/PSP/GAME/ssb64/` with `ssb64-menus.pak`
  removed and the user's `ssb64.sav` restored byte for byte after the
  test runs (the title counts boots into it).

## Findings

### The black screen

The boot log (`boot_log` feature) of the two launches:

| Stage | PSPLink: free / largest block | XMB: free / largest block |
|---|---:|---:|
| `psp_main` | 52,086,016 | 47,891,712 |
| after the pack | 5,435,136 / 5,177,088 | 1,240,832 / 982,784 |
| frame 60 | 2,570,496 | (never reached) |

From the XMB the game starts with exactly 4 MiB (4,194,304 bytes) less
user memory. The whole pack left 1.2 MB, the log stops after the save
loads, before the first frame: the first scene's allocations fail. `psp`'s
global allocator returns null, and its `#[alloc_error_handler]` is
`loop { spin_loop() }`, so the main thread spins forever at full priority
with the last frame (black) on screen; the exit callback cannot finish.

### The N64's loading model

The decomp (handoff note summarised here): every scene's `FuncStart`
calls `lbRelocInitSetup`, which forgets every file, and
`syTaskmanStartTask` resets the general heap, so no archive file survives
a scene change. A scene loads its `dXXFileIDs` with
`lbRelocLoadFilesListed`, the stage's map file
(`mpCollisionInitGroundData`), the battle interface (`dGMCommonFileIDs`),
effects, items, the fighter manager's files and each fighter's main file
with `lbRelocGetExternHeapFile`; loading a file loads its extern closure
(`lbRelocLoadAndRelocFile`). Fighter figatrees are read per status change
into a per-fighter heap (`ftMainSetStatus`). `ssb_rom::scene_roots` holds
these lists, cited per scene.

### The port's model (D-046)

The pack groups its blob by archive file; the game holds the tables and a
shared region (5.5 MB) and loads each scene's files and their closure at
the scene's start. See D-046 for the deviations. Hooks: `go_scene` and
`start_scene` (every `MScene`, the opening's scenes included), the
Training select, the stage select, the VS results, the 1P manager's
presentation scenes (`campaign_screen`) and `Session::enter` for every
battle. A battle that is its scene (an opening fight, How to Play, the
title demo, the 1P Game's stages) keeps the scene's files; a VS or
Training battle drops its selects'.

`capture_scene_file,headless_capture,profile`, average CPU per frame over
the reports after the first:

| Scene | Before | After |
|---|---:|---:|
| `vs4@4000` | 4.56 ms | 4.71 ms |
| `oneprace@3000` | 3.82 ms | 4.01 ms |
| `onepzako@3600` | 3.26 ms | 3.56 ms |

is now 0.2–0.35 s under PPSSPP (its emulated reads), up from 15 ms.

### The PSP-2000 runs

| Run (PSPLink, `boot_log,memory_ballast`) | Result |
|---|---|
| Attract loop, 47,891,712 bytes free at boot, 6 minutes | The N64 logo, all 19 opening scenes, the title, How to Play and the battles; lowest free 29.97 MB (largest block). An FPU exception (IUV) in `hit_pass` came after How to Play (below) |
| Attract loop, 46,000,000 bytes free, 7 minutes, with the fix | Three passes of the logo, opening, title, How to Play, Characters (all twelve fighters, 10.2 MB) and the title demo battle; no exception; lowest free 23.85 MB (the title demo's battle while Characters' files were still held for one frame); no growth between passes (the N64 logo's scene: 27.4, 27.0, 27.8, 27.9 MB free) |
| How to Play (`explain@4460`), before (`c81fee4`, pack v106) and this batch before the fix | No exception |
| The shipping PRX (`boot_log`), no ballast | Boots to the opening |

The FPU exception: EPC `0x088B1320`, module offset `0xAD320`
(`ssb64_psp_game::hit_pass`), `c.olt.s $f0, $f31` with `$f31` a NaN:
`ssb_game::grab::nearest_catch` kept its nearest distance in an `Option`,
and LLVM compared an empty `Option`'s uninitialised `f32` before testing
for `None`, the speculation RE-469 met in the CPU's input and the
particles. PSPLink enables the invalid-operation trap. The distance now
starts at infinity; the logic is unchanged (the first catchable fighter
is taken, then a strictly nearer one).

  the remaining ones are listed in `TODO.md`.

## Deviations

D-046 lists them: whole figatree sets per battle instead of one per
status, resident material-animation files, files two scenes share kept
rather than reloaded, and the last scene's files held until the frame
that starts the next one ends.
