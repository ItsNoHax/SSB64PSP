# RE-485 — A cached display list is slower than the uncached one

Status: COMPLETE (PSP-2000, 6.61 ARK, PSPLink v3.2.1, `profile_hw,capture_scene_file,no_audio` builds of `vs4@2400` at `91323e8` from `ms0:/PSP/GAME/ssb64/` with pack v108, `profile_hw.txt` = `frame`, reports 1–18, one run per build)
Topics: performance, hardware, toolchain, psp-ge
Relevant files: `psp-runtime/src/gu.rs`

## Question

RE-481 counted ~20,300 uncached stores a frame in four-player VS, nearly
all of them the display list: rust-psp's `sceGuStart` writes commands
through the uncached alias (`| 0x4000_0000`), and `sceGuGetMemory`
vertices land in the same list. The draw's memory stall per miss (100–130
cycles) is higher than the update's (63–70). Do the uncached writes stall
on the write buffer, and would a cached list written back for the GE be
faster?

## Change measured

A rust-psp feature (`cached-list`, kept on the local fork branch
`cached-list-experiment`, commit `4af2d7e`; not pushed, not used by the
game):

- `sceGuStart` in the direct context keeps the list's cached address.
- The direct list runs while it is being built: each
  `sceGeListUpdateStallAddr` (every draw, every `sceGuGetMemory`) lets the
  GE read further. Before each one the list's lines from the last
  writeback up to the new stall address are written back: whole lines with
  `cache 0x1b` (Hit Writeback Invalidate), the last partial line with
  `cache 0x1a` (Hit Writeback), so the commands that follow it still hit.
  `sceGuGetMemory` writes back only up to its jump: the caller fills the
  block afterwards, and the next stall update writes it back before any
  draw that reads it can run.
- `cached-list-cde` also claims each new list line with `cache 0x18`
  (Create Dirty Exclusive), so a line is not read from memory before
  being written: a check on every command, and a loop over the lines of
  each `sceGuGetMemory` block.
- The `cache` instruction runs in user mode on the PSP (commercial games
  use it; PPSSPP treats it as a no-op). LLVM's MIPS II target rejects the
  mnemonic, so the fork emits it as `.word` with the address in `$a0`.

Screenshots of all three builds render correctly; nothing ran in an
exception.

## Results

`vs4@2400`, Mario and three CPUs on Dream Land, without audio. Spans in
ms, counters per frame:

| `91323e8` | 41.23 | 17.75 | 4.23 | 16.52 | 3.88 | 4.95 | 1.53 | 0.82 | 7,005,728 | 3,688,526 | 17,236 | 25,912 | 16,263 | 4,287 |
| `cached-list` | 39.75 | 18.68 | 4.64 | 16.99 | 4.21 | 5.00 | 1.55 | 1.24 | 7,317,194 | 3,954,150 | 367 | 29,470 | 17,580 | 5,492 |
| `cached-list-cde` | 38.72 | 19.98 | 4.17 | 18.18 | 5.07 | 5.31 | 1.85 | 1.42 | 7,746,928 | 4,304,024 | 360 | 34,090 | 17,054 | 5,658 |

Draw includes the vblank wait. PRX SHA-256 prefixes: `91323e8`
`50163deecaf13ac4`, `cached-list` `3b1d968738f66916`, `cached-list-cde`
`28fa5d6be63f2f98`. The baseline reproduces RE-484's 41.0 FPS and
17.77 ms.

- **The uncached writes are cheap.** Taking ~16,900 uncached stores a
  frame off the list removes no measurable stall: the write buffer absorbs
  the sequential stores. RE-481's higher stall per miss in the draw is
  not the list.
- **The cached list costs more than it saves.** Per frame it adds 1,300
  D-cache misses (the list's lines read before they are written) and
  1,200 writebacks, which evict game data; the writeback loop at each
  stall update moves `submit` from 0.82 to 1.24 ms. The I-cache misses
  rise by 3,600: `send_command_i` and the stall update are inlined into
  every GU call, and the draw is bound by I-cache misses already
  (RE-481, RE-482).
- **Create Dirty Exclusive is worse still.** It saves no D-cache misses
  (17,054 against 17,580), and its check on every command adds another
  4,600 I-cache misses: 1.2 FPS below the plain cached list.

The display list stays uncached.

## Open

- Each draw and each `sceGuGetMemory` makes a `sceGeListUpdateStallAddr`
  system call. Updating the stall address less often (every few draws,
  and at `sceGuFinish`) would cut those calls without changing what the
  CPU writes. That costs some CPU–GE overlap, so measure it.
