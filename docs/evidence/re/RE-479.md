## Question

produce the N64's output, and what does it cost on a PSP-2000?

The reverb's low-pass section matches the capture only if it leaves its
output untouched; with the filter applied the correlation is 0.988. The
port follows the capture (`reverb::APPLY_LOWPASS`); the capture is HLE,
so real hardware is unverified. The near-full-scale samples are not
located: every per-command clamp matches rsp-hle's. `audio::n64ref`
replays both clips and compares PCM hashes.

- Audio costs 3 FPS in the opening and 1.6 in VS. Four-player VS
  runs at 40 FPS without audio: the game thread, not audio, holds it
  under 60.
- The production EBOOT on the Memory Stick (`d9bd863a…39f2`) is the
  same build; its PRX, started from that directory under PSPLink with no
  input, played the opening, title, How to Play, Characters and the demo
  battles for four minutes without an exception.

- One voice's 184-sample pull went from 176 to 72 µs (ADPCM 23, resample
  20, envelope mixer 27). The custom reverb went from 202 to 49 ms/s; in
  VS it is most of the audio thread.
- The optimised path is bit-identical to the reference Rust on the PSP
  itself (`audio_selftest`: four PCM hashes of a fixed 29 s scenario).
- Game-thread sound calls cost at most 18 µs a frame.
- PPSSPP (instruction-counted) shows about a third to a half of the PSP's
  cost: 44–95 ms/s in the title, mode select and VS, no underruns.
- The Allegrex has one multiply in flight with a 5–7 cycle latency;
  chained `madd` costs 3–4 cycles. The per-sample loops are now bound by
  their multiplies (envelope mixer 4, resample 4, ADPCM about 5.5,
  reverb 3 per section).
- Memory: the audio section is 4,428,816 bytes, resident from boot; the
  synth's state is under 100 KB, the thread's stack 64 KiB (about 63 KB
  free at the deepest).
  PPSSPP, attract loop (`opening@5400`) at the XMB's 47,891,712 bytes:
  lowest free 23.1 MB (RE-476: 24.9 MB), no underrun.

What made it faster: rust-psp's `memcpy`, `memmove` and `memset` copy one
byte per iteration (about 6 cycles a byte), and every `copy_from_slice`,
`fill` and zeroed array goes through them; the audio paths use word copies
(`audio::mem`). Reverb sections run in place on the delay line in one pass
instead of eight load, mix and save passes. Envelope ramps are computed
once per call. Allegrex kernels (`dsp::allegrex`: `min`/`max` clamps,
`madd` chains) do the mixer, reverb, ADPCM, resampler and envelope mixer.

## PSP and PPSSPP behaviour found on the way

- The SRC channel accepts 512-sample blocks at 32 kHz on a PSP-2000
  (6.61 ARK).
- A blocking output returns when the previous buffer has finished, so the
  buffer passed is still playing: three rotating buffers. PPSSPP copies
  the samples at the call, so reusing a buffer early is invisible there.
- PPSSPP never advances a thread's run clocks; audio cost there comes from
  `sceKernelGetSystemTimeLow` spans. PPSSPPHeadless forces sound off and
  ignores `--appendconfig`; the `audio_dump` feature writes the PCM
  instead.
- rust-psp's `sceKernelCreateSema` binding passes its fifth argument
  wrongly (PPSSPP shows `deadbeef`); the call goes through rust-psp's `i5`
  trampoline.
- A PSPLink `kill` of a running `profile` build hung PSPLink once (the
  device re-enumerated, the shell never answered again until PSPLink was
  restarted); the game had been running normally. A bare `reset` unloads
  the game without that hang.
- A 10 KB initialised static with 64-byte alignment in `.data` corrupted
  memory under PPSSPP in every audio build; the same state allocated at
  boot does not. The cause is not found; avoid over-aligned initialised
  statics.

## Batch 64a: microcode-exact Q15 rounding

- Ground truth: the n_aspMain microcode (disassembled), not rsp-hle. MIXER, ENVMIXER and RESAMPLE re-derived from it; no POLEF or low-pass command exists.
- Mix and envmix: `clamp16((o*0x7FFF + i*g + 0x4000) >> 15)` (`dsp::mixq`); the output is scaled by 0x7FFF, so gain 0 is not the identity. n_env issues the reverb aMix only for a nonzero coefficient. Resample: each tap's vmulf rounds on its own, then two saturating adds. Envmix lanes and ramps follow the microcode.
- Host and Allegrex kernels updated. Allegrex resample omits the pair clamps (ROM table max pair 29414; `taps_fit` test).
- Port vs two LLE RSP cores (parallel, cxd4), whole windows: b_menu 914,848 values and c_attract 3,324,512 values, 0 differing samples (HEAD: 81% and 94.7% differ). cxd4 attract checked for its first 3,112 frames.
- Same-frame voice order is observable with per-mix rounding: LLE needs FGM 429 before 42, and 175 before 31. The port's voice list mirrors `alLink` head insert.
- `audio::n64ref` regenerated from LLE: PREROLL 52, calls in LLE frames, `short_runs`. Reference hashes: b_menu `0xd5e2f3238581c901`, c_attract `0xf16c3088ce8a83eb`.
- PPSSPP cost per 552-sample frame, 16 voices: 2387 us to 3038 us (+651 us; 13.8% to 17.6% of real time). PSP-2000 cost unmeasured (PLAN "Audio cost").
- Harness copies: `~/ppsspp-test/b64a/lle_harness/`; raw captures stay in `~/ppsspp-test/b64a/` (never committed).

## Batch 156: exact VFPU reverb (PSP-2000)

- Audio on vs `no_audio`, game-thread busy, 2 rounds: vs4 +1.84 ms, intro +0.45, battle +2.32, Zebes +0.72, opening +1.56, Comets +3.53, Fall +3.30, `vs4@2170` r12 +3.03, r18 +1.97, r14 +2.48.
- Audio thread busy (ms/s, profile build): Zebes 74.9, vs4 107.7, elec 121.3, 1P 148.9, boss 193.6, opening 210.9. Reverb 56 in every scene; its section loop 50.7.
- Change: `reverb::SectionKernel` hook; `psp-runtime/src/reverb_vfpu.rs` runs the plain sections on the VFPU (8 samples per step, one list-scheduled body per nonzero-coefficient mask), written by `tools/audio/gen_reverb_vfpu.py` (`--check`). Delay line and `Dmem` 16-byte aligned; unaligned or non-multiple-of-8 windows keep the integer path.
- Exactness: Q15 operands split into 8-bit halves, so every `f32` intermediate is exact and the result does not depend on the rounding mode (`reverb::vfpu_model` doc). Host: `mix_matches_mixq_for_every_input`, `mix_matches_mixq_random` (4M), `kernel_matches_section`, `pcm_hash_golden_vfpu_model`. PSP `audio_selftest`: all four hashes equal the integer path's; control (`h = 0.4999`) changes all four.
- Rejected: magic-number floor and `vsat` clamp (not exact over the range); no FMA on the VFPU; unscheduled kernel (reverb 50.2 ms/s); a call per step (41.7).
- VFPU timing (probe): about one independent op per cycle, dependent latency 5, `sv.q` 7.2 cycles; a step costs ~230 cycles vs ~137 modelled (delay-line D-cache misses suspected, unchecked).
- Result: reverb 55.9 -> 39.6 ms/s; audio busy vs4 107.7 -> 91.6, opening 210.9 -> 192.1, elec 121.3 -> 105.2. Selftest µs/frame per segment 3301/3688/4002/1188 -> 3024/3407/3747/894.
- Game-thread busy, 4 interleaved rounds (HEAD -> batch): vs4 15.90 -> 15.82, intro 14.79 -> 14.56, battle 14.61 -> 14.53, Zebes 10.76 -> 10.67, opening 8.77 -> 8.75, Comets 15.37 -> 15.23, Fall 16.21 -> 16.06, r12 18.88 -> 18.78, r18 17.04 -> 16.93, r14 17.72 -> 17.60.
- Cost: PSP-2000 free -40,960 B; PPSSPP goldens boot_free and low_free -65,280 B (lowest low_free 37,485,824). Real code +3,268 B; +70,348 B of link-pin holes (grown pinned functions moved past the pins; `link-pins.txt` not rewritten). Accepted by the owner.

## Batch 157: Media Engine probe (PSP-2000, ARK 6.61)

- Bring-up from a user PRX: `kcall.prx` (mcidclan me-core-mapper) loaded from host0, `kcall_2(k_me_reset, 0x80000000)` 47-49 µs; ME at `me_entry` 0.53-0.71 ms after reset; ME cpuid 1. libme-core.a is eabi32: its reset handler and setup ported to Rust + `global_asm!`. `kinit` not called (its sysevent hook crashes the next suspend once the module is unloaded).
- Exactness: `ssb-engine` ADPCM, resample, envmix on the ME vs SC, 16 voices, 10,000 pulls x 3 runs, hash of whole `Dmem` + voice states per pull: 0 mismatches; final hash equal on ME, SC and host x86-64. Control (one input bit) gives the host-predicted 8 mismatches.
- Speed per synthetic pull (2000 pulls, best of 3): SC 111.3-112.6 µs; ME 110.07 (no cache ops), 112.14 (per-pull cache ops), 115.76 (SC streaming memory meanwhile). The ME runs at SC speed at 333/333/166.
- Mailbox round trip: 1.9-2.2 µs (tight ME poll), 3.0-3.2 (64-nop delay), 5.2-5.4 (256). Cache per 184-sample pull: ME 2.07 µs; SC inline writeback 448 B 0.082 µs, inline wb-inv 1.5 KB 0.53 µs; syscall writeback 0.59 µs, invalidate 0.92-0.97 µs.
- SC slowdown: ME working, SC pulls +0.1%, memory stream +1.9%. ME idle polling the uncached mailbox tightly: stream +10.8%; with 64/256/1024 nops between polls +3.3/+0.88/+0.28%.
- The ME has no readable clock (CP0 Count does not advance); times are SC wall clock.
- Not tested: sleep/wake (needs a person; suspend resets the ME), PPSSPP's handling of `k_me_reset`'s MMIO writes, `sceAudioSRCOutputBlocking` while the ME is ours.
- rust-psp gaps: no kernel-mode module or kcall support, no ME support, no inline dcache invalidate, no CP0 accessors; `asm!` needs `asm_experimental_arch` and LLVM rejects `cache` (encoded as `.word`).
- Probe crate, host checker and logs: `~/ppsspp-test/b157/` (never committed).

## Batch 159: DSP executor on the Media Engine (PSP-2000, ARK 6.61)

- Split: the control pass (sequencer, FGM, synth parameters, voice allocation, loop bookkeeping) records a `FrameList` (`ssb_engine::audio::exec`: 256 ops, 12 KiB arena, 64-byte aligned); one executor `Dsp` (owns `Dmem`, per-voice DSP state, reverb `Fx`) runs it on the SC, the ME or the host. Control pass about 10% of the audio thread.
- SC-only cost of the split (PPSSPP, fallback): +0.01 to +0.21 ms game-thread busy (battle +0.21); not a build-path artifact (HEAD from a worktree matches), relinking does not remove it.
- `psp_runtime::me`: `bring_up()` loads `kcall.prx` (game dir, then host0) and resets the ME to our handler; ME up within 5 ms or SC path. Per audio frame: control pass under the audio lock, writeback of the list, one uncached mailbox post; SC waits with `sceKernelDelayThread` then 100 µs polls; ME runs `Dsp::run_frame` (integer reverb; no VFPU on the ME), writes back its D-cache, ACKs. ME idle loop: 256 nops between polls.
- Watchdog: no ACK within 20 ms → SC path for that frame, `bring_up()` again after 120 frames, SC for good after 3 failures. PPSSPP (`kemulator:` devctl) never starts the ME.
- Deviations: ME FCR31 = 0 (FP exceptions masked; the DSP is integer); effect and reverb-kernel changes applied at the next frame start; ME time is the SC's wait (the ME has no readable clock: 0xbc600000 reads 0).
- Exactness: host `frame_list_equals_direct` (list limits 1, 7, capacity), streamed golden via frame lists (control: broken arena rebase fails); PSP `audio_selftest` on the ME (1,680 lists, 0 fallbacks) gives the four HEAD hashes; control (one PCM sample flipped on the ME) fails seg3. Goldens 286/286 (SC path).
- Audio thread (profile builds, ms/s): SC busy opening 168.7 -> 27.0, vs4 87.1 -> 14.5; ME busy (SC wait) 184.8 and 98.2 (18%, 10% of the ME). Opening 39 reports (~160 s): 0 underruns, 0 fallbacks, 0 resets; SRC output 62.3-62.9 blocks/s.
- Game-thread busy, 4 interleaved rounds (HEAD -> ME): vs4 15.82 -> 14.78, intro 14.56 -> 13.97, battle 14.52 -> 13.19, Zebes 10.67 -> 10.37, opening 8.76 -> 7.70, Comets 15.22 -> 12.76, Fall 16.09 -> 13.87, r12 18.80 -> 16.95, r18 16.92 -> 15.95, r14 17.60 -> 16.21. 48 of 48 runs without exceptions.
- Cost: free memory -90,624 B (profile build). Accepted by the owner.
- Untested: sleep/wake on hardware (needs a person), PSP-1000, PPSSPP's handling of `k_me_reset` (never called there).


## Batch 160: own kernel module (PSP-2000, ARK 6.61)

- `psp-kcall/`: `no_std` kernel-mode module `ssb64_kcall` (2,444 B PRX); `module_start` calls the function address passed as its argument (`k_me_reset`), returns 1 (`SCE_KERNEL_NO_RESIDENT`). Built by `psp-runtime/build.rs` (1.98.0, build-std, `prxgen`) and embedded in the game; replaces the third-party `kcall.prx`.
- Loading: `sceKernelLoadModuleBufferUsbWlan` from the user-mode game returns 0x80020149 (illegal permission call) on the PSP-2000; `sceKernelLoadModule` of a file loads it. The game writes the embedded module to `ssb64_kcall.prx` in its working directory (skipped when the file already holds it), then loads and starts it. Deviation: a 2,444 B file beside the EBOOT.
- PRX layout: every `PT_LOAD` segment with file bytes must share one `p_offset - p_vaddr` distance; `prxgen` and the loader read `module_info` by it. A 64-byte aligned object in the game's `.rodata` broke it (distance 0x140 vs 0x120) and hung the PSP-2000 at `ldstart`. Guards: `tools/psp-link.py` `check_layout` (game; control: a copy with one segment shifted 0x40 fails) and `psp-runtime/build.rs` `check_layout` (module).
- PSPLink launch: `audio_selftest` on the ME gives the four HEAD hashes, 1,680 lists, 0 fallbacks, `me_kmod=0`; control (one PCM sample flipped on the ME) fails seg0.
- XMB-equivalent launch (`sctrlKernelLoadExecVSHMs2`, RE-516 launcher), no `kcall.prx` on the stick: the game wrote `ssb64_kcall.prx`, same hashes, `exec=me`, 0 fallbacks.
- Game-thread busy, 2 interleaved rounds (`kcall.prx` -> own module): vs4 14.78 -> 14.72, intro 13.98 -> 13.77, battle 13.19 -> 13.14, Zebes 10.37 -> 10.37, opening 7.70 -> 7.69, Comets 12.76 -> 12.73, Fall 13.86 -> 13.85, r12 16.94 -> 16.87, r18 15.96 -> 15.86, r14 16.22 -> 16.12.
- Cost: game image +8,192 B (one link-pad quantum).
- Unload: `pspsh modlist` 40 s into a run on the ME lists 51 modules against 50 before, the one added being `ssb64_psp_game`; `ssb64_kcall` is gone (PPSSPP keeps `NO_RESIDENT` modules).
