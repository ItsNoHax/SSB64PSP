# RE-470 — CPU performance: from 8–15 FPS to about 60 under PPSSPP

Status: COMPLETE (PPSSPP cycle-model and host measurements, golden matrix 198/198; physical-PSP after-measurements pending)
Topics: performance, hardware, animation, pack, psp-ge, framebuffer, memory, visual-regression
Relevant files: `crates/ssb-rom/src/{pack,skeleton,n64_filter,ground_obj}.rs`, `crates/ssb-engine/src/math.rs`, `crates/ssb-game/src/{fteffect,item/hit}.rs`, `crates/ssb-rom/tests/anim_lookup.rs`, `tests/golden/scenes.tsv`, `psp-runtime/src/{gu,meshdraw,profile,ending,movie}.rs`, `psp-game/src/{main,player_screen,title_opening}.rs`, `psp-asset-viewer/src/main.rs`

## Question

RE-469 measured battles at 8–15 FPS on a PSP-2000, CPU-bound, with the
game advancing one tick per drawn frame. Where does the CPU time go, and
how close to 60 FPS can the game get without changing what it does?

## Method

- **PPSSPP as a cycle model.** PPSSPP advances the PSP clock by
  instructions executed, so `sceKernelGetSystemTimeLow` under
  PPSSPPHeadless measures emulated CPU time. The `profile` build of
  `640cc91` under PPSSPP ran `vs4@4000` at 8.2 FPS against the
  PSP-2000's 8.1, and `onepgame@4000`, Bonus Practice and the VS select
  at the PSP's 11.9, 14.9 and 14.9; only the title demo ran faster (20.3
  against 15.4). Relative changes under PPSSPP are therefore a usable
  proxy; absolute hardware numbers still need the PSP.
- **A sampling profiler.** A copy of PPSSPP (`~/.cache/ssb64-ppsspp-prof`,
  not in this repository) schedules a CoreTiming event every 2,000
  emulated cycles that counts the guest `pc` and `ra`
  (`PPSSPP_GUEST_PROFILE=path`), dumped at shutdown. Symbolised against the
  ELF at load address `0x08804000` (every sample's `ra − 8` is a `jal` or
  `jalr` there, 100%; other bases score under 11%).
- **Host microbenchmarks** of the same functions (`cargo run --release`),
  which put the worst offender at 82 µs a call on the host.
- Six scenes, as RE-469's hardware table: `title@4000`, `op-jungle@1200`,
  `vs4@4000`, `onepgame@4000`, `bonuspractice@4000`, `vsplayers@4000`,
  in `capture_scene_file,profile,headless_capture` builds, which freeze
  at the tick; averages of the two-second reports from the third (past
  loading) to the freeze.

## Findings

The build settings were already right: `psp-game`'s release profile has
`opt-level = 3`, `lto = true` and one codegen unit, without overflow
checks or debug assertions (`debug = true` only keeps symbols), and the
`mipsel-sony-psp` target is hard single-float. The target CPU stays
`mips2`: no LLVM CPU matches the Allegrex, and a richer one could emit
instructions it lacks. Soft `f64` is called per frame only
by `lb_sine_sample` (below); the CPU's random wander targets (the
source's `double` arithmetic), the options menus and the VS record keep
theirs, off the per-frame path. The time went to work
the code repeated every frame:

| Hotspot | Cost under PPSSPP before | Cause | Fix |
|---|---|---|---|
| `Pack::fighter_translate_scales` | Nearly all of `vs4`'s 46.5 ms animation | A reverse scan of all 6,311 animation rows, decoding each, twice per fighter a frame. Only Luigi has a row, so every other fighter scanned the whole table (82 µs a call on the host) | `Pack::anim_row`: a binary search of the sorted prefix, then an index, built once, of the 405 unsorted special rows. All nine special-row lookups use it; five open-coded scans in the game crates call `effect_anim` |
| `lb_sine_sample` | Nearly all of `vs4`'s 12.2 ms joint sampling | `dLBCommonSinLookup` rebuilt per lookup from a 12-term `f64` series, in software floating point on a PSP; six lookups per joint for the collision matrices | `LB_SINE`: the same formula evaluated by the compiler (`const fn`), equal word for word to the run-time series (test) and to the ROM (`lbcommon_sine_table_matches_the_rom`) |
| Sprite lookups | 25% of `vs4`'s samples after the two above | `Pack::sprite`/`fighter_sprite` scanned 903 sprite rows, decoding each, a dozen times a frame | A sorted index of the main pack's sprite table (packs under 64 sprites, opened every frame, are scanned) |
| Vblank wait | 6–11 ms a frame | `end_frame` waited for the next vblank and swapped `Immediate`, so a CPU-bound frame was rounded up to whole vblanks (a 20 ms frame took 33) | `sceDisplaySetFrameBuf(.., NextFrame)` without waiting; the next `begin_frame` waits only if no vblank has latched the frame yet, so the GE never draws into the buffer on screen and a frame still takes at least one vblank |
| Item hit search | 3.0 ms in Bonus Practice | `ItemPool` copied each `Item` out of its slot and back around every search | Searches borrow the slot; an item is copied only once it can be hit (0.8 ms) |
| Magnifier depth mask | Up to 10 ms a frame in battle | Each pixel sampled twice through the 3-point filter, four divisions per sample, one draw per span | Each pixel sampled once; `s` and `t` per column and row; a uniform interior quad short-cut and memo; one draw per row |
| Table reads | 1–2 ms | Table offsets re-summed from 22 counts per access; a bounds check per byte; `Pack::node` decoding 28 floats for a parent or a rest pose; a costume lookup searching the whole override table | Offsets computed in `Pack::open`; one bounds check per row; `node_parent`/`node_rest`; `costume_rows` |

Static code grew by 16 KB (`psp-size`: 2,972,472 against 2,956,376
bytes); the generic sorts the indexes first used added 35 KB and were
replaced by a shell sort. The opening Jungle's lowest free memory under
PPSSPP fell by 18 KB (2,338,816 to 2,320,896).

## Results

PPSSPP, `capture_scene_file,profile` builds of `640cc91` (before) and
`6c7bf55` (after), averaged over the two-second reports from the third
to the freeze tick. "CPU" is update plus draw, less any vblank wait; the
hardware column is RE-469's PSP-2000 run of the before build.

| Scene | PSP-2000 before | PPSSPP before: FPS, CPU ms (update / draw) | PPSSPP after: FPS, CPU ms (update / draw) | Worst frame after |
|---|---:|---|---|---:|
| Title attract demo (`title@4000`) | 15.4 | 20.3, 44.9 (20.6 / 24.3) | 59.9, 4.0 (1.9 / 2.1) | 72.3 ms |
| Opening Jungle (`op-jungle@1200`) | 29.9 | 30.5, 35.4 (28.9 / 6.5) | 59.8, 3.2 (0.2 / 3.0) | 33.6 ms |
| VS, 4 fighters (`vs4@4000`) | 8.1 | 8.2, 113.8 (73.9 / 39.9) | 59.6, 9.3 (4.3 / 4.9) | 54.5 ms |
| 1P Game, Link's stage (`onepgame@4000`) | 11.9 | 11.9, 72.2 (42.3 / 29.9) | 59.9, 6.6 (3.4 / 3.1) | 33.4 ms |
| Bonus Practice (`bonuspractice@4000`) | 14.9 | 14.9, 55.1 (29.8 / 25.3) | 59.9, 6.8 (4.6 / 2.2) | 17.4 ms |
| VS character select (`vsplayers@4000`) | 14.9 | 14.9, 64.7 (23.1 / 41.6) | 59.9, 2.2 (0.0 / 2.2) | 16.7 ms |

The worst frames are one-off: `vs4`'s are the entry, when all three CPUs'
magnifiers are large (up to 51 ms of magnifier a frame under PPSSPP);
the title's is a 34 ms effect-player catch-up on its first battle. In
`vs4`'s live battle the CPU time is 9.3 ms of the 16.7 ms frame: map
collision 1.7, the stage's draw 1.1, the fighters' 2.0, the interface
1.0.

**Hardware numbers are pending.** The PSP was unavailable for this batch;
every number above is PPSSPP's. RE-469's runs put the PSP-2000 within 2%
of PPSSPP on four of the five battle scenes and 25% slower on the title
demo, so `vs4`'s 9.3 ms may be 9–12 ms on the PSP.

## Deviations

None. No gameplay value, drawn pixel or tick order changes:

- The lookups return what the scans returned, row for row
  (`crates/ssb-rom/tests/anim_lookup.rs`, which fail when the index is
  broken).
- `LB_SINE` holds the bits the run-time series gave.
- The 3-point filter's short cut returns what the blend gives four equal
  texels.
- The present change alters when a finished frame reaches the screen,
  not what is drawn. Headless captures wait for the frame to be on screen
  (`Gpu::wait_presented`) before taking it.
- No golden drew a magnifier: with `draw_depth_image` returning at once,
  all 128 `psp-game` goldens matched. `vs4` captured at eight ticks from
  1000 to 3300 (a magnifier at 2800) is identical under `640cc91` and this
  batch, and `f1-vs-four-magnifier` (`vs4@2800`) is a new golden.
- Golden matrix: 198 of 198 match; deepest game stack 239,344 bytes.
