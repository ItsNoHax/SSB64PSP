**Outstanding: physical-hardware smoke test.** This session ran entirely in
a sandboxed environment with no physical PSP attached, so the plan's
mandated hardware smoke test of both EBOOTs has not been performed. The one
specific residual risk RE-297 flagged still applies: `psp-runtime::gu::
Gpu::end_frame` now calls `sceGuDebugFlush()` unconditionally for
`psp-game` too (previously `psp-game` never called it at all). RE-202's own
root cause -- the hardware crash lives in `sceGuDebugPrint`/`sceGuDebugFlush`'s
state once glyphs are actually queued, not in a bare `Flush` against an
empty buffer -- means this should be safe (years of `psp-asset-viewer`'s
own shipped, physically-confirmed builds already exercise exactly this
call every frame with `debug_overlay` off), but `psp-game` itself has never
been the specific subject of that hardware proof. Per RE-296's established
distinction, a `PSPLink ldstart` run is not equivalent to an installed-EBOOT
`PARAM.SFO` `MEMSIZE` run -- do not diagnose an `ldstart` memory limitation
as a `psp-runtime` regression; use the installed-directory path for the
real test.

**Verdict.** All software-verifiable acceptance criteria pass. This entry
stays `OPEN` until a physical PSP confirms both EBOOTs boot and run
correctly (staged EBOOTs/hashes above), at which point it should be closed
with the hardware results and F1 feature development can resume per
`STATUS.md`.
