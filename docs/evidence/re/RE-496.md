# RE-496 — Several anneal seeds at more iterations find a better link order than one seed found

Status: COMPLETE (PSP-2000, 6.61 ARK, PSPLink v3.2.1, `profile,capture_scene_file,no_audio` builds of `vs4@2400` with pack v109 on `ms0:`, reports 1–18, two interleaved rounds per pair; I-cache model in PPSSPP, `tools/icache/`)
Topics: performance, hardware, icache, toolchain
Relevant files: `tools/icache/layout.c`, `tools/icache/relink.py`, `psp-game/link-order.txt`

## Question

RE-495 found that a second anneal seed scored 3% fewer modelled misses and
ran 0.6 FPS faster than the single seed RE-494 used to search the shipped
audio build's order. Does searching with several seeds and more iterations
find a materially better order, and does the model's ranking still hold on
hardware?

## Findings

### Seed and iteration variance

Same trace/orderable/tail inputs as RE-494 (`capture_scene_file`, audio on,
`vs4@2400`, HEAD's order and tail as the search's starting point):

| Search | Runs | Train misses (best / median) | Held-out of best |
|---|---|---|---|
| HEAD's order (RE-494) | – | 331,754 | 332,274 |
| 30,000 iterations, seeds 1–16 | 16 | 322,591 (seed 5) / ~328,200 | 323,011 |
| 90,000 iterations, seeds 21–32 | 12 | **319,529 (seed 26)** / ~324,000 | **320,021** |

Seed 1 at 30,000 iterations (closest to how HEAD's order was made) scored
329,144 / 329,762 — barely better than HEAD's order, confirming RE-495's
"one seed is not enough." Sixteen seeds at 30,000 iterations found 2.8%
fewer misses than the single seed; tripling the iteration budget to 90,000
found about 1% more on top of that. The best two of the 90,000-iteration
seeds (26 and 22) scored within 0.2% of each other, so returns had
flattened — more seeds or more iterations were not pursued past this point.

The winning order (seed 26, 90,000 iterations) cuts the draw phase's
modelled misses from 241,799 to 230,710 (−4.6%) and the whole frame from
331,754 to 319,529 (−3.7%), about 556 fewer model misses a frame.

### Verification (RE-494's procedure, step 6)

- Relinking the winning order with `relink.py` and replaying both the
  training and held-out traces reproduced 319,529 / 320,021 exactly.
- The 315 searched functions have identical address and size between the
  relinked ELF and a real `cargo psp --release` build of the new order
  — the `LAYOUT_TAIL` pinning held.
- A real `cargo psp --release` build of the new `link-order.txt`, relinked
  through `relink.py` from the same saved inputs, produced a
  byte-identical ELF.

### Hardware A/B (PSP-2000)

The release build has no frame timer, and `profile` changes the size of
the draw code (HEAD's searched block shifts after function 16 in a
`profile` build), so — as in RE-494/RE-495 — the hardware A/B used a
`profile,capture_scene_file,no_audio` build with orders searched directly
for it (same procedure, 8 seeds × 30,000 iterations from HEAD's order,
trace windows at 20 s / 32 s, 23 frames):

| `profile` build order | Model train / held-out | FPS round 1 / 2 | Frame µs | Draw µs | Material µs |
|---|---|---|---|---|---|
| HEAD's file (as linked) | 416,280 / 416,080 | 52.52 / 52.50 | 19,119 | 11,371 | 1,432 |
| seed 1 (single-seed method) | 357,950 / 357,727 | 55.60 / 55.59 | 18,088 | 10,425 | 1,441 |
| best of 8 (seed 4) | 345,643 / 346,380 | **56.50 / 56.50** | 17,805 | 10,158 | 1,344 |

Round-to-round noise was ≤0.02 FPS. Hardware ranked all three exactly as
the model did. Best-of-8 against the single-seed method: +0.90 FPS,
−283 µs a frame for 12,307 fewer model misses, about 0.53 µs per model
miss (HEAD→seed-1 was 0.41 µs/miss; RE-494's calibration point was
0.385 µs/miss). The eight proxy seeds' scores spread from 345.6K to
358.8K (median ≈357K), so seed 1 was a typical single-seed draw, not an
unlucky one. An audio-on `profile` build with HEAD's file ran 47.10 /
47.27 FPS — audio adds about ±1 FPS of per-window jitter (why the A/B
build stays `no_audio`).

### A relinked ELF cannot be scored with `layout`'s "as linked" line

`layout`'s `ITERS=0` report maps the trace with the function addresses
*it* is given, so feeding it a relinked ELF's `nm` output just reproduces
the order it was told to measure, not the relinked ELF's actual layout.
Scoring a relinked ELF (to confirm `relink.py`'s output, or to compare a
real `cargo psp` build against a `relink.py` one) needs a small script
that maps each trace block with the *traced build's* `nm` (so block
identities don't change) but places it at the address it has in the
*relinked* ELF. That script (not added to `tools/icache/`) reproduced
`layout`'s own training counts exactly (322,591 / 319,665 / 319,529 for
the top three seeds) but gave held-out counts 50–100 lower than `layout`'s
reported held-out score, because `layout` places held-out-only hot
functions slightly differently from `lld`'s real packing. `layout`'s
held-out number is therefore a slight overestimate of a relinked ELF's
true held-out misses; the difference is under 0.1% and did not change
which seed won.

## Consequences

- `psp-game/link-order.txt` now holds the seed-26, 90,000-iteration order.
  Nothing else in the repository changed; the order still ends in the same
  six-function `LAYOUT_TAIL` (`session_frame`, `run`, `capture_ticks`,
  `scripted_buttons`, `scripted_stick_x`, `scripted_stick_y`).
- RE-494's procedure step 5 should read "several seeds, 90,000 iterations,
  keep the best held-out result" rather than one seed at 20,000–30,000.
- Diminishing returns: two seeds already found most of the gain RE-495
  flagged; a wider seed sweep and a 3× iteration budget found about 1%
  more on top, then flattened. A future re-search after hot code changes
  size should expect similar returns, not assume more seeds always pay.
- A trace-replay scorer that places blocks at a relinked ELF's real
  addresses (rather than `layout`'s own placement) would remove the small
  held-out overestimate above; `tools/icache/` does not have one yet.
