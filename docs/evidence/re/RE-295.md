# RE-295 — Real jump binding reaches the dummy's real spawn point; jab pixel-confirmed

Status: COMPLETE
Topics: front-end, physics, gameplay, input
Relevant files: psp-game/src/main.rs (`scripted_buttons`, `scripted_stick_x`, `JUMP_BUTTON_MASK`, `DETERMINISTIC_CAPTURE_TICKS`), tools/romtool/src/main.rs (`jumptest`), crates/ssb-engine/src/input.rs (`DEFAULT_MAPPING`), docs/evidence/re/RE-008.md

**Question.** RE-294 built Mario's jab end-to-end but could not pixel-confirm
it: the dummy sits at Dream Land's real spawn 1, a side platform at
`x=-1397, y=904` (measured via `romtool simulate`), roughly `1664` units from
the player's spawn-0 floor position — mostly vertical. `psp-game` had no jump
input wired at all (`main.rs` hardcoded `jump_held = false`, with a comment
declining to guess a control mapping), so nothing could ever close that
distance. Is there a real, decomp-sourced jump binding available, and can a
scripted input schedule using it actually land the player on the dummy's
platform and connect the jab, verified against the real pack's own collision
data rather than assumed?

**Answer: yes to both — the binding already existed unused, and the physics
(already fully ported) support a two-jump arc that lands within melee range.**

* **The jump binding was not an open design choice; it existed unwired.**
  `ft/ftcommon/ftcommonkneebend.c`'s `ftCommonKneeBendCheckButtonTap` treats
  *any* N64 C-button tap (`R_CBUTTONS|L_CBUTTONS|D_CBUTTONS|U_CBUTTONS`) as a
  real jump-by-button input, independent of camera/taunt uses — a genuine
  decomp finding for RE-008 (updated), not previously confirmed there.
  `crates/ssb-engine/src/input.rs`'s `DEFAULT_MAPPING` already assigns the
  PSP's Triangle/Square to `C_UP`/`C_DOWN`. So the real jump control was
  already one line away: read `controller.buttons` against a C-button mask
  and pass it as `Play::tick`'s existing `jump_held` parameter — itself
  already fully implemented (`crates/ssb-game/src/status.rs`'s
  `set_kneebend`/`set_jump`/`set_jump_aerial`, ported from
  `ftcommonjump.c`/`ftcommonkneebend.c` well before this session). No new
  physics or status code was needed, only the input wire.
* **A single grounded jump cannot reach the platform.** A new `romtool
  jumptest` subcommand (native, no PSP/emulator — ticks the real
  `ssb_game::fighter::Fighter` against a real pack's floor segments exactly
  as `Play::tick` does) measured a maximum-height button jump's apex at
  `~660` units — short of the `904`-unit platform regardless of horizontal
  stick, because `ftCommonJumpGetJumpForceButton`'s height/distance curve
  trades one for the other, and grounded run speed does not carry into a
  jump's `vel_air.x` in the original (`ftCommonJumpSetStatus`, confirmed
  against decomp source, not assumed). A second, midair jump
  (`ftCommonJumpAerialSetStatus`) resets `vel_air` from wherever the fighter
  currently is, so timing it partway up the first arc supplies the remaining
  height plus a fresh horizontal component.
* **The working schedule, derived by `jumptest` against the real pack:** tap
  a C-button at local tick 5 (vertical button jump, neutral stick, so no
  height is traded away); hold the stick toward the dummy (`-30`, not full
  deflection) from tick 25, tapping a second C-button that same tick
  (midair jump); release the stick at tick 82 so the landing does not dash
  off the platform's far edge; tap A at tick 90, once `LandingLight`'s lag
  has cleared into `Wait`. `jumptest`'s trace landed within `2.2` units of
  the dummy's real settled position and confirmed the jab hitbox overlapping
  the dummy's hurtbox (`ssb_game::attack::spheres_overlap`) at ticks 92-93 —
  the same formulas and radii RE-294 unit-tested, now proven reachable
  against real collision geometry rather than assumed reachable.

**What was built.**

* `psp-game/src/main.rs`: `scripted_buttons` gained the two C-button jump
  taps (real ticks 13/33 — Training's first fighter tick is tick 8, so
  `jumptest`'s local schedule is offset by 8) and the attack tap moved from
  tick 8 (RE-294's un-exercised placeholder) to tick 98. A new
  `scripted_stick_x` supplies the held-left carry phase (real ticks
  34–89). `JUMP_BUTTON_MASK` names the real C-button mask. The
  `regression_capture` branch of the Training tick call now builds its
  `ControllerState` from these scripted functions instead of a hardcoded
  neutral one — a deterministic capture of gameplay input has to actually
  drive that input, not discard it, once there is real input-driven movement
  to capture. `jump_held` is now `controller.buttons.contains(JUMP_BUTTON_MASK)`
  in both the `regression_capture` and real-pad branches, so the same real
  binding applies whether or not the build is a deterministic capture.
  `DETERMINISTIC_CAPTURE_TICKS` moved from `16` to `106` to cover the full
  jump-land-jab sequence plus a few ticks of post-hit knockback.
* `tools/romtool/src/main.rs`: new `jumptest` subcommand (see above) —
  general-purpose enough to keep as a permanent dev tool alongside `simulate`
  and `collide`, not a one-off script; the next attack/stage/select scene
  needing a scripted input schedule can reuse it rather than re-deriving one
  by trial-and-error against the emulator.

**Confidence: high.** The reachability claim rests on the same
`Fighter::tick`/collision code both the native `jumptest` trace and the real
`mipsel-sony-psp` PPSSPP capture ran, not a hand calculation (an earlier hand
estimate of the button jump's apex was wrong by roughly a factor of two;
`jumptest`'s empirical trace is what actually informed the schedule). The
jump binding itself is decomp-sourced (`ftcommonkneebend.c`), not invented,
and reuses `ssb_engine::input::DEFAULT_MAPPING`'s existing PSP button
assignment rather than adding a new one.

**Still open, unchanged from RE-289–294 except where noted:** no
physical-PSP evidence for `psp-game`. `sceFont` text for real menu/select
labels. The jab's second (joint-9) hitbox, per-bone hurtboxes, the
friction-based knockback decay curve, and a real `Damage` status/animation
for the target remain documented gaps in `crates/ssb-game/src/attack.rs`'s
module docs, unaffected by this session. An upward-stick jump (the game's
other real jump input, `JumpInput::Stick`) is not exercised by the capture
script (button jump only) but needed no separate wiring: `Fighter::tick`'s
status machine already reads `stick_y` directly, unconditionally on this
session's changes. C-Left/C-Right remain unmapped on the PSP's default
scheme (RE-008): only C-Up/C-Down were needed for a button jump, since any
one C-button satisfies the decomp's "any C-button" check.
