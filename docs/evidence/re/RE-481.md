# RE-481 — Four-player VS on a PSP-2000: hardware counters per span

Status: COMPLETE (PSP-2000 PSPLink runs of `vs4@2400` without audio, `profile_hw` build; counter meanings follow PSPSDK's register names, not a hardware manual)
Topics: performance, hardware, toolchain
Relevant files: `psp-runtime/src/hwcount.rs`, `psp-runtime/src/profile.rs`, `psp-runtime/src/meshdraw.rs`, `psp-runtime/src/gu.rs`

## Question

RE-480 found every span of four-player VS 2.5–7× slower on a PSP-2000
than PPSSPP counts, with no hot spot. Is that memory (cache misses,
uncached writes) or latency (load-use, FPU)? PSPSDK's profiler registers
at `0xBC400000` count both, but sit in kernel space.

## Reading the counters from the game

- ARK-4's SystemControl exports `KUBridge` to user mode (checked with
  PSPLink's `modexp @SystemControl` and `disasm` on the PSP-2000, 6.61
  ARK, PSPLink v3.2.1): `kuKernelPeekw` (NID `0x7A50075E`) is
  `lw v0, 0(a0); jr ra`, `kuKernelPokew` (`0x0E73A39D`) is
  `sw a1, 0(a0); jr ra`, and `kuKernelCall` (`0x9060F69D`) calls a
  user function in kernel mode with twelve arguments.
- `kuKernelCall` costs ~42,500 cycles a call (128 µs), ~1,070 of them
  COP0 instructions: it does cache maintenance. Called at each span's
  start and stop (thousands a frame, the per-primitive spans included),
  the frame grew from 18 to 75 ms of CPU; the log stopped after six
  frames, PSPLink stopped answering, and the PSP was later found asleep
  (below). Whether the calls or the sleep stopped the log is not
  settled. Once a frame, it ran a whole run.
- `profile_hw` reads ten registers with `kuKernelPeekw`, one system
  call each, enabling the profiler with `kuKernelPokew` if its enable
  register reads 0: 1,733 cycles (5.2 µs) a read. The per-primitive
  spans (`nodemat`, `material`, `submit`, `skin`) are timed only
  (`profile::start_fine`). With it the run's CPU span is 18.0–20.0 ms a
  frame, against RE-480's 18.3. Each report measures a read's own counts
  with back-to-back reads and subtracts them per read inside a span.
- The import stubs mirror rust-psp's `psp_extern!` (private to that
  crate) in `hwcount.rs`; cargo-psp's import fix-up handles them as it
  does rust-psp's own.
- PPSSPP has no `KUBridge`: `profile_hw` is for the PSP only.

## The PSP slept under the runs

Two runs ended with the USB device disconnecting 25–35 s after the game
stopped writing, without re-enumerating, the screen off. The battery read
100%. The game never called `scePowerTick`, and a measurement run gets
no input: the PSP's auto-sleep. `profile` builds now tick power every
frame; the next run held through all 19 reports.

## Results

`vs4@2400`, Mario and three CPUs on Dream Land, `profile_hw` reads per
span, reports 1–18 averaged (`cpu_us` = counted CPU cycles / 333; the
counters are global, so each span also counts interrupts taken inside
it):

- **Memory, not latency.** Over half the frame's cycles stall on memory;
  internal (load-use, multiply/divide) and FPU stalls take a tenth.
  PPSSPP charges neither, which accounts for most of RE-480's ratios: the
  spans that stall most (interrupts, hit detection, the stage draw, 60–71%)
  are the 4–7× ones.
- **The draw misses instructions.** It takes 22,926 I-cache misses a
  frame against 6,822 D-cache misses; the stage draw 6,562 against 1,172.
  The draw runs a large code path per node and primitive through a 16 KB
  I-cache. The update's misses are even. Memory stall per miss is 63–70
  cycles in the update and 100–130 in the draw, which also writes the
  display list uncached (`gu.rs`'s `DISPLAY_LIST`, `sceGuGetMemory`
  vertices: 20,321 uncached stores a frame).
- **Posing** is the one span with a large FPU share (17.6% COP1 stall).
- **Magnifiers.** While fighters are off-screen the interface costs up
  to 12.8 ms a frame in a two-second window, mostly the depth masks
  (`mmask` 7.2 ms average, 10.3 ms worst) — 10,869 uncached stores a
  frame across the run, the mask's 1-pixel span sprites
  (`draw_depth_image`). RE-480's 1.9 ms interface average hides these
  windows.
- The vblank wait counts 66 µs of cycles in its 2.9 ms: the CPU counter
  stops while the thread sleeps.
