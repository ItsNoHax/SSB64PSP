# RE-275 — angrylion-rdp-plus reference-render harness ported to RMG's sandbox, segfaults on plugin startup

Status: OPEN
Topics: texture, fighter, hardware, visual-regression, toolchain
Relevant files: docs/evidence/re/RE-274.md, docs/evidence/re/RE-216.md

**Question.** RE-274 left RE-272's face-texture bug needing an accurate N64
reference render (real hardware or `angrylion-rdp-plus`) of Mario's face at
the object-viewer's camera distance, to tell a faithfully-reproduced ROM
filtering quirk from a real addressing/scale bug. Is `angrylion-rdp-plus`
actually available in this environment, and can RE-216's scripted-capture
approach be reused to drive it?

**Measurement.** `angrylion-rdp-plus` is not checked out as source anywhere
in this repo or `refs/` (`crates/ssb-rom/src/n64_filter.rs`/`n64_addressing.rs`
only transcribe its algorithms as host-side reference models, per RE-219/
RE-220) — but it is installed as a ready-to-run GFX plugin,
`mupen64plus-video-angrylion-plus.so`, bundled inside a second, separate
flatpak N64 front end already present on this machine, Rosalie's Mupen GUI
(`com.github.Rosalie241.RMG`), alongside its own `libmupen64plus.so` core
(`/app/lib/RMG/{Core,Plugin}/...` inside that sandbox) — distinct from the
M64Py flatpak RE-151/RE-216's harness targets, which only bundles
`mupen64plus-video-rice`.

RE-216's `re151_driver.py` (Core-API-direct scripted capture: `CoreStartup`/
`CoreAttachPlugin`/frame-exact `ADVANCE_FRAME`, a custom no-libc-dependency
input plugin `re151_input.so`) is a generic pattern, not M64Py-specific.
Ported it to a new `~/ppsspp-test/re151-harness/re274_angrylion_driver.py`
(out-of-Git, RE-151/RE-216's own convention) pointed at RMG's paths instead:
`CORE_PATH=/app/lib/RMG/Core/libmupen64plus.so`,
`GFX_PATH=.../Plugin/GFX/mupen64plus-video-angrylion-plus.so`,
`RSP_PATH=.../Plugin/RSP/mupen64plus-rsp-hle.so` (RMG's audio plugin,
`RMG-Audio.so`, is a custom, non-`-sdl` implementation, also wired but
unused for this purpose). Two environment fixes were needed and applied:

1. RMG's flatpak sandbox did not have `~/ppsspp-test` in its filesystem
   permissions (`flatpak info --show-permissions`) the way M64Py's already
   did; granted with `flatpak override --user --filesystem=/home/alberto/ppsspp-test
   com.github.Rosalie241.RMG` (reversible with `flatpak override --user --reset`).
2. `re151_input.so` (`ldd`: only `libc.so.6`) loads unmodified inside RMG's
   sandbox via `ctypes.CDLL`, confirming RE-216's own "no libc dependency
   beyond the trivial CRT... sidesteps ABI mismatch" design travels across
   flatpak sandboxes as intended.

**Result: reproducible segfault.** Running
`flatpak run --command=python3 com.github.Rosalie241.RMG re274_angrylion_driver.py
--rom ".../Super Smash Bros. (USA).z64" --input-so re151_input.so --frames 30
--final-screenshot` boots the core (ROM identity confirmed: MD5
`F7C52568A31AADF26E14DC2B6416B2ED`, matching `PLAN.md`/RE-151's asserted
identity) and reaches `gfx.PluginStartup(...)` — the exact call RE-216 found
and fixed a `ctypes` `argtypes`-truncation segfault in — but crashes there
anyway (exit code 139 / SIGSEGV) despite the driver declaring the identical
`argtypes` fix RE-216 already proved correct for `mupen64plus-video-rice.so`
under M64Py. `coredumpctl list` confirms two `python3.13` SIGSEGV core dumps
at the run's timestamp; no `gdb` is installed on the host or inside either
flatpak sandbox to symbolize them, so the exact fault site inside
`mupen64plus-video-angrylion-plus.so` is not yet known — this is a different,
plugin-specific failure, not a reoccurrence of RE-216's argtypes bug.

**Not yet root-caused.** angrylion-rdp-plus likely performs more startup work
than rice inside `PluginStartup` itself (rice defers most GL/window setup
until later Core callbacks) — candidates include an internal thread/window
creation that needs a `VidExt` callback registration this minimal driver
never installs (`CoreOverrideVidExt`, unused by either driver so far, since
rice apparently tolerates its absence), or a config-section read that
segfaults without an existing `angrylion-plus`-specific `.ini` (only
`GLideN64.ini` exists under RMG's config dir; no equivalent has ever been
generated for angrylion, since RMG's own GUI has apparently never been run
with it selected as the active plugin).

**Conclusion.** Not fixed; this session's remaining budget did not extend to
installing symbol tools or auditing angrylion-rdp-plus's `PluginStartup`
implementation for its `VidExt`/config expectations. The harness, sandbox
permission grant and driver script are left in place
(`~/ppsspp-test/re151-harness/re274_angrylion_driver.py`) for the next
session to resume from, rather than re-derived. Real-hardware capture (the
other option RE-274 named) remains untried and does not depend on this path.

**Confidence: high** on the measurements (plugin located, ROM boots, exact
crash site and exit code observed); root cause of the segfault is open.
