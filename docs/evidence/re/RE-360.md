# RE-360 — `psp-game` Training reaches 60 Hz on the PSP-2000

Status: COMPLETE (PSP-2000 per-section timing, 3,600-tick live replay, native captures; PPSSPPHeadless goldens)
Topics: hardware, timing, performance, rendering, psp-ge, memory, stage
Relevant files: `psp-game/src/main.rs`, `psp-runtime/src/{gu,meshdraw,scene}.rs`, `crates/ssb-game/src/stage/{hyrule,zebes}.rs`

## Question

RE-341 measured Training at 30 Hz on the PSP-2000: each loop took
33,364 µs, but simulation took only 1,740 µs. What fills the rest of the
frame?

## Setup

PSP-2000 Slim, firmware 6.61 ARK, PSPLink v3.2.1. Pack v43
(`b83c6d37…`) loaded from `host0:`. Builds used `capture_scene_file`
with scenes `costume3` and `fireball`. Temporary probes, since removed,
timed each loop section and appended 300- or 600-frame averages to
`host0:`.

## FPU trap on Training entry

The first hardware run at `1267295` stopped on Training entry with
`FPU Exception (IUV)`. EPC `0x08885FB8` minus TextAddr `0x08804000` maps to
`ssb_game::hazard::search_hit_hazard`, at a `c.olt.s`. Under LTO,
`Hyrule::check_twister` is inlined into `Stage::check_obstacles`. LLVM
hoisted its float loads and compares above the `Controller::Hyrule` match.
On Dream Land the controller is `Pupupu`, so the bytes at those offsets
belong to another variant. One pattern is a NaN, and an ordered compare on
a NaN traps. This is RE-201's fault class. `check_twister` and
`Zebes::check_acid` (the same shape in `check_hazards`) are now
`#[inline(never)]`. The fixed build ran every later hardware test here
with an empty `exlist`.

## Where the frame went

Frozen `costume3` scene, averages over 300 frames:

| Section | Before (µs) | After (µs) |
|---|---:|---:|
| Draw-list build (CPU) | 19,436 | 7,390 |
| Stage | 4,516 | 4,468 |
| Two fighter shadows | 8,520 | 102 |
| Weapon and reflector section, no weapons live | 3,340 | 10 |
| Player fighter | 1,742 | 1,530 |
| Dummy fighter | 1,240 | 1,201 |
| GE wait after `sceGuFinish` | 23 | 42 |
| Vblank wait | 13,453 | 9,222 |
| Whole loop | 33,366 | 16,683 |

The GE finishes about 40 µs after the list closes. The limit was CPU time
spent building the list. `draw_fighter_shadow` scanned all 1,881 texture
descriptors for the shadow role on every call, twice per frame.
`draw_training` also scanned the mesh and object tables for the Fireball,
Blaster and Reflector every frame, even with no weapon live. Each table
read misses the cache. `psp-game` now resolves these four descriptors once
per pack (`DrawAssets`), and `draw_fighter_shadow` takes the resolved
texture. The stage draw (4.5 ms) is the largest remaining cost. It is
`P5` work.

Unfrozen `fireball` scene: simulation takes 2,938–3,593 µs per tick, and
the loop holds 16,683 µs with 6.0–6.6 ms of vblank slack. A 3,600-frame
run averaged 16,682 µs per frame with a maximum of 16,766 µs after the
first window. Only the Training entry frame (33,371 µs) missed a vsync.

## Display-list cache-line aliasing

The first 60 Hz build (`89d92026…`) displayed a garbled frame on the PSP
screen, reproduced in every capture. The capture showed two half-size
copies of the scene, side by side, over a black lower half. Decoding each
32-bit word as two RGB565 pixels recovers a clean scene. The GE drew the
whole run as RGB565 into the RGBA8888 buffers. A 12 ms busy-wait before
`end_frame`, or any small per-frame probe, removed the fault. Neither changes
any GE command, so the cause was code layout.

`DISPLAY_LIST` was `Align16`. In the bad build it started at `.bss`
`0xfca10`, in the same 64-byte D-cache line as `CURRENT_MATRIX_UPDATE`
(written by every `sceGum*` call) and `VRAM_ALLOCATOR` (taken in
`Gpu::init`). `sceGuStart` writes commands through the uncached alias, so
the cached copy of that line is stale. Its writeback overwrites the first
12 list words. In the init list those words hold the
`FramebufPixFormat` command from `sceGuDrawBuffer`, so the GE kept
`sceGuInit`'s reset format of 0 (RGB565). Every per-frame list sets only
the framebuffer pointer and width. The good baseline placed the list at
`0xfc8c0`, which is 64-byte aligned. `DISPLAY_LIST` is now
`#[repr(align(64))]`. It lands at `0xfca40` in the same scripted build,
`0xfb440` in the interactive `psp-game` and `0xb1a80` in the viewer.

The fixed scripted build (`cb0da1f1…`) capture `684551d0…` matches the
baseline hardware capture of the same frozen frame on every pixel.

## Verification

- Workspace tests: 1,193 pass. Pinned 1.98.0 Clippy and rustfmt pass.
- Both PSP release builds pass.
- PPSSPPHeadless: 73 of 73 goldens match twice, before and after the
  alignment change.
- The interactive `psp-game` PRX (`9d76d2c6…`) loads from `host0:`,
  `main_thread` stays alive and `exlist` is empty.

## Limits

This covers one PSP-2000 and the two-fighter Training scene. It does not
cover four-player VS or other stages. Hand-played input was not tested.
In the unscripted tail of the live run, both fighters leave Dream Land
by about 70 seconds, and the camera then shows only the clear colour. This
was not investigated. It does not affect the timing above.
