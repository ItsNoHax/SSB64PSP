# RE-492 — The battle wallpaper fits the VRAM photo region; sampled from there it saves 0.32 ms a frame

Status: COMPLETE (PSP-2000, 6.61 ARK, PSPLink v3.2.1, `profile_hw,capture_scene_file,no_audio` builds of `vs4@2400` with pack v109 beside the PRX on `host0:`, reports 1–18, two interleaved rounds; 198 of 198 goldens unchanged in PPSSPP)
Topics: performance, hardware, psp-ge, memory, texture
Relevant files: `psp-runtime/src/gu.rs`, `psp-runtime/src/meshdraw.rs`, `psp-runtime/src/scene_files.rs`

## Question

After RE-490's strips and RE-491's palettes, the battle wallpaper was the
largest texture the GE still read from main memory: 300 × 220 RGBA5551
with 3,031 colours, too many for a palette, about 0.5 ms of CPU memory
stall a frame. Its image is 256 KiB at a 512-texel stride and 256 padded
rows, more than the ~180 KiB of free VRAM. Can it be sampled from VRAM?

## Findings

### The photo region is idle in battle

`Gpu::init` keeps a 512 KiB VRAM region for the copy of the wallpaper
photo the frozen picture and the 1P Stage Clear wallpaper sample
(RE-476). Only the opening room's last picture and the Stage Clear
screen draw from it; no battle does. `gu::vram_resident` lends the
region to one texture: the GE copies the texture's image into it once
(`sceGuCopyImage` as rows of 32-bit words, whatever the format or
swizzle), and the texture is sampled from there until the photo needs
the region again or the texture's memory is freed. A tag records which
of the two the region holds, so each copies back in on its next use:
correct even if one scene drew both. `scene_files` clears the tag
before it frees retired blocks, since a later file can reuse the
texture's address. `meshdraw::draw_wallpaper` is the only user.

The copy samples the same texels, so all 198 goldens keep their pixel
hashes. Skipping the copy (the region left empty) fails
`f1-vs-sudden-death`, so the goldens do see the VRAM binding.

### Hardware

A is RE-491's PRX (`6bf4f513cc129f04`), B this change
(`59f8186b7cbde376`), both with pack v109 (46,954,960 bytes) beside the
PRX. Both read every battle file before the measured window (`io` 0).

| Build | FPS | CPU frame µs | Draw µs | Frame memory stall µs | Draw I-misses | Draw D-misses |
|---|---:|---:|---:|---:|---:|---:|
| A | 47.14 / 47.18 | 18,922 / 18,916 | 10,879 / 10,875 | 9,198 / 9,192 | 17,850 | 5,970 |
| B | 48.04 / 48.04 | 18,600 / 18,599 | 10,673 / 10,671 | 8,869 / 8,868 | 17,967 | 5,630 |

- −0.32 ms of CPU frame, −0.33 ms of memory stall, and 47.2 → 48.0 FPS.
  That is about two thirds of RE-490's 0.5 ms estimate for the striped
  wallpaper.
- Free RAM in battle is unchanged (40,279,296 bytes): the texture stays
  in the pack too.

## Consequences

- The texel stall left in four-player VS is mostly the stage's CLUT4
  textures (~0.45 ms, RE-490) and the rest (~0.2 ms).
- The photo region holds one texture at a time; a second large texture
  would need VRAM from elsewhere (16-bit colour buffers would change
  every golden).
