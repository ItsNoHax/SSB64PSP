# RE-533 — Four-player VS on a PSP-2000: one collision compose per fighter tick, a joint table, and a re-searched link order

Status: COMPLETE (PSP-2000, 6.61 ARK, PSPLink v3.2.1, `capture_scene_file,frame_timer` builds, audio on, 120-frame reports; base 3d43106)
Topics: performance, hardware, link-order, gameplay
Relevant files: `crates/ssb-rom/src/skeleton.rs`, `psp-runtime/src/scene.rs`, `crates/ssb-game/src/fighter.rs`, `psp-game/link-order.txt`

## Question

`vs4@2400` slowed between RE-500 and HEAD. Where did the time go, and how much comes back without changing a pixel?

## Findings

- `vs4@2400` regressed from 13.64 ms busy (ed405f1, RE-500) to 17.39 ms (3d43106). RE-514 cost +5.2 ms and has since been recovered; lighting is now 0.8 ms busy. The rest is the RE-509/510 slope pass and layout.
- The RE-509/510 slope pass composed collision parts for every grounded fighter, yet only about one fighter a frame (max 3) fits a slope.
- New behaviour: the parts compose is skipped exactly where `slope_contour` would reject it; it composes locals only; the joint sample reuses those locals for the world pass when the fighter did not move; a per-object joint table replaces `pose_for`'s per-node scan.
- Output is bit-identical: reference-copy tests on random poses and on every fighter object, 2,402-frame hash A/Bs on three stages, 218 of 218 goldens.
- Effect: fighter physics -312 us a frame (`profile` spans).
- Re-searched link order: training traces were the opening room, an opening fighter scene and vs4 at 20 s; vs4 at 32 s was held out; seeds 1-8 at 30,000 iterations. Model misses fell 17%. On hardware the chosen order (s7) beat the old one by 1.13 ms on the same code; it was the only top-vs4 order that held the opening.
- Final: `vs4@2400` 17.40 -> 17.13 ms busy (53.6 -> 54.8 FPS). stage=1 -0.02, stage=4 -0.08. The opening is unchanged within spread; Sector is +0.21 ms.
- Dropped: a word-wise `index_range` (no gain) and keeping the light pre-pass matrices (~20 us).
- Lit-expand anatomy: 1316 corners and 412 vertices a frame, ~0.68 us a vertex, memory-bound; the per-prim writeback is required.
- RE-532's `vs4@2400` figure (15.96 ms / 62.7 BFPS) is a 60-frame-report, 3..18 window. On 120-frame reports, 4..19, HEAD is 17.40.

## Method note

With `PPSSPP_ICACHE=1` the patched PPSSPP build writes a summary file named `1` into the cwd.

## Conclusion

The compose was smaller on hardware than the census assumed. The rest of the 3.75 ms gap to RE-500 needs `bind_texture` and the `sceGumDrawArray` stall-address syscalls (PLAN MS8).
