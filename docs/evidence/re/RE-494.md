# RE-494 — A trace-replay search of the link order cuts I-cache misses a fifth; an order fits one build only

Status: COMPLETE (PSP-2000, 6.61 ARK, PSPLink v3.2.1, `profile,capture_scene_file,no_audio` builds of `vs4@2400` with pack v109 on `ms0:`, reports 1–18, two interleaved rounds; the shipped order's gain is the PPSSPP cache model's, which those runs calibrate)
Topics: performance, hardware, icache, toolchain
Relevant files: `tools/icache/layout.c`, `tools/icache/relink.py`, `tools/psp-link.py`, `psp-game/link-order.txt`, `psp-game/src/main.rs`

## Question

RE-482: 39% of the draw's I-cache misses are conflicts, and the link order
(`tools/psp-link.py`, `psp-game/link-order.txt`) decides where code lands in
the 16 KB two-way cache. RE-487: regenerating the order with
`tools/icache/order.py`'s fetch-count heuristic made hardware slower, and a
680-byte shift of downstream code has cost 3 FPS. Can the order be chosen by
measuring each candidate's misses instead of by heuristic, and does a better
modelled layout run faster on the PSP?

## Findings

### The order file had gone stale

RE-493 outlined the per-mesh path's cold blocks into new functions that were
never added to `link-order.txt`. Twenty-five functions the draw runs, 5% of
its fetched instruction words, were placed 2.5 MB from the rest of the hot
code. They included `expand_float_uv_corners`, sixth in the draw by fetched
instruction words, along with `draw_ground_object`, `load_billboard_matrix`
and `draw_link_objects`.

### Replaying a trace predicts a layout's misses exactly

The cache model's block trace (`PPSSPP_ICACHE_TRACE`, 4M blocks, about 23
frames of `vs4@2400`) can be replayed through the PSP-2000's cache (16 KB,
two-way, 64-byte lines, LRU) with every function moved to its address under
another order. Replaying the unchanged layout reproduces the model's count to
11 misses in 451,471. Two details make predicted and linked layouts agree
exactly:

- lld packs the ordered functions back to back on 4-byte boundaries.
- Functions in rlibs (compiler_builtins' `u64_div_rem` and `__umoddi3`) are
  outside the LTO object that `psp-link.py` orders, so they keep their
  linked address.

One replay takes about 20 ms. Simulated annealing over the hot functions'
order, 20,000–30,000 swaps and moves (`tools/icache/layout.c`), takes 7–10
minutes. A second trace from a later window (emulated second 32 instead of 20)
is scored but not searched. Every searched order scored within 0.5% of its
training count on that trace.

`tools/icache/relink.py` relinks saved link inputs with another order in
seconds. The inputs come from a build run with `PSP_LINK_SAVE` set. The
relinked PRXs are byte-identical to `cargo psp` builds of the same order.

### Hardware ranks layouts as the model does

Three orders of one `profile,capture_scene_file,no_audio` build were run on
the PSP: HEAD's order (P0), an order the search found (A2), and a random
shuffle of A2's hot functions (rand2). Misses are the model's, measured on the
linked binaries.

| Layout | Model misses (23 frames) | FPS, round 1 / 2 | Frame (µs) | Draw (µs) |
|---|---|---|---|---|
| rand2 | 533,221 | 47.61 / 47.62 | 21,036 | 13,019 |
| P0 (HEAD) | 451,471 | 51.16 / 51.17 | 19,604 | 11,929 |
| A2 | 372,403 | 54.77 / 54.79 | 18,341 | 10,732 |

Frame time is close to linear in modelled misses, at about 0.385 µs per model
miss. The model counts 86% of the PSP's misses (RE-482), so that is about
0.33 µs per hardware miss. Run-to-run noise is 0.02 FPS.

### An order fits only the build it was searched on

A2 scores 452,503 on the same code built without `profile`, worse than that
build's own linked order (438,620). Several things change function sizes, and
every size change after a function moves the functions behind it:

- `profile` adds timers to the draw code.
- `no_audio` removes the sound calls from the game thread.
- `capture_scene_file` adds scripted input.

A downstream shift alone moves both layouts by 0–11% (64 to 4,096 bytes
tested). An order therefore has to be searched on the build that ships, and
searched again when the hot code changes size.

The shipped build has audio and no capture. A `capture_scene_file` build with
audio is needed to reach VS for tracing, and it differs from the release build
in only a few hot functions:

- `run` and `session_frame` (different sizes).
- `capture_ticks` and the `scripted_*` input functions (capture-only).

`LAYOUT_TAIL` puts these after the searched block. The 315 searched functions
then have the same address and size in the release EBOOT as in the traced
build.

### Result for the shipped build

Model misses on the audio build, `vs4@2400`, 22 frames of each window, all
three orders relinked from the same objects:

| Order | Misses | Draw-phase misses | Held-out window |
|---|---|---|---|
| HEAD | 419,746 | 321,716 | 416,780 |
| Searched for `no_audio` | 395,353 | 290,342 | 393,015 |
| Searched for this build | 331,753 | 241,803 | 332,278 |

That is 21% fewer misses (25% in the draw phase), about 4,000 fewer model
misses a frame, or about 1.5 ms a frame at the calibrated cost. The release
build has no frame timer and a `profile` build has different code, so this
number is the model's. The calibration above, three layouts on the PSP with
the same ranking, is its hardware evidence.

### Cargo did not relink after an order change

`link-order.txt` is read by the linker script, which Cargo does not track:
`cargo psp` finished in 0.12 s and kept the old layout after an edit. A
build script would make Cargo track the file, but it is ruled out
(`psp-game/.cargo/config.toml`: `cargo psp` renames the EBOOT once a package
has a second executable target). Instead, `psp-game/src/main.rs` names the
file in an unused `include_bytes!` constant, which puts it in rustc's
dep-info. An edit now rebuilds and relinks without changing the code.

## Procedure

After the hot code changes size, search the order again on the shipped
configuration:

1. Build `psp-game` with `--features capture_scene_file` (audio on) and
   `PSP_LINK_SAVE=DIR`.
2. Trace two windows under the model: `PPSSPP_ICACHE_TRACE`, scene file
   `vs4@2400`, starts 20 and 32 s.
3. List the orderable names: `tools/icache/relink.py --functions DIR`.
4. Write the tail list: every hot function whose size differs between this
   build and a plain release build (`psp-nm -S`).
5. Run `layout`, seeded with the current order, with several seeds at
   90,000 iterations, and keep the best held-out result; write it to
   `link-order.txt` (RE-496: one seed at 20,000–30,000 iterations left
   about 3.7% of the gain on the table).
6. Check it in two ways:
   - relink with `relink.py` and replay both traces;
   - compare the searched block's addresses in the release ELF with the
     relinked one.
