# RE-534 — Four-player VS on a PSP-2000: a texture bind-block cache, a CPU/GE race in `draw_rect`, and why stall batching cannot be bit-identical on PPSSPP

Status: COMPLETE (PSP-2000, 6.61 ARK, PSPLink v3.2.1, `capture_scene_file,frame_timer`, audio on, 120-frame reports; base dbee3cb)
Topics: performance, hardware, rendering, link-order
Relevant files: `psp-runtime/src/meshdraw.rs`, `psp-runtime/src/gu.rs`, `crates/ssb-rom/src/residency.rs`, `psp-game/link-order.txt`

## Question

After RE-533, what do `bind_texture` and the GE submission path cost in four-player VS, and can the GE stall-address updates be batched without changing a pixel?

## Findings

- `bind_texture` replays recorded GE words for a (texture, palette) pair. The cache is direct-mapped, 1024 slots of 80 bytes (about 80 KB of `.bss`), valid only for one pack base and one `residency::generation()`; a change of either empties it. An empty slot (`len 0`) and an unknown validity (`Option::None`) are explicit states, never a default (RE-300 rule). A live bind costs about 9.7 us, around 100 a frame. On one PRX with a file toggle the cache is -0.93 ms busy on `vs4@2400`.
- `Gpu::draw_rect` passed a stack `[RectVertex; 2]` to `sceGuDrawArray`. The GE reads vertices after the call returns, from memory and not the D-cache: the frame was reused by then, and on a PSP the lines may not have been written back. It showed in the KO screen flash (`draw_screen_flash` -> `draw_rect_translucent`), which came out as whole-picture differences when the GE ran behind. The corners now go into list memory (`sceGuGetMemory`, uncached alias). An audit of every GE-read buffer in `psp-runtime` and `psp-game` found no other stack or reused CPU buffer handed to the GE; the asset viewer's static quad and particle scratch is now copied too.
- Stall-update batching is held. With PPSSPP forced to one compute thread, the same build differs from the multithreaded run on 965 of 2402 frames: the software renderer's output depends on BinManager task ranges (`DrawRectangle` steps UV from the range-clamped start), and flush chunking, which batching changes, moves those boundaries. Single-thread stall/16 against stall/1 differs on 2 frames after the race fix (64 before), multithreaded on 741. It cannot be bit-identical on PPSSPP goldens, and it has no production route without a rust-psp change or psp-runtime-owned draw writes. The research measured -0.25 to -0.30 ms.
- Code growth broke the s7 link order: the candidate on s7 is +0.45 ms against HEAD, though the same code with the cache toggled is -0.93. A re-search (seed 11, 30,000 iterations; training vs4 20 s, opening room and Run; held out vs4 32 s) cut held-out model misses 29%. A `cargo psp` rebuild with the installed `link-order.txt` is byte-identical to the relinked PRX.
- Result on hardware (busy ms, HEAD -> final): `vs4@2400` 17.13 -> 16.46 (54.9 -> 57.9 FPS, reports 4..19); stage=1 16.18 -> 15.66; stage=4 15.78 -> 15.14; opening room 13.62 -> 12.72; opening Run 16.70 -> 15.78 (42 -> 50 FPS).
- Output is bit-identical: 2402-frame full-RGBA hashes on `vs4@2400` (0 differing frames) and 218 of 218 goldens, peak memory unchanged at 20,719,104 bytes.
- Not reproduced: the research prototype's alpha-only differences (its code was not kept).

## Conclusion

Bind-block replay is the first `bind_texture` lever and is bit-identical. Stall batching needs a hardware-only comparison method before it can be evaluated.
