# RE-480 — Four-player VS on a PSP-2000: where 18 ms of CPU goes

Status: COMPLETE (PSP-2000 PSPLink `profile` runs of `vs4@2400` without audio, PPSSPPHeadless on the same build; the `opt-level s` build's crash is not diagnosed)
Topics: performance, hardware, ppsspp, toolchain
Relevant files: `psp-runtime/src/profile.rs`, `psp-runtime/src/meshdraw.rs`, `psp-game/src/main.rs`, `psp-game/Cargo.toml`

## Question

Four-player VS runs at 40 FPS on a PSP-2000 with audio off (RE-479).
PPSSPP counts 5.4 ms of CPU a frame for it. What takes 18 ms on the
PSP, and is one fix within reach?

## Method

- PSP-2000, 6.61 ARK, PSPLink v3.2.1, 333/166 MHz. Builds from `42cd738`
  with `profile,capture_scene_file,no_audio`, started from
  `ms0:/PSP/GAME/ssb64/` with pack v108; `vs4@2400` (Mario and three
  CPUs on Dream Land), 18 two-second reports after the first.
- The same build under PPSSPPHeadless (`--feature
  capture_scene_file,profile,no_audio`), 19 reports.
- Repeated PSP runs of one build agree to 1 µs a frame on average.

## Results

µs per frame, averaged:

| Span | PSP-2000 | PPSSPP | PSP / PPSSPP |
|---|---:|---:|---:|
| Frame | 24,772 | 16,698 | 1.5 |
| CPU (update + draw − vblank wait) | 18,308 | 5,360 | 3.4 |
| Update | 4,635 | 1,419 | 3.3 |
| … interrupts | 782 | 108 | 7.2 |
| … physics | 2,167 | 790 | 2.7 |
| … hit detection | 557 | 90 | 6.2 |
| Draw, with the vblank wait | 16,697 | 15,001 | 1.1 |
| … vblank wait | 3,185 | 11,142 | 0.3 |
| … stage (links 0–8) | 3,855 | 943 | 4.1 |
| … fighters | 5,019 | 1,438 | 3.5 |
| … interface and magnifiers | 1,913 | 751 | 2.5 |
| Mesh lists: node matrices | 1,306 | 493 | 2.6 |
| Mesh lists: material state | 1,744 | 409 | 4.3 |
| Mesh lists: submission | 832 | 232 | 3.6 |
| Mesh lists: CPU skinning | 675 | 266 | 2.5 |

- **No single hot spot.** Every span costs 2.5–7× PPSSPP's count.
  PPSSPP charges about a cycle an instruction and nothing for cache
  misses or load and FPU latency. The 6–7× spans (interrupts, hit
  detection) are short loops over game structures.
- **Posing the drawn models** (a stage layer's `compose` and billboard
  scales, each fighter's `compose_model`): 780 µs a frame. The stage
  passes 0–5 Head0 and 0–5 Head1 pose the same layers twice; posing them
  once saves part of it.
- **The profiler's own cost.** `sceKernelGetSystemTimeLow` costs 0.56 µs
  on the PSP-2000, about 900 reads a frame: 0.5 ms, 3% of the CPU span.
- **`opt-level`.** `2` costs 3.6% more than `3` (19,346 against 18,675
  µs; text 2.77 MB against 3.05 MB). An `opt-level s` build (2.68 MB)
  runs under PPSSPP but takes PSPLink down on the PSP when loaded over
  `host0:`, twice out of two: the USB device re-enumerates, the shell
  never answers, and usbhostfs once logged an open request with a
  1,389-byte payload. No exception is left to read. Not diagnosed.
- **Frame pacing.** With 18–19 ms of CPU the double-buffered frame waits
  for the next vblank: 25 ms a frame on average, 40 FPS.

## PSPLink as a profiler

- `thctx` on a running game thread prints a context with EPC 0 and `ra`
  inside the stack: unusable for PC sampling on this firmware.
- Interrupting a module started with `debug` through usbgdb's remote
  protocol (`\x03`, `g`, `c` on port 10001) returned two samples, then a
  bus error in PSPLink's `GDBServer` thread (EPC `0x88218E98`, PSPLINK
  offset `0xAD98`, BadVAddr `0x02200003`).
- A `kill` of a running `profile` build hung PSPLink once (RE-479); a bare
  `reset` does not.

## Open

- The `opt-level s` build's crash on the PSP.
- What the per-span ratios come from: D-cache misses on pack reads,
  uncached list writes, or load and FPU latency. PSPSDK's profiler
  registers (`pspDebugProfilerGetRegs`, `0xBC400000`) count cache misses
  and stalls; reading them from the game is untried and probably needs a
  kernel-mode helper.

## Follow-up: stage layers posed once a frame

`draw_training`'s battle camera passes recomposed stage layers 0, 1 and 3
twice a frame (once for each pass's Head0 call, once for Head1, identical
inputs both times — PLAN.md's "stage poses links 0–5 twice"). A
`StagePoseCache` keyed by layer object slot now composes each layer once
per `draw_training` call and reuses it for the second head; `compose` and
`billboard_scales` are pure functions of the animator's already-ticked pose
and `(pack, object)`, so the two calls were always computing the same
result (`crates/ssb-rom/src/skeleton.rs`, test
`posing_a_stage_twice_gives_the_same_pose`). This matches the N64, which
also poses a `DObj` tree once per camera pass and shares the result between
both task heads (`gcDrawDObjTreeDLLinks`, `objdisplay.c:1616`).

PPSSPPHeadless, `vs4@2400`, `capture_scene_file,profile,no_audio`, steady
state (`prof n=17..19`, averaged): `compose` 356 → 337 µs/frame (−19 µs),
`dstage` 951 → 925 µs/frame (−26 µs). PPSSPP undercounts PSP cost by
2.5–7× per the table above, so the PSP-2000 saving is larger in absolute
terms than this software-rasterizer measurement shows; not re-measured on
hardware in this batch. 198/198 goldens are unchanged (pixel-identical, as
expected from a pure caching change). The cache adds up to ~18 KB to
`draw_training`'s frame (three cached `LayerPose`s, ~4.6 KB apiece); the
deepest measured game stack stays 310,912 bytes of the 512 KiB budget
(`f1-vs-sudden-death`, re-verified unchanged by the full golden run).
