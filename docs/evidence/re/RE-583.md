# RE-583 — Game-loop stack pinned in the d-cache way (batch 90)

Status: VERIFIED (PSP-2000 hardware, PSPLink, timer build)
Topics: stack, d-cache, perf, link-order
Relevant files: `psp-runtime/src/stack_pin.rs`, `psp-game/src/main.rs`, `tools/icache/stack-set.py`, `tools/psp-link.py`

## Findings

1. PSP d-cache is 16 KB, 2-way, 64 B lines: set = address mod 0x2000. Per-frame call stacks sit below `run`'s frame, so the offset of `run`'s end in the way chooses which sets frame locals share with `.bss` (RE-580) and heap.
2. Cause: `run`'s frame shrank 17280 to 15600 B (batch 90), moving its offset 0x1ad0 to 0x0160: intro +0.45 ms/frame on PSP-2000.
3. Rule: `psp_main` enters `run` through `stack_pin::enter` at way offset 0x1600 (`STACK_SET` in `psp-game/src/main.rs`); `run` asserts it (`stack_pin::check`). `enter` reads the frame size from `run`'s prologue and panics on an unknown prologue.

5. Acceptance, 0x1600 vs HEAD (2 runs each, busy ms): vs4 16.79 / 16.80 vs 16.88; intro 19.02 vs 19.11-19.14; battle 16.01 vs 16.06-16.18; Zebes 11.34 vs 11.45; opening 9.13-9.14 vs 9.15.
6. Cost: up to 0x2000 + 64 B of the 512 KiB stack unused above `run`; deepest stack 127,752 B (+896 B).
