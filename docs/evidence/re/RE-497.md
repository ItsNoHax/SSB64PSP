# RE-497 — VFPU model-matrix compose and a correctly-rounded `sqrt.s` beat a VFPU skin path

Status: COMPLETE (PSP-2000, 6.61 ARK, PSPLink v3.2.1, `profile,capture_scene_file,no_audio` builds of `vs4@2400` with pack v109 on `ms0:`, reports 1–18, interleaved rounds; each build relinked with its own searched `link-order.txt` per RE-494/RE-496)
Topics: performance, hardware, precision, vfpu
Relevant files: `psp-runtime/src/meshdraw.rs`, `psp-runtime/src/lib.rs`, `crates/ssb-rom/src/pack.rs`, `psp-game/link-order.txt`

## Question

PLAN.md's `MS8` VFPU item names two render-only matrix hot paths: the
per-node model-matrix compose (`compose_model_matrix`) and skinned-vertex
expansion (`CachedVertexPose::pose`). D-032 requires profiling before any
VFPU change; RE-487 already replaced `sceGumMultMatrix`'s `vmmul.q` with
scalar code because `sceGum*`'s per-call `vfpu_context` save/restore cost
more than the multiply. Does a hand-written VFPU routine that skips
`vfpu_context` entirely win back that trade, and does VFPU pay off in the
skin loop too?

## Findings

### Path A: raw `vmmul.q`, no `vfpu_context`, wins

`compose_model_matrix` (`meshdraw.rs:2291`) now loads `base`/`local` with
`lv.q` into VFPU banks 5–7 and issues one `vmmul.q M700, M500, M600`
directly via `psp::vfpu_asm!` (`#![feature(asm_experimental_arch)]`,
`psp-runtime/src/lib.rs:8-9`) — no `sceGum*`, no
`psp::sys::vfpu_context::prepare`, nothing held across calls. `sceGum*`
keeps its own state in VMAT0–3 (VMAT3 = current matrix); `psp::math` uses
only S000/S001 (VMAT0). Banks 5–7 don't overlap either, so the billboard
arm's still-`sceGum*`-based `load_billboard_matrix` cannot alias it and it
cannot clobber gum — no held/reserved-bank scheme (as originally planned)
was needed; per-call `lv.q`×8 + `vmmul.q` + `sv.q`×4 is already the win.
`ScePspFMatrix4` is 16-byte aligned, so `lv.q`/`sv.q` (not the unaligned
`ulv.q`/`usv.q`) are safe. Both the game thread and the audio thread run
with `ThreadAttributes::VFPU`, so the kernel saves VFPU state across
context switches.

On the PSP-2000, relinked and run interleaved against HEAD (`rB0`,
56.51/56.52 FPS) with its own searched link order: **+0.70 FPS, −219 µs a
frame, node-matrix span −180 µs** (`rV1`, 57.06–57.21 FPS).

### Skinning: the lever was `sqrtf`, not the matrix math

`Span::Skin` cost 614–647 µs a frame (~4% of frame time) on hardware —
measurable, unlike RE-471's PPSSPP-only "not measurable" finding, which
predates the per-joint `CachedVertexPose` cache. Disassembly of the skin
loop showed most of that time in two calls to `libm` 0.2.16's software
`sqrtf` (`multu`-based, ~0x18c bytes of MIPS), not the matrix multiply or
dot products.

`CachedVertexPose::pose` (`crates/ssb-rom/src/pack.rs`) now forwards to a
new `pose_with_sqrt(vertex, binding, sqrt: impl Fn(f32) -> f32)`
(`#[inline(always)]`); `pose` itself still passes `libm::sqrtf`, so
`ssb-rom` stays PSP-free and host/gameplay behaviour is unchanged. The
skin loop (`meshdraw.rs`, called from `draw_node_mesh`) passes a one-line
`fpu_sqrt` closure around a single Allegrex `sqrt.s`. On top of path A
(`rS`, 57.57/57.64 FPS): **+0.45 FPS, ~−150 µs a frame, skin span −200 µs**
(422 µs down from 621 µs, and from 647 µs against HEAD).

Overall `rB0` → `rS`: 56.5 → 57.6 FPS on PSP-2000 `vs4@2400`, each build
relinked to its own searched link order (RE-494/RE-496's procedure; an
order fits only the build it was searched on).

### Negative result: VFPU `vtfm` skin path is slower on hardware

A per-joint-resident VFPU vertex-transform variant was also written and
measured: `vtfm4.q` (position) and `vtfm3.t` (inverse-transpose normal) on
column-loaded per-joint pose matrices held in VFPU banks across a joint's
whole vertex run — the exact shape `n64psp`'s `tnl_vfpu.S` uses, and the
shape `CachedVertexPose` already has at the Rust level (matrix built once
per joint, `.pose()` called per vertex). It is bit-exact under PPSSPP, but
on hardware the skin span got **slower**, not faster: 579 µs against
422 µs for the scalar-plus-`sqrt.s` version. The per-vertex `mtv`/`mfv`
moves between the integer/FPU and VFPU register files outweigh saving
nine scalar multiply-adds. It also introduces hardware-only rounding
drift not present in the shipped scalar path (below). Reverted; not
shipped. This closes the `MS8` item's path-B half as "profiled and
rejected," consistent with D-032 — VFPU is not a blanket win, even for a
hot per-vertex loop shaped exactly like a known-good reference kernel.

### PPSSPP cannot see VFPU rounding at all — a golden blind spot

A hardware self-test compared the VFPU `vmmul.q` compose against the
scalar compose on real matrices: of 3,840,000 matrix elements, 312,157
differ in their low bits, and 967 (0.025%) still differ after the GE's
`>>8` truncation of the f32 mantissa. Under PPSSPP, the same comparison
found **0** differences — PPSSPP's software VFPU emulates `vmmul.q`/
`vtfm` as bit-identical in-order scalar sums; the PSP-2000's real VFPU
does not. Every golden in this project is a PPSSPP pixel hash
(`tools/golden.sh`), so **no golden can ever detect a VFPU rounding
regression** — only a hardware A/B (as done here) can. This is a
standing gap for any future VFPU work, not specific to this batch.

This is also why the rejected `vtfm` skin path's extra rounding mattered
only on hardware: 5 of 160,000 position components differed by ±1 unit
after `i16` quantization (normals identical) — invisible to every golden
run during that experiment, consistent with the blind-spot finding above.

### Allegrex `sqrt.s` is correctly rounded

A hardware self-test ran `sqrt.s` against exact `f64`-computed bounds for
249,001 inputs: 0 incorrectly rounded results. `libm::sqrtf` (used by
`ssb-rom`'s scalar `pose`) is also correctly rounded, so `fpu_sqrt` is
bit-identical to it, and skin output is unchanged on both PPSSPP and
hardware. A new host test,
`pose_with_a_correctly_rounded_sqrt_matches_pose` (`pack.rs`, 20,000
random vertices/bindings, `f64`-rounded sqrt compared against `pose`,
bit-exact), pins this contract so a future `libm` version or scalar
refactor can't silently drift from the PSP's `sqrt.s`.

### Goldens and movie/opening spot-check

`tools/golden.sh verify` ran the full 198-scene matrix after these
changes: 198/198 match (see STATUS.md's verification baseline). No golden
in `tests/golden/scenes.tsv` captures the animated opening/movie draw
path (`Span::MovieMesh`) — only `r1-mvopeningroom`, a static room. As a
stopgap, native PNG sha256 prefixes of `opening@3000` and `op-jungle@1200`
were captured for HEAD, the path-A-only build and the shipped build: all
three builds produced identical hashes (`aea6b9347526ff24`,
`ef3f2a3aff3ec381`) — no pixels changed, nothing rebaselined, but this is
a manual check, not a regression-tested golden (see Consequences).

## Consequences

- `compose_model_matrix` ships unconditionally as a raw VFPU routine (no
  feature gate — the originally-planned `vfpu_matrix` Cargo feature
  turned out unnecessary since hardware shows a clear gain and goldens
  are unchanged); the scalar version is deleted, not kept as a dual path,
  per this project's established convention (RE-487/488/493).
  `psp-runtime/src/lib.rs` gained
  `#![feature(asm_experimental_arch)]`.
- The skin loop's scalar math is untouched; only its `sqrtf` call is
  swapped for a PSP closure passed in from `psp-runtime`, keeping
  `ssb-rom` PSP-free per the crate-ownership table. `CachedVertexPose`'s
  public contract (`pose`) is unchanged for every other caller/test.
  `ssb-rom`'s own `cargo test -p ssb-rom` (739 passed with the ROM) still
  exercises the scalar path as ground truth.
- VFPU vertex transform (path B as originally scoped) is a closed
  negative result: do not retry `vtfm`-based skinning without a new
  reason to expect per-vertex `mtv`/`mfv` overhead to behave differently.
  `ssb_engine::math::sqrt`'s four divisions ([PLAN.md](../../PLAN.md))
  remains open and unrelated.
- `psp-game/link-order.txt` was re-searched (RE-494/496's procedure, 12
  seeds × 90,000 iterations from the new code's own start point) because
  `compose_model_matrix`/`pose_with_sqrt` changed hot-function sizes;
  seed 8 won on both train (314,313) and held-out (318,144) misses, 21.6%
  below the pre-search order re-scored on the new code shape. Verified
  per RE-494 step 6: `relink.py`'s replay reproduced `layout`'s own
  misses exactly (train) and within 0.03% (held-out, consistent with
  RE-496's documented small overestimate); a real `cargo psp --release`
  build using the installed order is byte-identical to the relinked ELF.
- Standing gap: PPSSPP cannot show a VFPU rounding regression in any
  golden. Any future VFPU work needs its own hardware self-test
  (instruction-by-instruction against the scalar path, as done here and
  per `refs/sf64-psp/docs/corneria_streak_postmortem.md`'s verification
  method) before trusting a passing golden matrix alone.
- Follow-ups not done in this batch: measure the billboard arm's
  still-`sceGum*`-based `load_billboard_matrix` (never profiled in
  isolation); add a movie/opening golden so the stopgap manual hash
  check above has a regression test (`docs/visual-regression/README.md`
  owns this); the link-order re-search's own replay scorer
  (`<scratchpad>/replay.py`, not added to `tools/icache/`) should move
  into the repo's tooling in a future batch rather than being rewritten
  from scratch each time, per RE-496's own gap.
