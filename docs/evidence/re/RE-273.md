# RE-273 — First physical confirmation on a second hardware unit (PSP-3000)

Status: COMPLETE
Topics: hardware, visual-regression, fighter, psp-ge, stage
Relevant files: psp/src/gu.rs, psp/src/depth_diag.rs

**Question.** All prior physical-PSP evidence (`RE-201`-`RE-271`) used one
PSP Slim, firmware 6.61. Does the renderer hold on a second, different
physical unit?

**Setup.** PSP-3000 ("Brite"), ARK/Infinity CFW (`InfinityControl`/
`ARKCompatLayer` modules present, same CFW family the Slim runs), PSPLink
v3.2.1, `usbhostfs_pc`/`host0:` session, same repository checkout (commit
`470ce1b`), same pack (`a79b0aa9...5935f`, already present and byte-matching
before this session — no rebuild needed). `sceWlanFirmVoyager_driver` in
`modlist` confirms this is the 64 MiB-RAM class (2000/3000), not the 32 MiB
PSP-1000 `STATUS.md` names as the still-open hardware gap — this session
does not close that gap.

**Coverage.** Built `regression_capture` (scene1, Dream Land), booted,
zero exceptions (`exlist` empty, `main_thread` alive), captured, upscaled
2x nearest-neighbour and diffed against `tests/golden/r0-dream-land-default.png`:
58,756/522,240 differing pixels, visually confirmed as the same edge-
antialiasing/PSPLink-overlay noise class prior sessions established (e.g.
`RE-210`'s 50,323/522,240 on the Slim), not a corrupted region.

Built `depth_mask_diagnostic` (the scene `RE-271` found a real
`draw_triangles` GE-race bug in and fixed), zero exceptions, captured,
diffed against `tests/golden/r2-depth-mask-diagnostic.png`: 628 differing
pixels — the exact count `RE-271` measured post-fix on the Slim. Confirms
the fix holds on this second unit; no regression.

Built `regression_capture_mario`, zero exceptions, captured, diffed against
`tests/golden/r2-mario-fighter.png`: 40,732/522,240 differing pixels, within
`RE-271`'s established fighter-capture noise range (25,136-40,328/522,240).
Zoomed visual inspection during this capture is what surfaced `RE-272` (a
real, pre-existing face-texture rendering bug, unrelated to and not caused
by this hardware unit — see that record).

Ran the plain feature-free EBOOT (hash `66ce9869...a5336`, byte-identical to
`STATUS.md`'s recorded build — confirms no code drift since `RE-271`) for a
10-minute continuous sustained session, checking `exlist`/`thlist`/`usbstat`
at the 0-, 5- and 10-minute marks: zero exceptions throughout, `main_thread`
alive, USB connection stable. Final screenshot shows Dream Land rendering
intact, no VRAM corruption or leak artifacts, matching `RE-271`'s own
10-minute Slim result.

**Conclusion.** The renderer, the `RE-271` `draw_triangles` fix, and 10
minutes of sustained operation all hold on a second physical PSP unit
(PSP-3000) with no new hardware-specific failure. PSP-1000 (32 MiB RAM,
`MEMSIZE=1` incompatible) remains the only physical-unit gap `STATUS.md`
tracks; this session does not close it. This session's real finding is
`RE-272`, not a hardware-compatibility issue.

**Confidence: high** — zero exceptions across three feature builds and one
10-minute session on a unit never tested before, diff counts matching
established per-scene noise baselines from the Slim, byte-identical builds
confirming no code drift.
