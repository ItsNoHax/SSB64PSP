# RE-280 — Root cause found: `Ci4`/`PsmT4` packing uses the wrong nibble order for the PSP GE

Status: COMPLETE — fix applied and confirmed, see RE-281
Topics: texture, fighter, hardware, visual-regression, asset-pipeline
Relevant files: psp/src/tri_addr_diag.rs, crates/ssb-rom/src/psp_texture.rs

**Question.** RE-278 cleared the addressing formula and fixed-coordinate GE
sampling for RE-272/274's Mario-face bug; RE-279 cleared the signed-UV float
path. Two candidates remained, both named in RE-278's own conclusion: real
per-pixel triangle interpolation of a wide UV delta, and the actual `Ci4`
(4-bit paletted, CLUT-indexed) bind path -- neither tested by RE-278's
fixed-coordinate, plain-`Psm8888` rig.

**Measurement.** Built `psp/src/tri_addr_diag.rs` (`tri_addr_diag_probe`
feature): two real screen-space triangle quads (`GuPrimitive::Triangles`,
matching `draw_mesh`'s real topology, not a degenerate sprite) whose corners
carry different `u` values spanning RE-274's own `-31..90` texel range, drawn
through the real `Ci4`/CLUT bind sequence (`sceGuClutMode`/`sceGuClutLoad`/
`PsmT4`, matching `meshdraw::bind_texture`) against a synthetic 64-texel
texture baking a period-16 sawtooth index pattern (`idx(i) = i % 16`,
deliberately not a smooth ramp, so the sharpest possible index jump lands
inside the interpolated span at texels 31/32). A 16-entry CLUT maps index
`i` to red channel `i * 17`, decoding the sampled index directly from the
captured screenshot.

Three readbacks, one capture (`tools/run-ppsspp-headless.sh --feature
tri_addr_diag_probe`, EBOOT `473f655a...4de06ae`, screenshot
`cb345659...4638`):

1. **Interpolated `Ci4`, Nearest filter** (`draw_quad`'s row): every probe in
   `PROBES` mismatched its prediction (`(clamp(addr,0,63) % 16) * 17`) --
   e.g. texel `5` predicted `85`, read `68`; texel `31` predicted `255`, read
   `238`; texel `32` predicted `0`, read `17`.
2. **Interpolated `Psm8888` control** (`draw_quad`'s third row: identical
   geometry, identical `baked_index` pattern, no CLUT/no nibble packing):
   read back as a *perfect* linear ramp, `0, 17, 34, .., 255`, wrapping
   exactly every 16 texels -- ruling out triangle-interpolation precision
   entirely. The bug is specific to the paletted path.
3. **Fixed (non-interpolated) `Ci4` probes** (`draw_fixed_probes`, the one
   case RE-278's rig never covered because it only bound `Psm8888`):
   mismatched too, with **no interpolation involved at all** -- e.g. texel
   `0` predicted `0`, read `17`; texel `45` predicted `221`, read `204`.

The interpolated-row mismatch is not noise: scanning the whole row
(`x=106..296`) shows a clean, periodic saw, `0, 51, 34, 85, 68, 119, 102,
153, 136, ...` -- alternating +51/-17 every pixel, repeating every 48
screen pixels (16 texels x 3 px/texel). That shape, plus the fixed-probe
mismatch, both point at the same mechanism: **every other texel reads the
wrong nibble of the right byte.**

**Confirmed decisively.** Rebuilt `TEXTURE` with the two nibbles swapped
(`(lo << 4) | hi` instead of the shipping `(hi << 4) | lo`) and re-ran:

* Fixed probes: **12/12 exact matches** against prediction (was 2/12,
  and those 2 were the clamp-to-zero cases).
* Interpolated Nearest row: became the same clean linear ramp the
  `Psm8888` control already showed.

The temporary swap was reverted (this rig ships testing the *currently
shipping* order, so it keeps failing -- and keeps proving the bug is real --
until the real fix lands).

**Root cause.** `crates/ssb-rom/src/psp_texture.rs` packs two 4-bit texels
per byte "high nibble first, matching the N64 order" at three coordinated
sites, all sharing the same (wrong, for the PSP GE) convention:

* `encode_level`'s `PsmT4` branch (~line 1717-1727): `x % 2 == 0` writes the
  *high* nibble.
* `pack_indexed`'s straight ROM-copy path (~line 731-732): copies raw ROM
  nibble-packed bytes through unchanged, on the explicit assumption "which is
  also what the PSP expects for PsmT4."
* `pad_edge_repeat_nibbles` (~line 609-635): its internal `get`/`set`
  closures also treat an even texel index as the high nibble, so it stays
  internally self-consistent with `encode_level` but would need to flip in
  lockstep with it.

PPSSPP's `PsmT4` texture reader (the deterministic golden source this
project already treats as ground truth for GE addressing behaviour, RE-278)
reads the *opposite* order: low nibble is the first (even-indexed) texel,
high nibble is the second (odd-indexed) texel. Because this convention is
baked into pack-time conversion itself -- used identically for both this
project's real PSP path and PPSSPP -- every `Ci4`-formatted texture the game
ships (every fighter face, among others) has had every adjacent texel pair
silently swapped since this pipeline was built. The existing host-side test
`ci4_packing_round_trips_through_swizzle_and_clut` (and its `unpack_ci4` test
helper, both in `psp_texture.rs`) only proves the pack step is
self-consistent with itself; it hand-constructs its input indices in the
same (wrong) convention, so it cannot catch this.

This plausibly explains RE-272 in full: adjacent-texel-pair corruption reads
exactly as the "repeating, aliased pattern with red patches" RE-272
described; it is most visible on sharp high-contrast content (an eye/eyebrow
outline against skin) and least visible on smoothly-shaded content, which is
why no other fighter's face had previously drawn a complaint even though
every one of them is equally affected; and it is invisible to the
regression-capture goldens by construction, exactly as `TODO.md` already
notes -- both the real PSP path and PPSSPP apply the identical wrong order,
so the two sides of every self-consistency comparison still agree with each
other, just not with the source ROM texture.

**Not yet done.** The fix itself (flip the nibble order at the three sites
above, in lockstep) has not been applied. `PsmT8` (one texel per byte) is
unaffected; this is a pack-time change that touches every `Ci4` (`PsmT4`)
texture the archive packs, which means: rebuilding `assets/generated/
ssb64.pak` afterward, and likely refreshing a
meaningful fraction of the 22 deterministic regression goldens (their stored
reference PNGs were captured under the current, wrong nibble order — a
pack-time fix changes rendered pixels for every affected texture, which is
an expected, explainable consequence per the visual-regression skill's own
rule, not a regression). That is real, non-trivial scope deserving its own
dedicated pass rather than folding into this measurement session.

**Confidence: high.** The swap-and-reconfirm test is about as decisive as a
measurement gets: 12/12 fixed-probe matches, a control texture that isolates
interpolation from the paletted path, and a shape (periodic every-other-texel
saw) that has no other obvious explanation. Not yet confirmed on physical
PSP hardware -- only PPSSPP's software rasterizer -- though this project's
existing precedent (RE-272 itself: "reproduces on PPSSPP too, so not
hardware-specific") treats that as strong evidence the same bug is real on
real hardware too, since both consume the identically-packed byte stream.

**Closed by RE-281.** The identified fix was applied at all three sites,
`assets/generated/ssb64.pak` rebuilt, and 18 of the 22 deterministic goldens
refreshed with their semantic delta explained (a texture-pixel correction,
not a regression). Mario's face/cap texture, RE-272's original complaint,
visibly no longer shows the repeating artifact. See RE-281 for the full
account.
