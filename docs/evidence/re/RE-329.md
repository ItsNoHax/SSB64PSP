# RE-329 — Blocking controller read causes the viewer's tick spiral

Status: COMPLETE (PSP-2000 interleaved scan A/B and per-section timing; 3,600-tick replay)
Topics: hardware, input, timing, performance, viewer
Relevant files: `psp-runtime/src/input.rs`, `psp-asset-viewer/src/main.rs`

**Symptom.** RE-322 measured the stage viewer's simulation cost near 4 ms
per tick at frame 1,200 and later observed about four catch-up ticks per
display frame. The stage view polls the controller once per fixed tick.
`PspInput::poll` used `sceCtrlReadBufferPositive`, which waits for a new
controller sample. Once a slow frame produces multiple catch-up ticks,
each read can wait for another sample and make the next frame slower.

**Investigation.** On the connected PSP-2000 Slim (firmware 6.61 ARK,
PSPLink v3.2.1), the pack was v36 plus RE-328 (`a5eacfa2…`). A temporary
diagnostic PRX, removed after measurement, ran stage 40 with 600-tick
windows and wrote timing outside each measured window to `host0:`.
First, adding two discarded `stage_anim` table scans on alternating windows
showed the redundant lookup cost: 3,580 µs/tick with the scans in ticks
1–600 versus 1,734 µs/tick without them in ticks 601–1,200. Despite that
improvement, the cached path reached 9,582 µs/tick in ticks 1,801–2,400
and 12,366 µs/tick in ticks 3,001–3,600. The lookup was a cost, not the
growing cause.

A second diagnostic split each tick by component. Before the input change,
ticks 1–600 averaged 1,381 µs (controller 375, fighter 164, material 810,
stage 1). By ticks 1,801–2,400 the total reached 9,878 µs: controller
polling alone was 8,904 µs while fighter, material and stage stayed at
163, 783 and 1 µs. All 273 display frames in that late window ran more
than one catch-up tick. The player remained at y=4,650, ruling out a
growing off-stage collision path. Long replays of stage and material
scripts returned no errors.

**Fix.** The shared PSP input backend now calls
`sceCtrlPeekBufferPositive`, which reads the latest controller sample
without waiting. If it returns no sample, the previous state is retained.
The viewer also caches its stage animation descriptor when the stage changes,
removing the two per-tick table scans. Repeated samples during catch-up
produce no new button edge.

**Hardware result.** With the same pack and timing probes, PRX SHA-256
`50ce3740…`, ticks 1–600 averaged 1,034 µs, and every subsequent
600-tick window through tick 3,600 averaged 1,026 µs. Controller polling
held at 7 µs/tick, with zero dropped ticks. At most one of roughly 600
display frames per window had multiple ticks. `exlist` stayed empty.
The production PRX was rebuilt without the timing probes and with the
no-sample guard (SHA-256 `5c4d348b…`), loaded from `host0:`, and opened the
pack. `exlist` was empty and `main_thread` alive. The preceding production
build displayed Dream Land from the same pack in a hardware screenshot
(`6747084a…`). The shared input change affects
`psp-game` as well; both PSP applications build, and all 68 viewer/game
goldens match twice in PPSSPP software.

**Limit.** This is one PSP-2000 and one idle stage-view scene, not a
30-minute run or second-unit acceptance test. Those remain deferred in
`TODO.md`.
