# RE-281 — RE-280's `Ci4`/`PsmT4` nibble-order fix applied, pack rebuilt, 18/22 goldens refreshed and explained

Status: COMPLETE
Topics: texture, fighter, hardware, visual-regression, asset-pipeline
Relevant files: crates/ssb-rom/src/psp_texture.rs, assets/generated/ssb64.pak, tests/golden/*.png

**Question.** RE-280 found and decisively confirmed the root cause of RE-272's
fighter-face artifact (`Ci4`/`PsmT4` packing used the N64's high-nibble-first
convention when the PSP GE — and PPSSPP's reader — wants low-nibble-first)
but did not apply the fix, per its own explicit scoping. This closes that
remainder: apply the fix, rebuild the asset pack, refresh whichever goldens
change, and visually confirm Mario's face specifically.

**Fix applied.** All three coordinated sites in `psp_texture.rs` flipped
together, in lockstep, to the corrected (low-nibble-first) convention:

* `encode_level`'s `PsmT4` branch: `x % 2 == 0` now writes the *low* nibble
  (was high).
* `pack_indexed`'s straight ROM-copy path: previously copied raw ROM
  nibble-packed bytes through unchanged on the (wrong) assumption that the
  N64's high-nibble-first order already matched the PSP's. Now swaps each
  copied byte's nibbles (`(b << 4) | (b >> 4)`) so the ROM's high-nibble-first
  input becomes low-nibble-first output.
* `pad_edge_repeat_nibbles`'s internal `get`/`set` closures: flipped in
  lockstep so odd/even texel-to-nibble mapping stays self-consistent with the
  other two sites.

The test-only `unpack_ci4` helper (`psp_texture.rs`'s `tests` module) and
`ci4_packing_round_trips_through_swizzle_and_clut` were updated to the
corrected convention too, per RE-280's own naming of this as the fix's
required test update — `unpack_ci4`'s decode order flipped to match the new
PSP output; the round-trip test's own input-construction loop (which builds a
synthetic N64-native, high-nibble-first index stream to simulate what
`pack_indexed`'s ROM-copy path receives) needed no change, since the fix now
swaps that same input during packing. Four literal-byte-value assertions in
`mip_tests` and the direct `pad_edge_repeat_nibbles` unit tests were updated
to the new expected byte values (derived by hand from the new convention, not
copied from a run) — two of the four padding-byte assertions were unchanged
by construction, since a padding nibble that repeats an edge nibble equal to
its own byte's other nibble produces the same byte under either nibble order.

**Semantic delta (applies uniformly to all 18 changed goldens).** Every
changed pixel traces to the same single cause: every `Ci4`-textured primitive
in the affected scene now decodes with the corrected (PSP-GE-matching)
nibble order instead of the previous adjacent-texel-pair swap. This is a
texture-pixel *correction*, not a rendering regression — no geometry,
lighting, depth, material, or animation code changed. The 4 unchanged scenes
(`catch-swirl-flat-color`, `depth-mask-diagnostic`, `dk-fighter`,
`kirby-fighter`) are consistent with this: a scene draws 0 differing pixels
either because it has no visible `Ci4` content in frame, or because its
specific `Ci4` bytes happen to have both nibbles equal (a byte like `0xAA`
swaps to itself), which RE-280 itself predicted ("least visible on
smoothly-shaded content"). This does not mean Donkey Kong or Kirby's face
textures were unaffected by the underlying bug — RE-280 measured the defect
as archive-wide — only that this specific frozen pose's on-screen `Ci4` bytes
happened not to change value under the swap.

**Visual confirmation (RE-272's original complaint).** Direct comparison of
the old and new `r2-mario-fighter.png`: the old golden's cap emblem (the
white "M") shows a jagged, aliased zigzag pattern — the classic
adjacent-texel-pair-swap signature RE-280 predicted. The new capture shows a
clean, correctly-rounded "M" with no repeating artifact. This is the same
class of defect RE-272 originally reported (a `Ci4`-texture readback showing
a periodic swap artifact), now visibly gone on the fighter this project's own
regression matrix already tracks.

**Determinism reconfirmed after the change.** Per this project's own
established practice (RE-123), two of the changed scenes
(`regression_capture`/Dream Land and `regression_capture_mario`) were
rebuilt and re-captured a second time (real rebuilds, not `--no-build`
reruns) and diffed against the first post-fix capture: 0 differing pixels
both. (An initial `--no-build` attempt at this check produced a large,
spurious diff — traced to reusing a stale EBOOT built for an unrelated
feature, not nondeterminism; discarded once identified.)

**Permanent diagnostic rig updated to match.** `psp/src/tri_addr_diag.rs`
(RE-280's `tri_addr_diag_probe` rig) hand-builds its own `Ci4` texture bytes
rather than going through `psp_texture.rs`, so it needed its own convention
flipped to `TEXTURE`'s `ensure_built` (now packs low nibble first,
permanently, instead of deliberately shipping the pre-fix order) plus an
updated module doc. Re-ran it post-fix and sampled all 12
`draw_fixed_probes` pixels directly from the PPSSPPHeadless capture:
**12/12 exact matches** against `(clamp(addr,0,63) % 16) * 17`, the same
result RE-280's original temporary swap-and-reconfirm found. The rig is now
a standing regression guard on the real GE's nibble-read behavior,
independent of `psp_texture.rs`'s own conversion path.

**Plain build reconfirmed.** `cargo psp --release` (no regression-capture
feature) built clean after the golden refresh, per the visual-regression
skill's own "always follow a regression-capture run with a plain build"
rule. EBOOT SHA-256
`9b9bfb8f94730a47ea04e50cb2a75a8d91536bd9b13f74682256a3ebe902ca8c`.

**Confidence: high.** This closes the fix side of the RE-272→RE-280 chain:
the fix is applied at all three coordinated sites, the whole workspace test
suite and the full 22-scene deterministic matrix both pass, every changed
golden's delta traces to one already-understood cause, and the original
named complaint (Mario's face/cap texture) visibly no longer shows the
artifact. Not yet confirmed on physical PSP hardware — this fix has not been
tested outside PPSSPP's software rasterizer — though RE-272 itself already
established the bug reproduces identically on PPSSPP and real hardware (both
consume the same packed byte stream), so this project's own existing
precedent treats that as strong evidence the fix carries over. A dedicated
physical-hardware recapture is deferred to the same physical-PSP-matrix
follow-up `STATUS.md` already tracks (PSP-1000 access), not a new blocker.
