# RE-272 — Fighter face textures show a repeating/aliased artifact absent from the raw ROM texture

Status: OPEN
Topics: texture, fighter, hardware, visual-regression, geometry
Relevant files: crates/ssb-rom/src/mesh.rs, tools/romtool/src/main.rs, psp/src/meshdraw.rs

**Question.** A user visually inspecting a zoomed physical-PSP-3000 capture
of Mario's `regression_capture_mario` scene (`docs/evidence/re/RE-271.md`'s
own capture method) reported the face looked wrong: a dense zigzag of
dark/blue stripes across the forehead and unexplained red patches near the
ears, instead of two clean eyes and eyebrows. Is this a real rendering bug,
or expected low-res N64 texture noise?

**Measurement.** Dumped Mario's eye/eyebrow texture directly from the ROM
(`romtool texdump ... --file 296`, file 296 offset `0x6F98`, `Ci4 32x32`,
palette-resolved the way `pack` resolves it — not a bare unpalettised dump).
The raw decoded texture is clean: one eyebrow arch, one eye (white sclera,
blue iris), correct skin tone, no noise, no red patches.

Both the physical PSP-3000 capture (this session) and the already-`COMPLETE`
PPSSPP golden (`tests/golden/r2-mario-fighter.png`, built by `RE-265`,
re-confirmed on physical Slim hardware by `RE-271`) show the same corrupted
region: the small eye/eyebrow texture appears to repeat several times across
the forehead instead of once per eye, plus red discoloration near the ears
not present in the source texture. Since PPSSPP headless runs this project's
actual PSP renderer code under emulation, both captures exercise the same
code path — this is not new to PSP-3000 or this session, and predates
`RE-265`/`RE-271`'s "visual inspection confirms every model, colour and
texture matches" conclusion. That conclusion checked PSP-hardware-vs-PPSSPP
self-consistency (both platforms run the same renderer), which this artifact
satisfies while still being wrong relative to the source texture — the
regression-capture methodology cannot by construction catch a bug baked into
the shared renderer since before the golden was captured. `docs/porting-
status.md`'s "Known gaps" section does not list this.

**Not yet root-caused.** Candidates not yet distinguished: UV/tile addressing
on this primitive (`R2.0`/`R2.1`'s addressing work covered other axes and
scale modes, not necessarily this specific small-texture case), texture
scale/wrap mode, or a mipmap/minification interaction (`RE-213` found this
game selects no conventional mip chain — constant LOD, max-mip 0 — so a
naive minification-aliasing theory needs checking against that finding, not
assumed). No fix attempted; this record only pins the measurement, per this
project's "measure, then open a follow-up" convention (`R2.0`/P0b -> P0c/P0d,
`R2.2`/C1 -> C2, etc.).

**Scope.** Affects Mario's face texture at minimum; not yet checked against
other fighters or textures of similar size/detail. Since the regression-
capture goldens cannot detect this class of bug by construction, other
fighters' captures matching their own goldens is not evidence they are
unaffected.

**Conclusion.** Real, unfixed rendering-correctness bug, independent of the
PSP-1000/physical-hardware-matrix work `plans/rendering/R2.md` currently
tracks. Needs its own scoped investigation: identify the exact primitive/
texture-state (`G_SETTILE` mask/shift/scale, UV coordinates) for this draw
call, compare against the `n64_addressing` reference model `R2.0`/P0b built,
and determine whether other fighters' face/detail textures share the same
defect before concluding root cause. Recorded in `TODO.md`.

**Confidence: high** on the measurement (raw texture demonstrably clean,
rendered output demonstrably not, on two independent platforms running the
same code); root cause is open.
