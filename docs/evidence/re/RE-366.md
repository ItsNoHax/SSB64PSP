# RE-366 — Remaining shared status clips

Status: IMPLEMENTED (decomp tables, host tests, pack v48 rebuilt from the ROM, both PSP builds, full PPSSPPHeadless golden matrix, PPSSPP boot smoke; no physical PSP)
Topics: animation, pack, status machine, items, shield
Relevant files: `tools/gen-anim-table.py`, `crates/ssb-rom/src/{anim,anim_table,pack}.rs`, `crates/ssb-game/src/status.rs`, `tools/romtool/src/main.rs`

## Question

After RE-355, which shared statuses still fell back to the Wait slot, and
which clip does each one play? The TODO named guard, teeter, pipe, item and
hammer statuses.

## Source

`dFTCommonActionStatusDescs[status − 6]` in `ftcommonstatus.h` names each
status's `FTCommonMotion`, and `dFT<Name>MotionDescs` names the figatree.
This is the same pairing RE-351 and RE-355 use.

The statuses that still fell back, with their motion:

| Statuses | Motion |
|---|---|
| `RebirthDown`/`Stand`/`Wait`, `WalkEnd`, `TurnRun`, `GuardKneeBend`, `GuardPass`, `OttottoWait`, `Ottotto`, `Twister`, `DokanStart`/`End`/`Walk`, `LightGet`, `HeavyGet`, `LightThrowDrop`…`FireFlowerShootAir` (104–145), `HammerWait`, `HammerWalk`, `GuardOn`, `GuardOff`, `ThrownKirbyStar`, `ThrownCopyStar`, `YoshiEgg`, `CaptureCaptain`, `ThrownDonkeyUnk` | Their own motion |
| `HammerTurn`, `HammerKneeBend`, `HammerFall`, `HammerLanding` | `HammerWalk` |
| `CaptureKirby` | `DamageFall` |
| `CaptureYoshi` | `CapturePulled` |
| `SquatRv` | Its own motion, which already had slot 4 but no status mapping |
| `TaruCann`, `DokanWait`, `Guard`, `GuardSetOff`, `CaptureWaitKirby` | -1 (keep the clip) |
| `LiftWait`, `LiftTurn` | -2 (keep the clip) |

A status with motion -1 or -2 loads no new figatree. It keeps the previous
clip, so it maps to that clip's slot:

- `DokanWait` follows `DokanStart`.
- `LiftWait` follows `HeavyGet` (`ftcommonget.c`), and `LiftTurn` follows
  `LiftWait`.
- `Guard` follows `GuardOn` (`ftCommonGuardOnProcUpdate`), and
  `GuardSetOff` follows `Guard`.
- `CaptureWaitKirby` follows `CaptureKirby`.

`TaruCann` can be entered from any status, so no single slot names its
kept clip. It keeps the Wait fallback, and the barrel hides the fighter.

## Implementation

- `TAIL_COMMON_SLOTS` adds 66 slots after `MarioAttack13`, in status order
  (`SLOT_REBIRTH_DOWN` = 541, `SLOT_LIGHT_THROW_DROP` = 556,
  `SLOT_GUARD_ON` = 600). `SLOT_COUNT` is 607 and pack `VERSION` is 48.
- All twelve playable fighters have every new slot, except Pikachu, whose
  `YoshiEgg` motion is null.
- `Status::anim_slot` maps the statuses above. `AnyStatus::keeps_motion`
  adds `CaptureWaitKirby`, `DokanWait`, `LiftWait`, `LiftTurn`, `Guard` and
  `GuardSetOff`.
- The generator also marks `LEADING_RUNTIME_JOINT` with
  `allow(clippy::large_const_arrays)`, like the other two tables. At 607
  slots it passes Clippy's size limit.

## Deviations that remain

- **Shield tilt.** During `GuardOn`, `ftCommonGuardUpdateJoints` layers the
  per-fighter `shield_anim_joints[angle]` event onto `YRotN`. `Guard` and
  `GuardSetOff` then replace every joint's pose with those events, blended
  toward the rest pose by `shield_rotate_range`
  (`ftCommonGuardInitJoints`). The port plays `GuardOn` and holds its last
  frame. The stick-driven shield tilt is not ported.
- **Start frame.** Some statuses start their clip at a frame other than 0:
  `RebirthDown` at 100, the hammer statuses at the hammer clip's frame, the
  gun and Fire Flower shots at the current frame, and the walks and `Pass`
  at their `anim_frame_begin`. `set_status` takes `anim_frame_begin` but
  does not store it, and `tick_skeleton_animation` always starts at frame 0.
  This gap predates this batch.

## Verification

- `romtool anims --verify`: 27 fighters decode, and 2,407 lengths agree
  with the decompilation (1,727 in RE-355).
- The new test `remaining_common_slots_match_the_anim_table` checks each
  slot's name against its `Status` and each kept-clip mapping. It checks
  that every -1/-2 status keeps its motion. For all twelve fighters, it
  also checks that the pack length equals `motion::anim_length` and that a
  fighter with the motion has a file. `only_the_moves_a_character_lacks_are_absent`
  counts the one new hole (Pikachu `YoshiEgg`).
- `cargo +1.98.0 test --workspace` with absolute `SSB64_ROM`, one thread:
  1,205 pass. Clippy (`-D warnings`), rustfmt and the
  `thumbv7em-none-eabi` builds pass. Both PSP release builds pass.
- Pack v48: 26,905,648 bytes (+879,120), SHA-256
  `4e264113cb1413760fc8abef3b5363d348b62b205377c026a583ec504fc8b76c`.
- PPSSPPHeadless: 73 of 73 goldens match twice. No golden enters these
  statuses, so no change was expected.
- PPSSPP `psp-game` boot smoke: 60 FPS. The 12-second frame is identical
  byte for byte to HEAD (`7ada929`) run with the v47 pack.
