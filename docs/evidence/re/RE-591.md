# RE-591 — Sleep and wake: audio output damaged, audio thread fault, ME not restarted

Status: MEASURED (PSP Slim, 6.61 ARK, PSPLink v3.2.1 and XMB; owner listening)
Topics: audio, hardware, psp-slim, media-engine, power
Relevant files: `psp-runtime/src/power.rs`, `psp-runtime/src/audio.rs`, `psp-runtime/src/me.rs`

## Setup

- PSP Slim, 6.61 ARK, PSPLink v3.2.1; game run from `ms0:/PSP/GAME/ssb64dbg/` (cwd there; `host0:` drops at sleep).
- Builds: `--features profile,audio_dump`; base `1de54eb2` (PRX sha256 `48a4d07e742b512f`), fix PRXs `b22bb72ef560d979`, `6fabf70fc999fe03`.
- Owner pressed the power switch to sleep, then woke the PSP; `audio.raw` = mixed PCM before `sceAudioSRCOutputBlocking`.

## Findings

1. Base, ME on: after the wake, audio "choppy, certain frequencies or volume parts stop working" (owner).
   - `ame` report at the wake: `state=2`, `kmod=0xffffffff` (module file write failed); next report `state=4` (`NO_KMOD`, terminal); SC fallback for the rest of the run.
   - `audio`: `under_total=2` at the wake, then 0 new; `err=0`; 62.5 blocks/s.
   - The mix itself is clean: owner listened to 16 s of `audio.raw` before and after the wake. The damage is in the output path.
2. Base, ME never started (module path replaced by a directory → `NO_KMOD` at boot), `SceMeRpc` left registered: the wake faults the audio thread.
   - `exlist`: thread `ssb_audio`, "Address load/inst fetch", EPC `0x08C007C8` (`ssb_game::combat::goto_damage_status`+0x20), BadVAddr `0xDEADE6E1`, caller-saved registers `0xDEADBEEF`, `ra` = return from the output syscall in `audio::thread_main`.
   - Cause in both runs: the audio thread sat in `sceAudioSRCOutputBlocking` across the suspend and kept the SRC channel reserved before it.
3. Fix (`power`): a callback thread (priority 0x11) on `scePowerRegisterCallback`.
   - Suspend (`SUSPENDING`, or `POWER_SWITCH` without a resume flag): sets `suspended`, waits up to 100 ms for the audio thread to park.
   - Audio thread (`audio::park`): between blocks, waits for the hardware queue to drain (≤ 100 ms), releases the SRC channel, sleeps until resume, reserves the channel again (≤ 100 tries, 10 ms apart), calls `MeExec::resumed`.
   - Resume (`RESUMING` or `RESUME_COMPLETE`): clears `suspended`.
   - Flags seen: boot `0x84`; switch `0x80000084`; resume `0x40084`; second suspend of a run `0x10084` (`SUSPENDING`).
4. Result, fix `b22bb72e` (ME on), 2 sleeps (`susp=2`, `res=2`): owner: audio fine; `exlist` empty; `under_total=0`, `err=0`.
   - ME not back: 3 bring-ups failed `kmod=0xffffffff` → `STATE_GAVE_UP`, SC executor with VFPU reverb; sounded fine.
5. ME restart (`me`): `MeExec::resumed` sets `DOWN`, resets the fail count, first try 120 frames later; a failed module load after the ME has run counts as one of `MAX_FAILS`, not `NO_KMOD`.
   - Module file: relative `ssb64_kcall.prx` from the audio thread after the wake fails, open error `0x8002032c`; the absolute path in the game's folder (`argv[0]`, set at boot) works.
   - Fix `6fabf70f`, 1 sleep: `state=1` again, `kmod=0`, `kfile=0x8002032c`, `resets=2`; `under_total=2` at the wake, 0 after.
6. Owner XMB test (release build of the fix, EBOOT sha256 `a9ffbb49e68011be`, `ms0:/PSP/GAME/ssb64/`, save kept): audio fine after a sleep and wake.
7. PPSSPP: goldens unchanged (5-scene subset); 20 s smoke exit 0.
