# RE-278 — Fixed-coordinate GE sampling matches the addressing model exactly, including the Linear clamp-boundary blend

Status: OPEN
Topics: texture, fighter, hardware, visual-regression
Relevant files: psp/src/addr_diag.rs, psp/Cargo.toml, psp/src/main.rs

**Question.** RE-277 showed `n64_addressing`'s hardware reference model and
this project's `psp_lowering_axis` abstraction agree bit-for-bit at every
real texel RE-272/274's Mario-face primitive reaches -- but that only proves
two *models* of the pipeline agree with each other, not that real GE
hardware (or PPSSPP's software rasterizer, the deterministic golden source)
actually samples that way. RE-274 also never checked `TextureFilter::Linear`
at the exact clamp boundary, where a hardware or emulator bug in neighbour
selection could produce visible artifacts with zero divergence in the
discrete addressing formula.

**Measurement.** Added `psp/src/addr_diag.rs`, a permanent measurement rig
(`addr_diag_probe` feature, same `texgen_normal_diagnostic_*`/
`depth_mask_diagnostic` shape as `normal_diag.rs`/`depth_diag.rs`): a
synthetic 64-texel-wide `Psm8888` texture whose red channel is an
independently-authored triangle wave (`i` for `i<32`, `63-i` for `i>=32`) --
the exact mirror+clamp bake RE-221/RE-274 describe for `mask_s=5,
mirror_s=true, clamp_s=true, drawn_width=64` -- sampled through
`TRANSFORM_2D` sprites at fixed, non-interpolated raw texel-address
coordinates (`Gpu::draw_wallpaper_sprite`'s own established identity-scale
convention), so each probe is exactly one GE texture-unit sample with no
screen-space interpolation to separately model. Two rows repeat 14 probes
(`-31, -1, 0, 5, 31, 32, 45, 63, 63.5, 64, 64.5, 70, 80, 90` texels -- RE-274's
own measured span plus two half-texel probes straddling the drawn rect's far
edge) under `Nearest` and `Linear` filtering. Captured with
`tools/run-ppsspp-headless.sh --feature addr_diag_probe` (EBOOT
`b066065e...5d87c16`, screenshot SHA-256 `f93e489b...2a600a067`), read back at
each probe's known screen column (2x native scale: PPSSPPHeadless emits
960x544 for a 480x272 scene).

Red-channel readout (`Nearest` / `Linear`) against this rig's own
independently-derived prediction:

| probe (texels) | predicted | Nearest | Linear |
|---|---|---|---|
| -31, -1, 0 | 0 (clamp low) | 0, 0, 0 | 0, 0, 0 |
| 5 | 5 | 5 | 4 |
| 31 | 31 | 31 | 30 |
| 32 | 31 (second period starts, flipped) | 31 | 31 |
| 45 | 18 | 18 | 18 |
| 63 | 0 (last baked pixel) | 0 | 0 |
| 63.5 | n/a (half-texel) | 0 | 0 |
| 64 | 0 (clamp high, same held edge as 63) | 0 | 0 |
| 64.5 | n/a (half-texel) | 0 | 0 |
| 70, 80, 90 | 0 | 0, 0, 0 | 0, 0, 0 |

`Nearest` matches the prediction exactly at every integer probe. `Linear`'s
small off-by-ones at `5`/`31` (reading `4`/`30`) are the expected sub-texel
blend from sampling exactly at a texel boundary under bilinear
reconstruction, not an addressing error. Critically, **`63`, `63.5`, `64`,
`64.5`, `70`, `80` and `90` all read exactly `0` under both filters** -- the
GE holds the far-edge texel on both sides of the clamp boundary with no
blend against a wrapped-around or garbage neighbour, and continues holding it
uniformly all the way out to `90` texels, well past RE-274's measured `80`.

**Conclusion.** Fixed-coordinate GE texture sampling -- addressing, clamp,
and `Linear` boundary blending together -- matches the hardware-addressing
model exactly under PPSSPP's software rasterizer, at both integer and
half-texel granularity, for RE-272/274's exact axis configuration. This rules
out "the GE mis-samples a *known* UV coordinate near this clamp boundary" as
RE-272's cause, on top of RE-277's ruling out the addressing formula itself.

What this rig does **not** test, and what remains open: it samples fixed,
non-interpolated coordinates -- it says nothing about whether the GE's
*per-pixel linear interpolation* of UV across an actual 3D triangle (with
perspective correction, real vertex data, and RE-274's full 24-triangle
primitive's per-*triangle* UV delta, which may differ from the whole
primitive's aggregate `-31..80` bbox this rig borrowed) introduces the
artifact instead. Also untested: the real primitive's actual pixel format is
`Ci4` (4-bit paletted, CLUT-indexed) with a mip/swizzle path this rig's plain
`Psm8888` texture does not exercise. The next step is a rig closer to
RE-274's real draw: a small number of real triangles (not a 2D sprite) with
authored `GU_TEXTURE_16BIT` UVs spanning a comparable per-triangle delta,
through the same `Ci4`/CLUT path `bind_texture` actually uses, to isolate
whether triangle-interpolation precision or the paletted-format path is where
this diverges from the fixed-coordinate case this record clears.

**Confidence: high** on the measurement (exact, reproducible readback,
confirmed on a second identical build/capture); the redirected scope
(interpolation precision or CI4-specific path) is not yet independently
tested.
