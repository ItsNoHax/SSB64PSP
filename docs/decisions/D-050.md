# D-050: FPU Trap Enables Stay As the PSP Arms Them; Every Trap Is a Bug Fixed With the N64's Result

Category: Platform & Toolchain

**Decision:** The game does not change the PSP's FCR31. Both game threads
start with V, Z and O trap enables set (`0x0e00`, measured under PSPLink
and at an XMB-style LoadExec launch, RE-516). Any float operation that traps there is a bug in our code. It is
fixed by reproducing the N64's result without the trapping instruction:

- `ssb_engine::math::div_ieee`: IEEE quotient, including x/0 = inf and 0/0 NaN
  (libultra sets FS|EV, so the N64 divides by zero without trapping).
- `ssb_engine::math::f32_to_i32_sat`: the saturating `as i32` without
  `trunc.w.s` (NaN gives 0).
- `ssb_engine::math::div_nonzero`: a division LLVM may not speculate.

Host tests arm the same traps (`ssb_engine::fpu_traps::with_traps`). The
`fpu_mask` cargo feature masks all enables for A/B diagnosis only and is
never part of a release build.

**Reasoning:** Rust and LLVM assume masked exceptions: `as` runs `trunc.w.s`
before it saturates and divisions may be hoisted past their guards (RE-469).
Masking in release would hide bugs, and the N64 itself still traps Invalid.
**Amendment trigger:** a launch whose FCR31 differs from `0x0e00`, or
evidence that masking is needed for a fighter.
