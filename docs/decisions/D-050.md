# D-050: FPU Trap Enables Stay As the PSP Arms Them; Every Trap Is a Bug Fixed With the N64's Result

Category: Platform & Toolchain

## Decision
- Game does not change the PSP's FCR31.
- Both game threads start with V, Z, O trap enables set: `0x0e00`.
  - Measured under PSPLink and at an XMB-style LoadExec launch (RE-516).
- Any float operation that traps is a bug in our code.
  - Fix: reproduce the N64's result without the trapping instruction.

| Helper (`ssb_engine::math`) | Behaviour |
|---|---|
| `div_ieee` | IEEE quotient; x/0 = inf, 0/0 NaN; libultra sets FS\|EV, so the N64 divides by zero without trapping |
| `f32_to_i32_sat` | saturating `as i32` without `trunc.w.s`; NaN gives 0 |
| `div_nonzero` | division LLVM may not speculate |

- Never keep float state in an `Option` payload or `None`-seeded accumulator that a guard skips.
  - why: LLVM speculates the compare or multiply onto unwritten stack.
  - Use: enum or integer, always-initialised struct with a flag, or a `found` flag.
  - `stack_poison` feature (hardware only) detects the class (RE-531).
- `Option<f32-bearing>` payload read in float math after a tag test: use `ssb_engine::math::defined_or` (`black_box` barrier) or a real store.
  - `unwrap_or(CONST)` is not enough; LLVM folds it back onto the payload (RE-531).
- Host tests arm the same traps: `ssb_engine::fpu_traps::with_traps`.
- `fpu_mask` feature: masks all enables, A/B diagnosis only, never in a release build.

## Why
- Rust and LLVM assume masked exceptions (RE-469).
  - `as` runs `trunc.w.s` before it saturates.
  - Divisions may be hoisted past their guards.
- Masking in release hides bugs; the N64 itself still traps Invalid.

## Amendment trigger
- Launch whose FCR31 differs from `0x0e00`.
- Evidence that masking is needed for a fighter.
