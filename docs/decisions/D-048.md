# D-048: Nothing Read From the ROM Is Committed — Tables Are Generated at Build Time, Goldens Are Pixel Hashes

Category: Version Control

**Decision:** The repository holds no data taken from the ROM and no
picture of the game. It extends [D-033](D-033.md) from the ROM and the
asset pack to everything else.

- **Tables.** `ssb-game` and `ssb-rom` read some tables that the original
  keeps in its code and data segments rather than in the asset archive:
  fighter motion scripts and motion tables, colour-animation scripts, CPU
  input scripts and attack tables, status flags, and the fighter animation
  table. Tables in the fighters' archive files count too: joint masks, hidden
  and texture parts, hurtbox descriptors and Falcon Dive's capture offsets
  ([RE-544](../evidence/re/RE-544.md)), and so do the other relocData
  attribute structs: item attributes, the monster weapons' attributes, the
  Smog's scale animation, Mario's physics and Kirby's copy table
  ([RE-545](../evidence/re/RE-545.md)). So do the decompilation's `d*`
  data arrays compiled into the code and overlay segments (user decision,
  2026-10-18): the handicap, costume, item-throw, ground-hit, Zebes acid,
  Sector Z Arwing, Yoshi egg, charge-shot, shield-colour and boss tables;
  the countdown, pause and announcer HUD data; the title, Characters, 1P
  Game, stage-clear, staff-roll, congratulations and opening scene data;
  and the archive file ids, offsets and effect and transition descriptors
  `ssb-rom` reads from the code (`ssb-tablegen`'s `battle_data`,
  `ifcommon`, `menu_data`, `sc1p_data`, `ending_data`, `opening_data` and
  `rom_layout`; [RE-546](../evidence/re/RE-546.md)). The smaller `d*`
  arrays (HUD digit widths and colours, camera and projection defaults,
  fighter, item, weapon, effect and stage constants, the `dLBCommonSinLookup`
  sine table) come from one generic generator, `ssb-tablegen`'s
  `d_arrays`: each crate's list (`d_arrays/{game_a,game_b,rom,engine}.rs`)
  gives every array's symbol, overlay, address, element type, shape and,
  for one field of a record array, its stride. `ssb-game`, `ssb-rom` and
  `ssb-engine` include the result as a private `crate::d_arrays` module and
  name each array after its symbol without the `d`, in `UPPER_SNAKE`
  ([RE-547](../evidence/re/RE-547.md)). Each is read at its
  symbol's overlay, from the overlay's ROM start, never from a VRAM alone.
  Their build scripts call `crates/ssb-tablegen`. It finds the ROM
  (`SSB64_ROM`, else the single `.z64` in `rom/`), verifies its SHA-1 and
  writes the tables as Rust into Cargo's `OUT_DIR`, and the crates
  `include!` them from there. Only where each table lies and how it is laid
  out is committed: ROM offsets, record sizes, counts, word counts and
  non-script regions, and the identifiers the port gives entries. Without a
  ROM the build stops and says how to supply one.
- **Stub tables.** `SSB64_STUB_TABLES=1` makes empty tables of the same
  types and sets `cfg(ssb64_stub_tables)`. This is for CI, which has no ROM:
  it type-checks, lints and runs every test that does not need ROM data.
  Tests that do are marked
  `#[cfg_attr(ssb64_stub_tables, ignore = "needs the ROM-generated tables")]`.
  Tests and tools that read the ROM themselves find it with
  `ssb_tablegen::test_rom(env!("CARGO_MANIFEST_DIR"))`, the build scripts'
  `locate_rom` (`SSB64_ROM`, else the single `.z64` in `rom/`), and skip
  when there is none. A stub build cannot run the game.
- **Goldens.** A golden capture is recorded as the SHA-256 of its decoded
  pixels in `tests/golden/hashes.tsv`. Its PNG is never committed. Local PNGs
  for difference masks live in the gitignored `tests/golden/local/`
  ([visual regression](../visual-regression/README.md)).
- **Enforcement.** `tools/docs/validate_docs.py` (CI) fails on any tracked
  ROM, pack, save or binary file, any image or media file outside the
  original XMB artwork (`psp-game/xmb/`, `psp-asset-viewer/xmb/`), any
  known generated-table path, and any tracked `.rs` file with a generated
  header. Check 10 (`tools/docs/rom_tables.py`) fails on a new
  hand-transcribed table in any crate (`ssb-tablegen` aside, whose tables
  are the ROM layout): a const or static array of 8 or more numeric
  literals (24 in test code), a struct literal or tuple static of 8 or
  more, or a const or static of 2 or more whose doc comment names a data
  symbol (a `d*` name with a module or fighter prefix, an `ll*` label or a
  `relocData/NNN_*.c` file) and that does not read the generated
  `d_arrays`, unless `tools/docs/rom_tables_baseline.tsv` lists it with its
  reason; a row whose table is gone fails too, so the list only shrinks.
  Literals inside an index are positions and not counted. Its local scan
  (`tools/local_arrays.py`) places a function-local array in the overlay.
  Scalar constants in function or `match` bodies are out of scope while
  the per-fighter ROM struct values (attributes, hitboxes, throw
  descriptors, item events) are generated.
- **Layout versus data.** `SpriteFile` manifests and `*_OFFSETS` tables are
  layout (label offsets in a file) and may stay. `Backup`'s default is
  generated from `dSCManagerDefaultBackupData`. `effect.rs` `QUAKE` and
  `THUNDER_SHOCK` stay baselined as open until `ssb-tablegen` can play
  AnimJoint scripts (`PLAN.md`).

**Reasoning:** The tables used to be committed. `tools/gen-*.py`
transcribed them from the decompilation's C sources, which describe bytes
in the ROM, so the source tree held about 1.5 MB of the game's data. The
golden PNGs showed its characters and stages. Generating the tables from
the user's ROM makes the README's legal statement true for the tree. It
also removes the Python generators' last dependency on a local
decompilation checkout.

The ROM-based generator reproduces the committed tables exactly, with one
exception. The motion scripts' sound commands, and four `SetFlag1` words
in the Star Rod swing scripts that carry a sound id, now hold the ROM's
FGM and voice ids. The Python generator could not resolve the
decompilation's `nSYAudio*` enumerators and wrote 0 for them. Audio is not
ported. The motion interpreter skips sound commands, and the Star Rod
status clears flag 1 without reading it. So nothing the port does
changes: the workspace tests, the golden matrix and How to Play's
`rng_trace` are unchanged.

Not covered: the gameplay code itself is a translation of the decompiled
code. It contains the constants, enum values and small tables the
translated functions use, such as `colanim_preserve.rs`, which lists the
`ftMainSetStatus` call sites whose flags preserve state. These are facts
about the original's code, not tables the ROM holds as data. A named `d*`
array is data, not code, even when the code segment holds it (user
decision, 2026-10-18, above). Only the `ll*` link-time offsets the code
passes as immediates, `match`-arm values and test fixtures remain; the
baseline lists each with its reason.

Amendment (2026-10-19): arrays local to a decompiled function (initialised
locals the compiler placed in the overlay's `.data`, strings in `.rodata`)
are ROM tables. They are generated through `ssb-tablegen`'s `d_arrays`
(`DArray::local`, `CStr`), each read at its overlay and vram. Enum-valued
lists are generated with checked const mappings
([RE-548](../evidence/re/RE-548.md)).
