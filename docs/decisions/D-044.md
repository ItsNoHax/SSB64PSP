# D-044: PSP Backend Split Into Shared psp-runtime + Two Applications

Category: Platform & Toolchain

## Decision
- One shared library: `psp-runtime/` (package `ssb-psp-runtime`).
- Two applications on it:
  - `psp-asset-viewer/`: debug, render validation.
  - `psp-game/`: player-facing front end, Training.

```
psp-asset-viewer ─┐
                  ├──> psp-runtime ──┬──> crates/ssb-engine
psp-game ─────────┘                  ├──> crates/ssb-rom
                                      └──> crates/ssb-game
```

- `ssb-engine`, `ssb-rom`, `ssb-game` never depend on `psp-runtime`.
- `psp-runtime` owns:
  - PSP asset loading, input, timing.
  - GE/GU rendering: `gu.rs`, `meshdraw.rs`.
  - Pack-to-game scene bridge `scene.rs`: `FloorSegments`, `FighterScene`, packed-data conversions, skeleton ticking.
- Stay in each app crate:
  - App diagnostics: viewer overlays, regression-scene selection.
  - Gameplay orchestration: Training state, scripted regression input, `Dummy`/`apply_hit_from`.
- `psp-runtime` has no `rust-toolchain.toml`; invoking app's pinned nightly (D-026) governs the build.

## Why
- Two hand-copied backends diverged and were costly to sync (RE-297).
  - Merge surfaced a bug: `sceGuViewport`/`sceGuScissor` outside an open `sceGuStart`/`sceGuSync` block are silently dropped.
- Enforced dependency direction keeps game logic portable.
- PSP hardware code in one place; apps differ only where they must.
