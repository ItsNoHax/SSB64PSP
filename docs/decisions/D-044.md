# D-044: PSP Backend Split Into Shared psp-runtime + Two Applications

Category: Platform & Toolchain

**Decision:** The PSP backend is one shared library, `psp-runtime/`
(package `ssb-psp-runtime`), plus two independent PSP applications built on
it: `psp-asset-viewer/` (debug/rendering-validation) and `psp-game/`
(player-facing front end/Training). Dependency direction:

```
psp-asset-viewer ─┐
                  ├──> psp-runtime ──┬──> crates/ssb-engine
psp-game ─────────┘                  ├──> crates/ssb-rom
                                      └──> crates/ssb-game
```

`crates/ssb-engine`, `crates/ssb-rom` and `crates/ssb-game` must never
depend on `psp-runtime`. `psp-runtime` owns PSP asset loading, input,
timing, GE/GU rendering (`gu.rs`/`meshdraw.rs`), and the pack-to-game scene
bridge (`scene.rs`: `FloorSegments`, `FighterScene`, packed-data
conversions, skeleton ticking). Application-specific diagnostics (viewer
overlays, regression-scene selection) and application-specific gameplay
orchestration (Training-session state, the scripted regression-input
script, `Dummy`/`apply_hit_from`) stay in their own crate.

`psp-runtime` is a library, not an executable, and has no
`rust-toolchain.toml` of its own: both applications pull it in as a path
dependency, and the invoking application's own pinned nightly (D-026)
governs the whole build, including `psp-runtime`.

**Reasoning:** Before this split, `psp-asset-viewer/` (then `psp/`) and
`psp-game/` each carried an independent, hand-copied implementation of the
entire PSP backend — `input.rs` was byte-identical, `meshdraw.rs` differed
only by a doc comment, and `gu.rs`/`play.rs` had already started to diverge
in ways that were easy to miss and expensive to keep in sync by hand (see
RE-297 for the renderer-merge details, including one real bug the merge
surfaced: `sceGuViewport`/`sceGuScissor` calls outside an open
`sceGuStart`/`sceGuSync` block are silently dropped). A shared library with
an explicit, enforced dependency direction keeps portable game logic
portable, keeps PSP hardware code in one place, and lets the two
applications diverge only where they are genuinely different (debug
diagnostics vs. Training gameplay) without duplicating everything else.
