# D-045: Save Data Is the N64 SRAM Image in a Plain File Beside the Pack

Category: Platform & Toolchain

## Decision
- Save `gSCManagerBackupData` as the N64 SRAM image.
  - Image: `ssb_game::backup::Backup::image`.
  - Layout: two big-endian copies of `LBBackupData`, 0x5EC bytes each, at 0 and 0x5F0.
  - Checksum: `lbBackupCreateChecksum`.
- File: plain `ssb64.sav`, in the directory the pack loaded from (`ssb64.pak`'s three search paths).
- `psp-runtime/src/savedata.rs`:
  - Read: `sceIoRead` at boot.
  - Write: `sceIoOpen(WR_ONLY | CREAT)` (no truncation), two `sceIoWrite`s, first copy then second.
  - Write trigger: whenever `Backup::writes` moves.
- Do not use `sceUtilitySavedata`.
- Load: `lbBackupIsSramValid` unchanged.
  - First valid copy wins; bad first copy restored from second.
  - Missing, short or doubly invalid file: fall back to `dSCManagerDefaultBackupData`, write back.
- Golden captures neither load nor save; only `saveunlock`/`saveplayers` scenes do.

## Why
- Save is 3 KB, written at few scene transitions like the N64's SRAM DMA.
  - Synchronous write stalls only a transition (not measured on hardware).
- `sceUtilitySavedata` costs:
  - Async dialog pumped every frame beside the display list.
  - Needs `PARAM.SFO`, icon, title per save; holds utility memory.
  - ~6 MB left in challenger battle, no menu to host it: risk, no gameplay benefit.
- oot-PSP precedent: plain `sceIo` file beside the EBOOT (`OotPsp_LoadSram`, `OotPsp_FlushSram`).
- N64 byte layout and both copies:
  - Fallback stays meaningful (cut-short write leaves other copy).
  - Host test checks defaults byte-for-byte against the ROM.
- Beside the pack, not `ms0:/PSP/SAVEDATA`: folder there without `PARAM.SFO` shows as corrupted data in XMB.

## Consequences
- XMB save manager neither lists nor copies the save.
- Moving to `sceUtilitySavedata` needs only a new `savedata.rs` backend; image format and portable model stay.
