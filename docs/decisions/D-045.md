# D-045: Save Data Is the N64 SRAM Image in a Plain File Beside the Pack

Category: Platform & Toolchain

**Decision:** `gSCManagerBackupData` is saved as the N64's SRAM image
(`ssb_game::backup::Backup::image`: two big-endian copies of
`LBBackupData`, 0x5EC bytes each, at 0 and 0x5F0, with
`lbBackupCreateChecksum`'s checksum) in a plain file, `ssb64.sav`, in the
directory the asset pack was loaded from (`ssb64.pak`'s three search
paths). `psp-runtime/src/savedata.rs` reads it with `sceIoRead` at boot and
writes it with `sceIoOpen(WR_ONLY | CREAT)` (no truncation) and two
`sceIoWrite`s, first copy then second, whenever the portable game's
`Backup::writes` count moves. `sceUtilitySavedata` is not used.

Loading is `lbBackupIsSramValid` unchanged: the first valid copy wins, a
bad first copy is restored from the second, and a missing, short or
doubly invalid file falls back to `dSCManagerDefaultBackupData` and is
written back. Golden captures neither load nor save (only the
`saveunlock`/`saveplayers` scenes do), so a play session's save cannot
change a capture.

**Reasoning:**

- The save is 3 KB and written at a handful of scene transitions, like
  the N64's SRAM DMA, so a synchronous write stalls only a scene
  transition (not measured on hardware).
- `sceUtilitySavedata` is an asynchronous utility dialog that must be
  pumped every frame alongside the GU display list, needs a
  `PARAM.SFO`, icon and title strings per save, and holds utility
  memory while it runs. With about 6 MB left in the
  challenger battle (pack v103) and no menu to host the dialog, it adds
  risk for no gameplay benefit. oot-PSP keeps its SRAM the same way, as
  a plain `sceIo` file beside the EBOOT (`OotPsp_LoadSram`,
  `OotPsp_FlushSram`); sf64-psp does not persist its EEPROM at all.
- Keeping the N64 byte layout and both copies keeps
  `lbBackupIsSramValid`'s fallback meaningful (a write cut short leaves the
  other copy) and lets a host test check the defaults byte-for-byte
  against `dSCManagerDefaultBackupData` in the ROM.
- Beside the pack rather than under `ms0:/PSP/SAVEDATA`: a folder there
  without `PARAM.SFO` shows as corrupted data in the XMB, and the EBOOT's
  own directory is where the same build already finds its pack under
  PPSSPP and on a memory stick.

**Consequences:** The XMB's save manager does not list or copy the save.
Moving to `sceUtilitySavedata` later needs only a new `savedata.rs`
backend; the image format and the portable model stay.
