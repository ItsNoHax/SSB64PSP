# F1 — Front End & Training Mode

Part of [PLAN.md](../../PLAN.md). Runs in parallel with `R3` (rendering
performance) — depends only on `R2` (physical rendering validation),
`COMPLETE`. Must not block, or be blocked by, `R3`.

Status: `TODO`

## Objective

Build the PSP-native front end — intro/splash screen, main menu, minimal
character select and stage select — and a Training Mode combat sandbox, as a
**new, separate PSP application** distinct from the existing debug asset
viewer (`psp/`). Both applications share the existing library crates
(`crates/ssb-engine`, `crates/ssb-rom`, `crates/ssb-game`) but produce
independent EBOOTs.

This is the one explicit, scoped exception to the rendering-gate-before-
combat rule (`AGENTS.md`, `PLAN.md` §1). It exists so the front end and a
real (not stubbed) combat vertical slice can be built and evidenced now,
without waiting on `R3` or opening full match combat (`G0`–`G2`), which stay
gated.

## Dependencies

* `R2` — Physical PSP Rendering Validation — `COMPLETE`
* Explicitly independent of `R3` — Rendering Performance — `NOT_STARTED`

## Scope — what is in vs. out

In scope (allowed under the carve-out):

* Intro/splash screen, main menu, minimal character select, minimal stage
  select.
* One player-controlled fighter vs. one stationary/dummy target, no AI.
* Real hitbox/hurtbox from `FTAttributes` descriptors (RE-032).
* Real damage/knockback/hitstun physics ported from `ftphysics.c`.
* At least one grounded attack, input → hitbox → hurtbox → damage →
  knockback → hitstun, end to end, verified against decomp.

Out of scope (stays behind `R3` + `G0`–`G2`):

* CPU AI / any non-player-controlled opponent.
* Stocks, blast zones, KO logic, match timer, sudden death.
* Items, hazards, multiplayer.
* Any additional game mode beyond Training (VS/1P/etc. are `G2`).

Acceptance criterion 6 below requires this boundary to be verifiably absent,
not merely unused.

## Acceptance Criteria

1. New PSP application (its own crate/Cargo.toml/EBOOT, e.g. `psp-game/`)
   boots independently of the asset-viewer PRX; the existing `psp/` crate's
   build and EBOOT are unmodified by this work.
2. Intro/splash screen renders and transitions to the main menu on input.
3. Main menu offers Training Mode as a selectable entry (other entries may
   be stubbed/placeholder).
4. Minimal character select and stage select feed into a loaded scene,
   reusing existing stage/fighter loading code from the shared crates.
5. Training mode: the player-controlled fighter executes at least one
   grounded attack against a stationary dummy/target, applying decomp-
   accurate hitbox/hurtbox, damage, and knockback/hitstun.
6. No stocks, KO, match timer, CPU AI, or items exist in this build —
   confirmed absent by inspection, not just unreachable from the menu.
7. All new combat code is verified against the original decompilation
   (`ft/ftkey.c`, `ftphysics.c`, `FTAttributes` hitbox descriptors) per the
   reference hierarchy (`PLAN.md` §4).
8. Evidence recorded per the existing verification standard (PPSSPP first,
   then physical PSP per the `psp-hardware` Skill).

## Verification

* PPSSPP (`visual-regression` Skill) for intro/menu screens and the training
  scene where a deterministic capture is feasible.
* Physical PSP (`psp-hardware` Skill) for the training-mode combat loop.
* Decomp cross-check for every new hitbox/damage/knockback value (`ft/`
  sources, `ftphysics.c`).

## Scene loading — still to build

The first `psp-game/` increment (crate scaffold, intro/menu state machine)
draws only flat coloured rectangles: no pack, no stage, no fighter, no
texture. That is scaffolding, not the shipped front end. Reaching acceptance
criteria 4-5 needs real scene loading in `psp-game/`, ported from `psp/`'s
equivalent pieces (own copies, per the crate-boundary rule above — not a
shared refactor of `psp/`):

* `assets.rs` — load `assets/generated/ssb64.pak` into a heap buffer and
  open it with `ssb_rom::pack::Pack`, mirroring `psp/src/assets.rs`. **Done,
  RE-291** — the pack loads and parses; nothing is drawn from it yet (needs
  the 3D pipeline below).
* A full `gu.rs` 3D pipeline (depth test, culling, projection/view matrices,
  textured mesh drawing), plus `meshdraw.rs`'s mesh/texture drawing and
  `play.rs`'s fighter/stage instantiation through `ssb-game`'s `Fighter`,
  `ground`, and `camera` modules. **Done, RE-292** — all three ported
  verbatim from `psp/`; Training spawns a real Mario on Dream Land (stage
  index 0) and draws both through the real battle camera, pixel-confirmed.
  Character select, stage select and costume/character choice still feed a
  hardcoded default rather than a real selection UI; material/stage-scenery
  animation are not ticked (documented simplifications, not guesses). Jump
  is now wired, **RE-295** — any N64 C-button tap, decomp-sourced.
* Real on-screen text for menu/select labels. `sceGuDebugPrint`/
  `sceGuDebugFlush` is not an option (RE-202: crashes real hardware, which is
  why `psp/`'s own use of it is gated behind an off-by-default
  `debug_overlay` feature). Use `sceFont` (PGF glyph rasterisation into a GE
  texture) instead — real, shippable UI text, not a diagnostic overlay.

## Known Limitations

* Single stationary dummy target only — no CPU, no second live fighter.
* Not a full `G0` vertical slice: `G0` additionally requires an opponent,
  stock handling and a match loop, which stay `BLOCKED_BY_R3`.
* Menu scope here is minimal (enough to reach Training Mode); the remaining
  `G3` scope (options, save/persistence, results screen, credits) is not
  covered.
